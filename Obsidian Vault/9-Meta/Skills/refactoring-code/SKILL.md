# 安全重构代码

## 核心原则

在不改变可观察行为的前提下改善结构。把重构做成一串小而可逆的步骤；一次只解决一个问题，每一步后验证。

## 硬性约束

- 先读取仓库规则、架构约束和现有测试；服从项目约定，不套用个人偏好。
- 把新增功能、修复行为、性能优化与结构重构分开。需要改变行为时，先明确并测试新行为，再单独实施。
- 建立当前环境可提供的最强基线。能运行时优先测试；无法直接运行时，不因此放弃重构，但必须降低改动幅度并补充替代证据。
- 保护公共接口、协议、持久化格式和外部调用方。无法同步修改全部消费者时，保留兼容入口并委托到新实现。
- 不为“将来可能需要”制造抽象。只处理当前证据支持的坏味道。

## 工作流

1. **界定目标**：写清要消除的坏味道、保持不变的行为、影响范围与完成标准。
2. **建立地图**：定位定义、调用者、子类、数据所有权、测试及跨模块边界；先理解再编辑。
3. **验证基线**：运行可用的最小相关测试；无法运行时，组合静态分析、历史运行材料和人工验证清单，记录原始结果。
4. **选择一步**：采用当前最小、可命名、可回退的重构；避免一次迁移多个职责。
5. **修改并验证**：完成一个原子改动后立即执行当前最强验证。失败时回到最后一个已知正确状态，不在多步混合改动上猜错。
6. **逐步扩大**：已有证据持续成立后，再扩大验证范围；仅在收益仍明确时继续下一步。
7. **交付证据**：区分已运行验证、静态验证和待游戏内验证，说明剩余风险与复验方法。

## 无法直接运行时

按可靠性从高到低组合证据，不把任何单项静态检查当作运行验证：

1. **静态验证**：执行语法、类型、导入和构建检查；追踪调用链、事件订阅、协议入口、生命周期、数据所有权及平台分支；逐项对照重构前后的控制流、副作用、调用顺序和返回值。
2. **历史材料**：利用日志、协议样本、崩溃栈、回放数据、配置、截图或录屏锁定现有行为。
3. **游戏内验证清单**：写明所需环境、操作步骤和预期现象，例如登录、切场景、进入战斗、打开界面、协议收发及 PC/移动端覆盖。

根据风险控制修改深度：

- 纯计算、纯数据转换和局部机械改名：证据充分时可以完成静态重构。
- UI、事件、协议和对象生命周期：保持补丁极小，必须标记待游戏内验证。
- 战斗队列、异步时序、引擎状态和跨平台行为：没有运行环境时不得宣称完成；只准备可审查、可回退的最小补丁。

把未完成的运行验证记录为**验证债务**：列出未验证场景、所需环境、预期结果和失败后的回退点。静态验证只能提高信心，不能证明运行时行为完全等价。

## 快速决策

| 信号 | 优先考虑 | 警惕 |
|---|---|---|
| 过长函数、注释解释“做什么” | 提炼并按意图命名函数 | 无法准确命名时强行拆分 |
| 重复代码 | 提炼函数、上移共同实现或集中算法 | 只有表面相似却强行统一 |
| 类过大、因多种原因变化 | 提炼类，搬移字段与函数 | 新类没有清晰职责 |
| 函数更依赖别处的数据 | 搬移函数到数据所有者附近 | 为搬移引入更深消息链 |
| 嵌套条件遮住主路径 | 卫语句、分解或合并条件 | 单次条件就引入复杂层级 |
| 多处按稳定类型选择行为 | 状态、策略或多态 | 类型易变或分支仅出现一次 |
| 参数总是成组出现 | 参数对象或保持对象完整 | 传入远超所需的庞大对象 |
| 查询同时修改状态 | 分离查询与命令 | 为兼容而偷偷保留副作用 |
| 继承只复用少量实现 | 委托或折叠继承体系 | 因代码复用误判“是一个”关系 |
| 消息链暴露导航结构 | 隐藏委托关系 | 形成只会转发的中间人 |

## 边界判断

- 让共同变化的数据与行为靠近，让不同原因导致的变化分开。
- 优先依赖职责、数据所有权和调用方向判断归属，不依赖文件大小或行数阈值。
- 提炼函数时按“做什么”命名；搬移函数时优先靠近它最常使用的数据。
- 在隐藏委托与移除中间人之间，选择能让调用方知道更少、同时不制造空壳转发层的边界。
- 性能问题先测量热点；只有证据表明结构改动影响目标指标时，才在独立步骤优化。

## 示例

为 200 行计价函数增加折扣时，先用特征测试锁定现有价格。若游戏环境无法运行，则先追踪所有调用者和副作用，用历史价格样本对照纯计算部分，只提炼并命名“基础价格计算”；同时记录游戏内价格复验步骤。折扣仍应在独立改动中实现，不要同时重写模型、替换算法和修改公共接口。

## 停止条件

出现以下任一情况时停止扩大改动：无法说明行为为何等价；现有行为不明确；静态分析无法覆盖关键运行时序；影响范围持续扩大；需要猜测外部接口；收益已不再清晰。保留证据充分的小改动，或完整回退到最后一个已知正确状态，并交付验证债务。

# 工程原则

解释代码流程、设计或修改代码前读取，审查时据此核对。小问题、小改动由主线程直接处理，不启动设计子代理；普通文档编辑、配置录入和只读调查也不触发该流程。

## 总目标：降低复杂度

所有设计和编码都以降低复杂度为目标，以下原则优先于局部便利。以修改扩散、认知负荷和隐含依赖衡量复杂度，不以代码行数或方法数量判断优劣。

## 图示表达

解释代码流程、呈现设计方案时必须使用 Mermaid 图，以图为主，文字只补充结论、理由、约束和待决策事项。按问题选流程图、时序图、架构图或状态图；默认一张主图，必要时补局部图，只保留关键职责、路径、分支和变化，省略实现细节。区分当前实现、拟议方案和推断，必要的源码依据放在图外。

## 编码前先设计

无论改动大小，动手前都先：
- 说明关键假设（显而易见的可省略）；需求有多种理解时列出来问用户，不默默选一种。
- 有更简单的做法时直接提出。用户提出的方案也要先判断：该反对就反对，有明显风险或更好的做法时明确说出来并给出理由；没有就直接采用，不为显得审慎而罗列利弊。用户权衡后做出决定的，按用户的决定执行。

先由主线程判断改动范围。目标明确、影响局部、方案直接且不涉及接口或架构取舍的小问题、小改动，主线程确认相关代码后直接修改并做必要验证，不为走流程启动子代理，也不额外要求设计文档。不能仅凭代码行数少判断问题简单。

涉及模块职责、公共接口、跨模块行为或明显方案取舍的任务，才执行独立设计流程：

1. 只读调查需求、已有接口、兼容约束和相关代码。
2. 按下方「独立子代理」启动一位设计子代理，只提供必要上下文，要求它返回职责、接口、取舍和验证要点。
3. 主线程同时独立设计，自身设计完成后再参考子代理结果，给出最终方案，在已有 spec 或对话中简述结论后编码，不机械拼接方案。

小问题、小改动不使用子代理，也不受下一节条件的阻塞。

编码完成后的审查循环见同目录 `code-review.md`。

## 独立子代理

设计子代理和审查子代理（见 `code-review.md`）都按本节要求启动：

- 与主线程**同模型**，**不继承当前对话历史**，只拿到任务说明中给出的信息。
- **只读**：不修改任何文件；任务中写明“不得派生、调用或请求新的子代理”。
- 主线程在使用子代理前确认实际模型；同模型或历史隔离做不到、模型身份不明时，说明限制并询问用户替代方式，确认前只读，不静默替换，也不把未完成的结果当作完成。

**Claude Code 下的执行方式**：主线程从系统提示的模型 ID 确认自身模型。使用 Agent 工具的 `Plan` 类型：它从空白上下文开始，没有写文件和派生子代理的能力；不使用 fork 等继承当前历史的方式。`model` 显式传入与主线程同系列的别名（如主线程为 `claude-opus-*` 时传 `opus`），并要求子代理在结果开头报告其系统提示中的模型 ID；主线程核对与自身一致后再采用。

## 设计与实现

- **避免修改扩散**：同一项知识改变却需要多处手动同步时，重构或重新整理逻辑，使其只有一个来源，不逐处复制修补。接口、实现和测试各自承担不同职责，不因修改涉及多个文件就认定结构有问题。
- **深模块**：将复杂逻辑封装在实现内部，对外提供简单、容易调用的接口。接口同时包括形式化定义（类型、参数、返回值）和文档契约（用途、前置条件、副作用、边界行为），两者都要完整，不隐瞒必要的错误和生命周期约束。
- **消除隐含依赖**：不留下“修改 A 却不知道还必须改 B”的依赖。优先通过设计消除；无法消除时，用类型或编译期检查显式约束，无法有效约束时至少在两处注释中互相指明关联和同步条件。
- **相关逻辑集中**：必须相互了解内部实现才能正常工作的逻辑，应合并或放在一起并重划职责；不为控制文件或函数行数拆散完整操作，契约清晰的正常协作除外。
- **最少实现**：只实现需求要求的内容，不加没要求的功能，不为不可能发生的情况写错误处理。
- **改动可追溯**：每处改动都能对应到需求。发现的无关问题（包括死代码）在交付时指出，不顺手修改；只清理本次改动造成的无用 import、变量和函数。
- **适度通用**：优先考虑稍微通用、能简化接口的方案，分开通用机制和业务专用策略；不为假设需求增加抽象、开关或参数。
- **集中处理或消除异常**：在能够做出恢复或失败决策的统一边界处理异常，不到处重复 try/catch，也不捕获后吞掉错误。可在保持契约正确的前提下调整操作定义，消除不必要的异常，例如将删除定义为“确保不存在”；不得据此静默忽略权限、数据损坏等真实失败。资源释放和 Mock 恢复仍在所属作用域使用 finally 等机制保证。
- **及时重构**：本次改动引入上述复杂度时，在本次修改中整理相关逻辑，不留待以后。重构范围较大或超出当前任务时，先说明问题、影响和方案，由用户决定是否一并处理；不擅自扩大到无关代码。
- **准确命名**：同一概念同名，不同概念异名；避免模糊词，例如不同含义的 `block` 应使用准确限定词。
- **保持风格**：修改现有代码时沿用命名、布局、错误处理和组织方式；本次新增或实质修改的文档注释按下述规范编写，不全量改写历史注释。

## 注释与文档

注释使用中文。本次新增或实质修改的每个类、接口、枚举、枚举项及类型成员都写文档注释；修改现有行为时同步修正相关注释，不给无关旧代码补注释。说明职责和契约，不机械复述名称。

采用对应语言的标准文档注释风格；Python 使用 Google 风格 docstring。`Args`、`Returns`／`Yields`、`Raises`、`Attributes`、`Examples` 按需填写；简单成员可只写一句话，不凑区块或重复显然的信息。

- **文件与类型**：文件头说明用途，类说明职责、资源归属和生命周期；工具类必要时给简短用法，不复述实现过程。
- **接口与事件**：说明调用契约，按需交代参数、返回值、异常、触发时机和副作用。优先写易误用的约束，如完整集合还是增量输入、重复调用限制、资源释放责任和状态保留范围。
- **数据字段与枚举项**：逐项说明作用，必要时补单位、范围和空值含义；类型字段可集中于 `Attributes`，但不能遗漏成员。
- **复杂实现**：必须在对应代码前解释为什么这样做，包括约束、边界、风险和取舍，不复述代码步骤。较长的设计取舍放入 spec，代码处保留必要说明和指向。
- **逻辑分隔**：函数内不同逻辑块、多个“注释＋代码”块之间用空行分隔。
- **表达**：术语直接、准确、简短，不用比喻代替具体概念，不重复代码，也不用注释弥补含糊命名。依赖处互相指明位置，完整说明只维护一份。
- **一致性**：修改后核对注释中的参数、触发来源、状态和释放条件；“唯一”“始终”等断言须有代码依据，过时说明及时修正或删除。

交付前核对复杂度、接口、命名、职责边界和注释是否符合上述要求。

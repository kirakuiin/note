# 编码后审查循环

代码修改完成、交付之前读取本文件。本文件只讲交付前由 Codex 做的审查；用户要求提 CR、把已提交的改动上传到 reviewboard 时，见 `cr-diff.md`。

整体顺序：

```text
编码 → Codex review（本文件，直到收敛） → 真机自检 → 交付总结 + 提交说明
```

- 真机自检委派执行（test 任务，默认包含改动执行检查 `exec-check.md`），见 `cli.md`。主会话先按 game-debugging.md「选择设备」自动确定要测的端（PC／互通）和设备（`client_launch.py select`，不需要用户确认），再委派。只对审查收敛后的最终版本做一次，避免每轮修改后都重新进游戏；成本很低的单元测试可以每轮都跑。自检发现业务缺陷时回到编码，修复后按本文件重新判断是否需要审查。
- 交付时先做提交前自检，再附上提交说明，见 `svn-commit.md`。

## 1. 判断是否需要审查

**跳过**：`engineering-principles.md`「编码前先设计」中可由主线程直接处理的小改动，例如改文案、调坐标、补一个明显的空值判断。

**需要审查**（满足任一条）：
- 涉及模块职责、公共接口、跨模块行为，或有明显的方案取舍；
- 改动虽小但风险高：
  - 网络协议或存档数据；
  - PC 与互通两端都会走到的公共逻辑；
  - 战斗、经济等出错代价大的系统；
  - 被大量调用的底层函数。

无论是否审查，都在交付总结里写明判断结果，例如“改动局部且无高风险项，未做审查”。

## 2. 委派与审查信息

审查者是 Codex，委派方式见 `cli.md`：Claude 主会话用 `codex_cli.py` 的 review 任务，第 2 轮起加 `--resume` 沿用同一个会话；Codex 主会话用 `reviewer` 子代理。任务说明里提供以下信息；文件类信息给路径，让审查者自己读取，以节省主线程上下文：

| 信息 | 内容 |
| --- | --- |
| 项目规范 | 项目根目录 `AGENTS.md` 的路径（团队规范，受管区段之外的部分） |
| 编码准则 | 本 skill 的 `engineering-principles.md` 路径 |
| 需求 | 相关 spec 路径、追踪工单的 `description_path` 或 popo 工单内容；都没有时，由主线程把用户提出的需求整理成要点。迭代已有功能时，原需求给原 spec 路径，另外单独写明「本轮新增需求」 |
| 改动范围 | 修改、新增的文件列表，让审查者自己运行只读的 `svn diff <文件>`；新增文件直接读取全文。只审 review 之后的增量时，给 `changed_since_review` 中的文件（见 `svn-commit.md`「提交前自检」） |
| 已做的验证 | 已经跑过的测试和结果；没有就写“尚未验证” |
| 前几轮记录 | 第 2 轮起：前几轮的意见及处理结果（采纳或拒绝，以及理由）；要求重点检查修复是否正确、是否引入新问题，仍认为被拒绝的意见成立时说明理由 |

**不要提供**：主线程对实现思路的解释、对代码质量的自我评价，以及“我认为没问题”之类的结论。审查者只需要知道要实现什么、实际改了什么，以免被先入为主的说法带偏。

**续接**：第 2、3 轮沿用同一个审查会话，任务说明只写本轮新增的信息：本轮的改动范围、已做的验证和前几轮记录。

## 3. 审查任务说明（模板）

```text
你是代码审查者。只读：不修改任何文件，不得派生、调用或请求新的子代理。

项目根目录：<路径>
请先阅读：
- 项目规范：<AGENTS.md 路径>
- 编码准则：<engineering-principles.md 路径>
- 需求：<spec／工单路径，或需求要点>
改动文件：<列表>（用只读 svn diff 查看修改；新增文件直接读全文）
已做的验证：<…>
<第 2 轮起> 前几轮意见及处理：<…>。重点检查修复是否正确、是否引入新问题；被拒绝的意见如果你仍然认为成立，说明理由。

可以只读查阅仓库中的调用方和相关模块。请检查：
1. 需求中的每一点是否都已实现，有无遗漏或理解偏差；
2. 正确性：边界条件、异常处理、PC／互通差异、资源与状态的释放；
3. 是否符合项目规范和编码准则（复杂度、接口、命名、注释）；
4. 实现是否符合 spec 中确认的方案：模块职责、接口和调用关系有没有偏离；有偏离时说明是否合理。

按以下格式逐条输出，没有问题就明确写“没有必须修改的问题”：
- [必须修改 | 建议修改 | 疑问] 文件:行号 —— 问题；依据；建议的改法

级别：“必须修改”只用于现实中会触发、且影响实际行为的问题；概率极低的边界情况列为“建议修改”，并写明触发条件。
```

## 4. 处理意见

- 主线程逐条判断“采纳”或“拒绝”，记录理由供后续审查。需求明确、修法确定且在授权范围内的问题，自行修复和验证，不打扰用户。
- 只有真正重要、需要人判断的事项才交给用户：需求歧义、重大取舍、兼容性或重要副作用、超出授权范围，以及无法消除的审查分歧；不按问题类别或严重程度一概上交。
- 采纳的意见修改后，再跑一次低成本的检查（语法、单元测试）。

## 5. 收敛条件

- **通过**：某一轮没有“必须修改”的意见。通过后运行 `precommit.py --mark-reviewed` 记录 review 指纹（用法见 `svn-commit.md`「提交前自检」），之后再改动的部分会在自检中列为 `changed_since_review`。
- **进入下一轮**：只有本轮的修改涉及逻辑时才进入下一轮；只改了注释、命名、格式等表面问题，不再审查。
- **分歧**：再次提出已被拒绝的意见时，先依据需求和代码核实；仍无法消除的分歧交用户裁决。
- **上限 3 轮**：第 3 轮后仍有“必须修改”的意见时，停止循环，不要继续修改，把未解决的问题和双方理由交给用户决定。

## 6. 交付时汇总

审查通过后进入真机自检。交付时简述是否审查及原因、真机自检结果，只展开待决策事项、未解决风险与验证限制；不逐轮汇报或罗列内部修复，已修复问题仅在影响理解最终行为时简述。全部完成后，按 `svn-commit.md` 附上提交说明。

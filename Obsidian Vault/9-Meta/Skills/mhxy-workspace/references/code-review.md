# 编码后审查循环

代码修改完成、交付之前读取本文件。本文件只讲交付前由子代理做的审查；用户要求提 CR、把已提交的改动上传到 reviewboard 时，见 `cr-diff.md`。

整体顺序：

```text
编码 → 静态审查循环（本文件，直到收敛） → 运行时验证 → 交付总结 + 提交说明
```

- 运行时验证（测试、游戏内自测，见 `game-debugging.md`）只对审查收敛后的最终版本做一次，避免每轮修改后都重新进游戏。成本很低的单元测试可以每轮都跑。
- 交付时先做提交前自检，再附上提交说明，见 `svn-commit.md`。

## 1. 判断是否需要审查

**跳过**：目标明确、影响局部、方案直接的小改动，例如改文案、调坐标、补一个明显的空值判断。判断标准与 `engineering-principles.md`「编码前先设计」一致，不能只看代码行数。

**需要审查**（满足任一条）：
- 涉及模块职责、公共接口、跨模块行为，或有明显的方案取舍；
- 改动虽小但风险高：
  - 网络协议或存档数据；
  - PC 与互通两端都会走到的公共逻辑；
  - 战斗、经济等出错代价大的系统；
  - 被大量调用的底层函数。

无论是否审查，都在交付总结里写明判断结果，例如“改动局部且无高风险项，未做审查”。

## 2. 准备审查信息

按 `engineering-principles.md`「独立子代理」启动审查子代理，每一轮都用**全新的子代理**。任务说明里提供以下信息；文件类信息给路径，让子代理自己读取，以节省主线程上下文：

| 信息 | 内容 |
| --- | --- |
| 项目规范 | 项目根目录 `AGENTS.md` 的路径（团队规范，受管区段之外的部分） |
| 编码准则 | 本 skill 的 `engineering-principles.md` 路径 |
| 需求 | 相关 spec 路径、追踪工单的 `description_path` 或 popo 工单内容；都没有时，由主线程把用户提出的需求整理成要点 |
| 改动范围 | 修改、新增的文件列表，让子代理自己运行只读的 `svn diff <文件>`；新增文件直接读取全文 |
| 已做的验证 | 已经跑过的测试和结果；没有就写“尚未验证” |
| 前几轮记录 | 第 2 轮起：前几轮的意见及处理结果（采纳或拒绝，以及理由） |

**不要提供**：主线程对实现思路的解释、对代码质量的自我评价，以及“我认为没问题”之类的结论。审查者只需要知道要实现什么、实际改了什么，以免被先入为主的说法带偏。

## 3. 审查任务说明（模板）

```text
你是代码审查者。只读：不修改任何文件，不得派生、调用或请求新的子代理。结果开头先报告你系统提示中的模型 ID。

项目根目录：<路径>
请先阅读：
- 项目规范：<AGENTS.md 路径>
- 编码准则：<engineering-principles.md 路径>
- 需求：<spec／工单路径，或需求要点>
改动文件：<列表>（用只读 svn diff 查看修改；新增文件直接读全文）
已做的验证：<…>
<第 2 轮起> 前几轮意见及处理：<…>。重点检查修复是否正确、是否引入新问题；被拒绝的意见如果你仍然认为成立，说明理由。

可以只读查阅仓库中的调用方和相关模块。请检查：
1. 需求中的每一点是否都已实现，有无遗漏或理解偏差；
2. 正确性：边界条件、异常处理、PC／互通差异、资源与状态的释放；
3. 是否符合项目规范和编码准则（复杂度、接口、命名、注释）。

按以下格式逐条输出，没有问题就明确写“没有必须修改的问题”：
- [必须修改 | 建议修改 | 疑问] 文件:行号 —— 问题；依据；建议的改法
```

## 4. 处理意见

- 主线程逐条判断“采纳”或“拒绝”，不盲从。拒绝时写明理由（例如与需求冲突、审查者缺少某项上下文、风险可接受）。
- 采纳的意见修改后，再跑一次低成本的检查（语法、单元测试）。
- 子代理报告的模型 ID 与主线程不一致，或没有报告时，按 `engineering-principles.md`「独立子代理」处理，该轮结果不能直接采用。

## 5. 收敛条件

- **结束**：某一轮没有“必须修改”的意见。
- **进入下一轮**：只有本轮的修改涉及逻辑时才进入下一轮；只改了注释、命名、格式等表面问题，不再审查。
- **分歧**：新一轮审查者再次提出已被拒绝的意见时，说明分歧值得用户裁决，在交付总结中列出。
- **上限 3 轮**：第 3 轮后仍有“必须修改”的意见时，停止循环，不要继续修改，把未解决的问题和双方理由交给用户决定。

## 6. 交付时汇总

审查过程不逐轮汇报，交付时一并说明：
- 是否做了审查及原因；
- 共几轮，每轮的主要意见；
- 采纳了哪些、拒绝了哪些以及理由；
- 未解决的分歧（如果有）；
- 然后进入运行时验证；全部完成后，按 `svn-commit.md` 附上提交说明。

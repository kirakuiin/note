# 客户端覆盖率

用户明确要求覆盖率的创建、设置、跑测、补测、查询、提交或删除时读取本文件。

- 只处理当前工作区对应 SVN 分支的**已提交**代码，不处理未提交的修改和 Sunshine 设置。确认未提交改动能否跑通是另一项能力，见 `exec-check.md`，两者互不替代。
- 不要因为开发完成就自动跑覆盖率。
- 客户端操作先读 `game-debugging.md`，沿用其中的设备、调用方式、结果检查和 Mock 恢复规则。

## 任务身份

- **分支和 diff**：从只读 SVN 信息确定当前分支和目标提交的 diff。不需要核对工作副本、业务文件、客户端或网站记录的 SVN 版本号，版本号缺失或不一致也不影响跑测。没有依据不要 reload。
- **分支格式**：脚本的 `--branch` 是仓库相对路径，即 context 的 `branch.path`（如 `branchs/2026_dev/xxx`、`trunk`），不是 `branch.name`。查询和登记脚本省略 `--branch` 时自动从 svn 推断，优先省略。
- **结果对应的提交**：网站结果只针对任务当前的提交版本（查询输出的 `revision`）。之后有新提交时，旧的 100% 不包含新改动，需要 `set` 后重跑。
- **redmine_id**：先看追踪工单（context 输出或 `tracking.json`）。只有一个追踪工单，或用户本轮已选定时直接使用；有多个而目标不明确时先问；没有工单信息才向用户索要。
- **task_name**：由用户确认，不要自己生成。
- **coder_name**：取自配置（见 workspace-management.md「配置」）；配置和邮箱都没有时再问。
- task_name 和 redmine_id 属于单个覆盖率任务，不写入配置，也不在初始化时询问。
- **复用登记**：`coverage_tasks` 中同工单、同分支的登记，在核实远端任务存在后可以复用；不能套用其他工单或分支的登记。
- **Mock 的能力边界**：网站按工单、程序名和提交 diff 匹配执行行。Mock 可以切换 PC／互通的 Python 条件、构造边界输入；但依赖专有引擎、模块或真实平台行为的路径，不能假定切换标志就能验证，要说明实际覆盖的范围。

## 跑测流程

1. **创建或设置任务**：确认客户端已启动，按调试规范初始化设备，再检查任务是否存在。
   - 不存在：执行 `$$scover_create <redmine_id> <task_name> <coder_name>`，成功后立即开始采集，再查询覆盖率。
   - 已存在且用户明确要求跑测：执行 `$$scover_set <task_name>`。
   - “指令已执行”不等于成功，创建和上传都要用客户端的成功日志或网站记录核实。超时先查状态，不要重复创建。
2. **登记身份**：远端任务创建成功或核实存在后，由主会话用下方的 `coverage-task` 命令登记。跑测委派给测试执行者时，执行者不能写 `tracking.json`：任务说明要求它在结果中返回 task_name、redmine_id 和远端核实依据（成功日志或网站记录），主会话核对后再登记。`created: true` 只表示任务存在，不表示仍在采集或已经通过。换分支后要重新核对，不能沿用旧任务。
3. **编写并执行 Mock**：根据目标 diff、网站追踪文件和未覆盖行编写 Mock，执行**原始**被测逻辑并断言关键行为。可以复用已有测试的断言，但必须调用客户端的原始模块。
   - 禁止：用离线重建或提取出来的业务函数冒充覆盖；替换掉被测逻辑；伪造执行行；修改统计范围来达标。
   - 每轮执行后恢复运行时替换；Mock 文件保留，方便补测。
   - 每轮执行前后按 `game-debugging.md`「收集客户端报错」收集报错，记录与被测逻辑有关的报错。
4. **上传**：执行 `$$scover_finish <task_name>`。提交不需要先解绑，多次提交由服务自动累计合并。补测时继续用同一任务，必要时用 status 核实采集状态后再 set。不要调用本地 `clear_cov` 清掉已有的采集数据。
5. **查询并补测**：必须通过下方的查询脚本读取网站结果，核对任务、分支和提交的新鲜度；根据未覆盖行调整 Mock，再执行、提交、查询。网站的行覆盖率不能单独证明所有分支的行为都正确。
6. **判定结果**：只有目标范围真实达到 100%、本轮结果已反映到网站、断言也通过，并且收集到的报错中没有与被测逻辑有关的，才能报告通过。
   - 剩下 `global`、括号这类疑似不可执行的行时，用客户端实际函数的字节码行表核实（包括嵌套的代码对象）。确认后列出文件、行号和证据，并区分“可执行行已全部覆盖”和“网站未达 100%”。不要自动忽略、人工确认或缩小范围。
   - 认证失败、接口不可用，或连续补测没有进展时，停下来报告阻塞。

**统计范围检查**：创建任务后，核对网站基准与当前配置能否形成目标 diff。同分支同版本，或应覆盖 0 行时，先排查基准；不能接受空范围的 100%，也不要自动修改基准。（这里检查的是统计范围，不是本地 SVN 版本。）

**辅助指令**：`$$scover_status <task_name>` 查看任务；`$$scover_show <task_name>` 查看追踪文件；`$$scover_unset <task_name>` 只在需要解绑时使用，不是每次 finish 的必要步骤。以上是指令原文，通过 MCP 调用时以工具的实际参数格式为准。

## 本地文件与登记

**Mock 文件**：放在项目的 `.mhxy-workspace/coverage/<任务目录>/` 下。目录名不能含路径分隔符或 `..`，必要时用任务名的稳定摘要作为目录名。脚本开头简述对应的任务、用例和运行方法，不要保存凭据。保留 Mock 脚本不等于保留运行时的 monkeypatch。

**登记命令**：身份写入 `.mhxy-workspace/tracking.json` 的 `coverage_tasks`，只由主会话通过下面的脚本写入。先预览，再加 `--apply`。参数必须来自已确认的任务；本地登记不能代替远端创建。

```text
python "<skill>/scripts/workspace.py" coverage-task --root "<工作区>" --task-name "<确认的任务名>" --redmine-id "<工单>" --coder-name "<邮箱前缀>"
```

- 按工单号和分支定位：更新这一条登记，保留其他工单的登记。不要求先追踪工单；工作区须已初始化，见 workspace-management.md「sync 做什么」。
- 本地登记丢失（例如清理了个人目录）后重新跑测：先确认 task_name，再查远端是否已存在；不能因为本地没有登记就直接 create。

**删除**
- 用户明确要求删除覆盖率临时文件时，只删对应的 Mock，保留本地登记。删除前核对绝对路径确实位于该项目的 coverage 目录内，遇到符号链接或目录联接就拒绝。
- 清理整个个人目录按 workspace-management.md「清理个人目录」执行，会一并清除登记。
- 以上两种都不会删除远端任务、spec 或业务文件。普通 finish 之后不删除任何文件。

## 网站查询

网站是 `https://mh-mos2-coverage.eros.nie.netease.com`。只通过下面的脚本读取结果，不要用浏览器观察或客户端本地行号代替：

```text
python "<skill>/scripts/coverage_query.py" --root "<工作区>" --task-name "<任务名>" --submitted-after "<本轮finish前记录的带时区ISO时间>"
```

**参数**
- `--branch`：见「分支格式」，一般省略。报 `scope_mismatch` 时，消息里会列出网站记录的分支和传入值，先核对格式，不要据此断定任务不在当前分支。
- `--submitted-after`：首次查询定位缺口时可以省略，但省略后脚本不会返回 passed。提交后按网站的处理进度适度重查，不要为了等结果反复 finish。
- 脚本自动按网站任务的 `cur_ver` 查询；旧的 `--revision` 参数仅为兼容保留，已忽略。不与本地 SVN 或客户端版本比较，但会核对任务、分支和提交记录的身份。
- 脚本只调用网站的 GET 查询接口，不执行 reset、ignore、confirm 等写操作。

**认证**
- 默认用用户级配置中的 OpenID 账密登录。配置方法和无交互终端时的处理见 workspace-management.md「配置」「密码」。登录需要支持 SM4 的 `cryptography`，会话只保存在进程内存中。
- `--auth-file`（或环境变量 `MHXY_COVERAGE_AUTH_FILE`）可以改用已有会话。认证文件是只含 `Cookie`／`Authorization` 请求头的 JSON 对象，由用户在本机自行配置；不要写入配置、工作区、Mock、入口文件或聊天内容，也不要自动提取浏览器登录态。没有认证或认证过期时返回 `auth_required`。
- `--openid-user` 可以指定交互登录的账号；与配置中的账号不同时，不会使用已存的密码。`--coder-name` 可以覆盖配置中的 coder。
- 需要验证码、二次验证，登录失败或协议变化时停止，不要重试密码。

**输出与判定**
- 标准输出是 JSON，包含 `status`、任务／分支／版本、`website_rate`、`required_count`、`executed_count`、`last_submission`、`files`（逐文件的缺失行和忽略行）和 `blockers`。版本字段只用于记录，不作为验收条件。
- 退出码：0 为 passed，2 为 incomplete，3 为阻塞或错误。要解析输出内容，不能凭脚本没报错就判断成功。
- 存在人工调整、空范围，或无法确认本轮提交时，不报告通过。
- 网站上没有时区的提交时间，按其前端逻辑视为 UTC；但传入的 `--submitted-after` 必须带时区。身份不符时返回 `submission_scope_unverified`，不要为了通过而关闭这项检查。
- 结构异常、返回登录页或认证失败，都不能当作空任务或 0%／100%。
- 接口已用已认证的历史任务做过只读查询核验（提交历史用 `task_id` 和 `revision`，分支从任务元数据核对）。这只说明查询可用，不代表执行过客户端跑测或上传。

**最终反馈**包含：任务链接、目标分支、网站百分比、逐行的覆盖数／总数（两者口径可能不同，不要互相推算）、未覆盖行、忽略／确认的影响、收集到的报错及判断，以及 Mock 断言和恢复结果。证据不足时不要宣称真实 100%。

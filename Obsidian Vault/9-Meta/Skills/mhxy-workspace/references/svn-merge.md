# SVN 合并

把一个分支上的修订合到当前工作副本：研发分支合到外放分支或 trunk、把主干同步到研发分支、处理合并冲突，都走这一个流程，用同一个脚本 `scripts/svn_merge.py`。分支类型只决定提交说明怎么写，不改变流程。

不要手写 `svn merge`，不要用拷贝文件或打补丁代替合并，也不要再用独立的 `svn-merge` 技能。

## 两条硬性保证

1. **一定记录 `svn:mergeinfo`**。合并只用 SVN 原生的 merge。源地址不管写成什么协议，脚本都统一到目标工作副本所在仓库的地址上；不是同一个仓库直接拒绝。合并后、提交后各核对一次合并信息，缺了就不能提交。遇到“svn:mergeinfo 没有记录”时只能 `abort` 后查原因，不要手工补属性，不要换别的办法把内容弄过去。
2. **提交里只有这次合并的内容**。工作副本里单纯被修改的其他文件（最常见的是入口文件 `AGENTS.md` 的受管区段）合并前自动暂存，结束后放回，变更列表也会恢复。不要为了合并手工还原它们。

## 流程

1. **定源和修订**。源可以写 URL、另一个工作副本的路径，或仓库内的相对路径（`trunk`、`branchs/2026_dev/<分支名>`）。修订有两种给法：
   - 用户给了修订号、工单号或描述：用只读的 `svn log` 在源分支上找到对应修订，用 `--revs` 列出。
   - 用户只说“把那个分支合过来”或“同步主干”：用 `--eligible`，合并源分支上所有还没合过的修订；可加 `--min-rev`、`--max-rev`、`--skip-revs`。
2. **计划**（只读，不动工作副本）：

   ```text
   python "<skill>/scripts/svn_merge.py" plan --root "<目标工作区>" --source "<源>" --revs <修订…>
   ```

   输出里有：统一后的源地址、目标分支类型、每个修订的作者和日志首行及改动的文件、已经合过会跳过的修订、提交说明的格式（`message.format`）、会被暂存的本地修改、挡路的内容（`blockers`）和提醒（`warnings`）。
   - `blockers` 不为空（新增、删除、冲突、缺失、锁定、属性修改）：先让用户处理，不要自己还原。
   - `status` 为 `nothing_to_merge`：都合过了，告诉用户，不用继续。
   - 外放分支上一次合并涉及多个工单时会有提醒，按工单分开合并、分开提交。
3. **写提交说明**。格式和直接提交完全一样，见 [svn-commit.md](svn-commit.md)「格式」「工单号」「工单名」：外放分支和 trunk 是 `finish #工单号 工单名：改动描述`，研发分支是 `#工单号 工单名：改动描述`。不用在说明里写“merge from 哪个分支哪些版本”：来源由 `svn:mergeinfo` 记录，那才是可靠的依据。例如：

   ```text
   finish #864519 特效迭代-金刚护法（仅测试效率，不改效果）：加入测效率开关
   ```

   工单号按 svn-commit.md 的顺序确定（合到外放分支时是那张放出单，不是研发分支上的开发单）；计划里的 `tracked_tickets` 和 `source_tickets` 只是参考。
4. **向用户确认一次**：源和目标、要合的修订、完整的提交说明、会被暂存的本地修改、合完是直接提交还是先停下。用户明确说了可以提交才带 `--commit`。
5. **执行**。说明写进 UTF-8 文本文件：

   ```text
   python "<skill>/scripts/svn_merge.py" run --root "<目标工作区>" --source "<源>" --revs <修订…> --message-file "<说明文件>" [--commit]
   ```

   脚本依次做：暂存本地修改、更新工作副本、合并、自动处理能安全处理的冲突、校验、提交或停下。按输出的 `status` 处理：

   | status | 含义 | 接下来 |
   | --- | --- | --- |
   | `committed` | 已提交，`revision` 是新版本号 | `verified` 为 false 时把 `errors` 告诉用户，先核对仓库，不要重复提交 |
   | `merged` | 合好了，还没提交 | 用户看过后运行 `commit`；不要了运行 `abort`。带了 `--commit` 却停在这里，是因为 `review` 里列出了和源修订对不上的改动，把它讲给用户听 |
   | `conflict` | 有冲突需要处理 | 按下节处理，然后运行 `continue` |
   | `blocked` | 校验没过，`problems` 里是原因 | 按原因处理后运行 `continue`；原因是没有记录 `svn:mergeinfo` 时只能 `abort` |
   | `commit_failed` | 提交被拒或结果不明 | 看 `error`；结果不明时先用 `svn log` 核对有没有提交上去，再决定是否 `commit` 重试 |

6. **汇报**：源和目标、合了哪些修订、提交后的版本号（或停在哪一步）、自动处理和手工处理的冲突各是哪些以及怎么处理的、`local_changes` 里的放回结果、`review` 里的差异。

其他命令：`status` 看有没有没结束的合并（任务开始前、会话中断后先看一眼）；`commit [--message-file …]` 提交已经合好的结果；`abort` 撤销没提交的合并并恢复本地修改。一次只能有一个进行中的合并。

## 冲突处理

脚本先自动处理两类不需要判断的冲突，结果列在 `auto_resolved` 里，汇报时照实说明：

- **编码不同造成的文本冲突**：源和目标文件编码不同（例如一边是 GBK、一边已转成 UTF-8），三方内容都能解码，按文字看两边的改动并不重叠。脚本合好后统一存成 UTF-8，Python 文件头部的编码声明也改成 `utf-8`。
- **只有 `svn:externals` 属性冲突**：保留目标分支原来的外链，外链不跟着合并走。

其余冲突停在 `conflict`，`conflicts` 里每一项给出路径、类型，以及三份参考内容的文件路径：目标分支原内容、共同基准、源分支内容。逐个处理：

1. 三份内容都读。先分清哪些是源修订要带过来的改动，哪些是目标分支自己已有的改动，哪些只是编码或换行的差异。
2. **两边的有效改动都要保留**。不能为了合进源的改动把目标分支已有的修复退回去，也不能为了保住目标而丢掉源修订的意图。源修订依赖目标分支没有的东西（函数、字段、资源）时，说明这次合并缺了前置修订，停下来告诉用户，不要自己补写。
3. 不要整文件采用某一边（`theirs-full`、`mine-full`），除非用户明确说这个文件就用哪一边。
4. 保持文件原来的编码和换行，不要顺手统一；非 UTF-8 的文件按原编码读写。
5. 生成的文件（协议头、导表结果等）不要手工合：只合它的来源文件，再按该项目的做法重新生成。
6. 改好后 `svn resolve --accept working <文件>`。树冲突（一边删除或改名、另一边修改）没有可靠的通用做法，把两边各做了什么讲清楚，由用户决定。
7. 全部处理完运行 `continue`。脚本会再检查：还有没有冲突、冲突标记和临时文件，处理过冲突的 Python 文件语法是否还对，有没有出现乱码，合并信息是否齐全。不过就按提示再改，再 `continue`。
8. 拿不准某一处该怎么合时，不要猜：保持冲突状态，把这一处两边的内容和你的判断发给用户。合并可以停在这里等，状态不会丢。

每个手工处理的冲突，在汇报里写明文件、源想做什么、目标原来是什么、最后怎么合的。

## 本地修改的放回

`local_changes` 说明合并前暂存的文件怎么样了：

- `restored`：原样放回了。
- `remerged`：这次合并或更新也改了这个文件，本地修改已经自动合并到新内容上（两边改的不是同一处）。
- `pending`：这个文件这次合并也改了，要等合并提交之后才放回，免得本地修改被一起提交；`commit` 结束时会放回。
- `kept`：本地修改和合并改到了同一处，没有自动合并，也没有覆盖。工作副本里是合并后的内容，本地版本在 `backup` 给出的路径里。入口文件遇到这种情况时运行 `workspace.py sync --root . --apply` 重写受管区段；其他文件对照备份把本地修改合回去，并在汇报里说明。

停在 `conflict` 期间本地修改都还没放回，入口文件暂时没有受管区段，`context` 会提示这一点；处理完冲突、`continue` 或 `abort` 之后就恢复了，不要因此重新初始化工作区。

## 授权

- `plan`、`status` 是只读的，随时可以运行。
- `run`（不带 `--commit`）、`continue`、`abort` 会改工作副本，要用户确认过合并计划。
- `--commit` 和 `commit` 会提交到仓库，要用户明确批准提交：要么事先说了“合完就提交”之类的话，要么看过合并结果后同意。
- 无人值守时合并类工单的处理见 [unattended.md](unattended.md)：不带 `--commit`，合完停在 `merged` 就结束。
- 后台服务拉起的会话如果没有得到提交的批准，会带着环境变量 `MHXY_NO_COMMIT=1`。这时脚本即使收到 `--commit` 或 `commit` 也只停在 `merged`，并在 `reason` 里说明；照实报告给用户，不要想办法绕过。

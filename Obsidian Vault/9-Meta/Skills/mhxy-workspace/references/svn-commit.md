# SVN 提交

交付时生成提交说明和待提交文件清单。用户明确确认后，agent 按「提交」用本地 Python 脚本代为提交，不手写 shell `svn commit` 命令。

## 何时提供

- **交付时主动附上**：任务的代码修改完成、向用户交付时，先做「提交前自检」，再在总结末尾附上「交给用户的内容」。改动执行检查在此之前的真机自检中完成（见 [code-review.md](code-review.md)），交付时不再询问。同一任务分多轮修改时，只在用户确认改完或任务完成的那次交付附上，不要每改一处附一次。
- **不附**：只读调查、纯文档修改，或本次没有改动工作副本时。
- **用户要求时**：用户要求撰写或检查提交说明时，随时提供。
- **工单号不明确时**：交付时直接问用户对应哪个工单，拿到后再给出完整说明；不要用占位符代替。

## 格式

格式由分支类型决定，分支类型以 context 输出的 `branch.kind` 为准（按 SVN URL 判定，规则在 `workspace.py` 的 `classify_branch`；周期分支一定带日期，即 `_ship` 下的 `<类型>_YYYY_MM_DD`）：

| 分支类型 | 格式 |
| --- | --- |
| trunk、周期分支（外放分支） | `finish #工单号 工单名：改动描述` |
| 研发分支 | `#工单号 工单名：改动描述` |

- 普通工单提交必须同时包含工单号、工单原名和实际改动描述；跟测 bug 使用下方专门格式。
- 外放分支一律用 `finish`，不用 `refs`。
- `branch` 为 null 时，先问用户是哪类分支。

## 工单号

按以下顺序确定：
1. 本上下文处理的 popo 工单 → 用下面的跟测格式。
2. 用户本轮指定的工单。
3. 唯一的追踪工单（context 的 `tracked_tasks`）。有多个而本轮没指明时，先问用户。

找不到工单信息时必须问用户，不要编造，也不要写 `#0`。

## 工单名

- 使用与所选工单号对应的原名，不自行缩写或改写；工单名与后面的改动描述是两个独立字段。
- 优先使用用户本轮明确提供的工单原名；否则读取匹配工单号的 `tracked_tasks.title` 或工单记录标题（`description_path`），不要从改动内容猜测工单名。
- 已有记录缺少名称时，先补读对应工单资料；仍无法确定时再询问用户，不直接省略工单名。

普通工单示例：`#828911 特效迭代：更新超级兽诀紫色特效并调整己方定位`。

## 跟测 bug（popo 工单）

如果本上下文用 `popo-issue-fetch` 处理过某个 popo 工单，默认使用跟测格式：

```text
#<策划单号> #跟测 bugfix %<popo 工单号> #<提单人> 描述
```

外放分支在最前面加 `finish `。各字段取自 `popo.py show` 的输出：
- **策划单号**：「所属任务」中任务名的 `#` 前缀，例如 `#816033 全屏战斗界面` 里的 `816033`。不是 popo 工单号。
- **popo 工单号**：标题行 `# #291271 ...` 中的数字。
- **提单人**：「提单」行括号前的姓名，例如 `W王海峰`。用平台显示的姓名，不用账号。

示例：`#816033 #跟测 bugfix %291271 #W王海峰 调整速度条法宝图标尺寸`

所属任务为“无”或拿不到策划单号时，先问用户。一次改动涉及多个 popo 工单时，先问用户是拆成多次提交，还是写在同一条里。

## 描述

- 用只读的 `svn diff` 查看本次实际改动，一句话写清楚做了什么。工单名保留原文，改动描述单独撰写，不用重复工单标题代替实际改动说明。
- 需要补充时，用空格接在后面，例如“review 修复”“顺带处理以前的报错，和本次功能无关”。

## [NO MERGE] 与导表数据

`[NO MERGE]` 加在说明末尾，表示这次提交不合并到其他目录。适用于：
- **外链更新**（`svn:externals` 属性变化）：不要覆盖其他目录的外链设置。
- **导表数据**：每个目录都会各自重新导出。

**导表数据（`data/` 下的导出结果）默认不提交**：从待提交清单里排除，并提醒用户自行处理。用户明确要提交导表数据时，提醒加 `[NO MERGE]`，并和代码分开提交。

外链更新和代码改动混在一起时，建议拆成两次提交，让代码能正常合并。

## 提交前自检

交付前先运行（只读，约几秒）：

```text
python "<skill>/scripts/precommit.py" --root "<项目根目录>"
```

脚本输出 JSON，退出码 0 表示没有阻断问题，2 表示有阻断问题，1 表示自检本身失败（例如 svn 不可用、不是工作副本）。各字段含义：

| 字段 | 内容 | 怎么处理 |
| --- | --- | --- |
| `commit` | 待提交的修改、新增、删除和属性修改 | 核对是否都属于本次任务；混入的无关改动要指出 |
| `unversioned` | 未纳入版本控制的文件或目录 | 判断哪些是本次新建、需要先加入版本控制的，列进待提交清单并标明；新目录（及其中的文件）交给用户自己提交 |
| `excluded_local_only` | 不应提交的本地文件：`.mhxy-workspace/`、`.claude/`、`AGENTS.md`、`CLAUDE.md` | 不提交。受版本控制的入口文件已在 `ignore-on-commit` 变更列表中（见 workspace-management.md），提交对话框默认不勾选 |
| `ignore_on_commit` | 其他在 `ignore-on-commit` 变更列表中的改动 | 默认不提交，不列进待提交清单；用户要提交时由用户先移出该列表 |
| `excluded_data` | 导表数据（`data/`） | 默认不提交，见上一节 |
| `property_changes` | 属性改动，常见于外链更新 | 建议单独提交并加 `[NO MERGE]`；目录上的属性（`svn:externals` 通常在目录上）交给用户自己提交 |
| `blocking` | 冲突、缺失文件、编码错误、语法错误 | **必须先解决**，否则不能交付 |
| `warnings` | 混用换行符、新增的 `print`／调试断点／写死的设备 ID、Mock／追踪器残留（`sys.settrace`、`unittest.mock`、`lambda *a, **k` 替换模块属性、保存原函数的 `_orig_*` 等）等 | 逐条判断：属于正常代码就说明理由，否则修改 |
| `review_mark` | 最近一次 review 通过时记录指纹的时间；null 表示没有记录 | 只是参考，不阻断 |
| `changed_since_review` | review 记录之后内容、状态或属性值变化，或新出现改动的文件和目录；已没有本地改动的（如已提交、已还原）不列出；完整列出，不截断 | 不为空时，只把这些文件交给 Codex 做增量 review（审查信息见 [code-review.md](code-review.md)「委派与审查信息」），通过后重新记录。粒度是文件：没有保存 review 时的内容，增量 review 审这些文件当前的整份 diff |

- **编码和语法**：项目有 `tools/check_py_source_encoding.py` 时，脚本用它检查（`--expect-utf8 --compile`）；没有时（例如 release2）用内置检查：UTF-8 字节、utf-8 编码声明、语法编译。客户端是 Python 3.11，与本机一致，语法检查结果可信。
- **范围**：只检查主工作副本，不含外链。编码检查和调试残留扫描的范围相同：待提交的修改／新增源码，以及未纳管的源码（含未纳管目录中的）。
- **review 指纹**：Codex review 通过时运行 `python "<skill>/scripts/precommit.py" --root "<项目根目录>" --mark-reviewed`，记录各待提交文件（含新增和未纳管的）的内容哈希和 svn 状态，以及属性修改的文件和目录的属性值哈希到 `.mhxy-workspace/review-mark.json`，覆盖旧记录。要求工作区已初始化。`svn_commit.py` 提交成功后从记录中删掉已提交的文件；删除失败只在输出的 `warnings` 中提醒，不影响提交结果。
- 自检发现的问题修改后，重新运行一次，直到没有阻断问题。

## 交给用户的内容

1. **提交说明**：一行，可以直接复制。
2. **待提交文件**：根据自检结果列出 `commit` 中的文件，并标出需要加入版本控制的新文件、已排除的本地文件、`ignore-on-commit` 中的改动和导表数据。新目录、目录属性修改和目录删除单独列出，说明需由用户自己提交（见「提交」）。
3. **自检结果**：阻断问题已全部解决；对保留下来的警告逐条说明理由。
4. **询问是否代为提交**：问用户要不要由 agent 按以上说明和清单提交，还是自己提交。

## 提交

只有用户针对**本次**的提交说明和待提交文件明确同意（例如“提交吧”）后才执行。交付、自检通过或以前的同意都不算确认；确认之后说明或清单又有变化（重新修改代码、增减文件、改说明），要重新确认。

所有分支都用本技能的 `scripts/svn_commit.py`，由 Python 直接调用本机 `svn.exe`。脚本按实际 SVN URL 判定分支类型，规则与「格式」中的 `branch.kind` 相同（`workspace.py` 的 `classify_branch`），只接受 trunk、周期分支和 `branchs/<年份>_dev/` 下的研发分支。

仅处理工作副本根目录内明确列出的文件。支持修改、新增、删除和文件属性修改；拒绝跨工作副本或已切换的文件、本地辅助文件、导表数据和 `ignore-on-commit` 变更列表中的文件。**目录相关的改动都交给用户自己提交**：新目录（包括其中的文件，即上级目录尚未提交或未纳管时）、目录属性修改（如 `svn:externals`）和目录删除，脚本会在预览时拒绝并说明原因。本脚本不执行更新、合并、relocate、冲突处理或自动重试。

1. 把已确认的**完整说明**写到临时 UTF-8 文本文件。脚本按分支类型校验首行是否符合「格式」（trunk、周期分支带 `finish`，研发分支不带），不会拼接或改写说明；不符时修改说明并重新确认，不要为了通过校验改写已确认的内容。
2. **只读预览**（以下文件名仅作例子，以本次确认的清单为准）：

```text
python "<skill>/scripts/svn_commit.py" --root "<项目根目录>" --message-file "<UTF-8说明文件>" --path "gameplay/ui_msg/example.py" --path "spec/bugfix/example.md"
```

核对返回的 `branch.url`、`message`、`entries` 和 `changed_count`。必须与确认的分支、说明、文件清单及数量一致；`will_add` 只包含确认清单中的新文件，预览不会添加它们。

3. **提交**：使用完全相同的参数，仅追加 `--apply`。脚本只添加清单内的新文件，再以 UTF-8 消息文件提交，随后读取**指定的新修订**，核验完整日志与实际变更路径集合。
4. `committed: true` 且 `verified: true` 时报告新版本号；两个字段分别表示“已提交”和“日志与路径核验通过”，不能混用。

失败处理（任何失败都报告 `error` 原文，不自动 update、resolve、cleanup 或重试）：
- `committed: false`：没有提交。包括预览阶段的拒绝，以及 SVN 在提交前或钩子阶段拒绝（版本过旧、冲突、非法目标、pre-commit 钩子拒绝等，判定的错误码见脚本 `REJECTED_CODES`）。如果新文件已添加，保留并说明其本地状态。
- `committed: null`：提交结果不明（超时、连接中断、未知错误）。先只读查询仓库日志确认结果，不重复提交；超时时提示用户工作副本可能需要 cleanup。
- `committed: true` 但 `verified: false`：已提交，报告版本号与核验错误，先核对仓库日志，不重复提交。

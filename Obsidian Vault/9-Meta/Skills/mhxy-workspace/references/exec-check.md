# 改动执行检查

在客户端里把本次**未提交改动**的每一行真实执行一遍，确认一般情况下运行到这些代码时不会报错。

这是开发流程第 5 步真机自检的默认方法，不需要用户另外要求：主线程把它写进委派的 test 任务（见 `cli.md`），由受委派的测试执行者按本文件执行并向主线程汇报。用户也可以单独要求做这项检查，同样委派执行。

## 和网站覆盖率的区别

| | 改动执行检查 | 网站覆盖率（`coverage.md`） |
| --- | --- | --- |
| 对象 | 工作副本中未提交的改动 | 已提交到 SVN 的代码 |
| 目的 | 改动的代码跑得通、不报错 | 按工单统计覆盖，结果用于提测 |
| 结果 | 只在本次对话中汇报，不上传、不登记 | 上传网站，登记到 `tracking.json` |

两者互不替代。向用户描述时说“执行检查”，不要称为“覆盖率”。

## 1. 确定目标行

```text
python -X utf8 "<skill>/scripts/exec-check/diff_lines.py" --root "<项目根目录>" [相对路径 ...]
```

- 用 Python 3.11 运行，与客户端一致：目标行取自解释器的行号表，版本不同时行号可能对不上客户端的 `f_lineno`。版本不符时输出的 `warnings` 会说明，换 3.11 重新运行。
- 不给路径时，取 svn status 中修改、新增、替换或未纳入版本控制的 `.py` 文件（未纳入版本控制的文件整个算作改动），排除个人目录、入口文件和导表数据。
- 输出 `files`（文件 → 目标行号）、`total`、`skipped`（无法解析的文件及原因）和 `warnings`。
  - 行号按 Python 的换行规则计数：单独的 CR 也算一行，与客户端的 `f_lineno` 一致，可能和 `svn diff` 显示的行号不同。
  - 只统计函数体内会执行的行。注释、空行、docstring、模块级和类体语句不计入：它们在导入或热更时就执行了，不由用例触发。
- `total` 为 0 时，汇报没有可检查的行，结束。`skipped` 不为空时先报告；有语法错误时返回主线程先修好。

## 2. 准备客户端

- 设备选择、`init_client`、调用方式和结果检查，都按 `game-debugging.md` 执行。
- 确认客户端加载的是当前工作副本的代码：目标模块的 `__file__` 指向工作副本，且改动已经生效（例如被改函数的 `__code__.co_names` 里有新调用的名字）。不一致时返回 blocked，由主线程请用户热更或重启客户端，不要擅自 reload。
- PC 客户端不加载 `mobile/` 目录下的文件，互通客户端不加载 `win32/` 目录下的文件。当前客户端加载不到的目标文件，单独列为“未检查”，不要传给追踪器。
- 用例需要战斗、特定门派等前置状态时，只执行任务说明中已授权的 GM 指令。有破坏性副作用（例如转门派会清空天赋）而任务未预先授权的指令，不要执行，返回 blocked 并写明要用的指令及其副作用，由主线程向用户确认。

## 3. 编写用例

- 每段改动至少有一个用例覆盖。用例直接调用客户端里的原始函数，可以构造输入或临时修改前置数据，但不能替换被测逻辑本身。
- 每个用例加简单的断言，检查改动想要的结果。
- 迭代已有功能时，另加几个回归用例，覆盖 spec 中列出的原有关键行为，确认本次改动没有破坏它们；用到的 spec 由任务说明提供。
- 用例要符合 `game-debugging.md`「找到并调用工具」中 `execute_code` 的写法：用例函数里需要的模块在函数内部 import，不引用顶层定义的其他名字。
- 用例里临时修改的全局数据、属性，在用例自己的 `finally` 中恢复；临时创建的界面在用例结束后销毁。
- 用例脚本保存在项目的 `.mhxy-workspace/exec-check/<任务名>.py`，开头写明对应的改动、各用例的作用和用法，方便之后复用或补测。

## 4. 执行

报错收集按 `game-debugging.md`「收集客户端报错」执行，行追踪用 `scripts/exec-check/exec_trace.py`。分两次调用 `execute_code`：

1. 代码依次为 `scripts/game-debugging/error_watch.py` 全文、`exec_trace.py` 全文、用例定义，最后一行写 `[error_watch_start(), exec_check_start(TARGETS, CASES)]`。
   - `TARGETS` 是第 1 步输出中当前客户端能加载的 `files`，`CASES` 是 `[(名称, 无参函数)]`。
   - 返回值第一项是收集器的启动结果。第二项是逐个运行用例后的 `results`、`covered`、`missing`，运行完行追踪器就会卸载。
   - 第二项返回 `abort`（已有追踪器，说明调试器或网站覆盖率正在采集）时，不会运行任何用例。要先结束收集，再返回 blocked。
2. 按「收集客户端报错」的结束步骤调用 `error_watch_finish()`，取回检查期间的报错。

用例里直接抛出的异常记在 `results` 中；之后几帧才执行的回调报错，由收集器收到。

行追踪只覆盖用例运行期间的当前线程：在之后几帧的回调、定时器、其他线程中才执行的目标行，即使确实执行了，也总是记为 `missing`。

## 5. 判定与处理

- **通过**：所有用例为 `ok`，`missing` 为空，`error_watch_finish` 没有与改动相关的报错。
- **有行没执行到**：补充用例后重跑。以下情况补充用例也无法消除，列出行号和原因，由主线程判断能否接受，必要时问用户：
  - 确实无法构造前置状态，例如依赖服务端的特殊状态；
  - 目标行只在之后几帧的回调、定时器或其他线程中执行，追踪器看不到（见第 4 步）。可以另用日志或收集器的结果说明它们是否执行、是否报错。
- **有报错**：先判断是检查本身的问题，还是业务代码的问题。
  - 检查本身的问题：例如用例写错、构造的数据不合法。修正后重跑。
  - 业务代码的问题：停止检查，带证据返回主线程，不修改业务源码。主线程回到编码修复（按 `engineering-principles.md` 和 `code-review.md`），修完后对最终版本重新做一次完整检查。
- 与改动无关的报错也要列出来，并说明为什么判断为无关。

## 6. 汇报

向主线程汇报以下内容，由主线程核验后在交付时向用户简述：

- 每个文件已执行的行数和总行数，以及没执行到的行。
- 各用例的结果和断言。
- 用构造的数据代替真实场景的地方。
- 收集到的报错及判断，以及收集不到的报错类型（见「收集客户端报错」）。
- 临时状态的恢复和临时界面的销毁结果。
- 未检查的文件和原因，例如当前客户端加载不到 `mobile/`。

# SVN 合并并入本 skill（svn_merge.py）

日期：2026-11-11　版本：0.3.34–0.3.35（2026-11-11 补记）

当时没有写 spec，本文按 git 备份（`205b9a8`、`72d1df0`）和现有代码补记，作为后续修改的依据。规则正文在 `references/svn-merge.md`，本文只记设计取舍。

## 目标

合并（研发分支合到外放分支或 trunk、把主干同步到研发分支、处理冲突）走一个流程、一个脚本，保证：

1. 一定记录 `svn:mergeinfo`：只用 SVN 原生 merge，源地址统一到目标工作副本所在仓库；合并后、提交后各核对一次，缺了不能提交。
2. 提交里只有这次合并的内容：工作副本里单纯被修改的其他文件（最常见是入口文件的受管区段）合并前暂存，结束后放回，变更列表一并恢复。

## 过程

- **0.3.34**（2026-11-10）：合并交给独立的 `svn-merge` 技能。入口规则加路由行；`workspace-management.md` 加「合并时」，说明入口文件会被那个技能暂存到 `.svn-merge-stash/`，合并结果未提交时要手动 `restore-stash`；`require_initialized` 遇到暂存目录时提示先放回。问题：独立技能的暂存要手工放回，入口规则在合并未提交期间整段缺失，`context` 等命令都报错。
- **0.3.35**（2026-11-11）：改为本 skill 自带 `scripts/svn_merge.py`，不再用独立技能。

## 设计（0.3.35）

- 子命令：`plan`（只读）、`run [--commit]`、`continue`、`commit`、`abort`、`status`，都输出 JSON。状态存在 `.mhxy-workspace/merge/state.json`，同一工作区一次只能有一个进行中的合并。
- 修订：`--revs` 明确列出，或 `--eligible`（可加 `--min-rev`、`--max-rev`、`--skip-revs`）合并源上所有没合过的修订。
- 提交说明格式与直接提交一致（`svn-commit.md`「格式」），不写“merge from”，来源由 mergeinfo 记录；提交走 `svn_commit` 的校验和核验。
- 暂存与放回：`restored`／`remerged`／`pending`（合并也改了，提交后再放回）／`kept`（同一处冲突，本地版本留备份）。只有停在 `conflict` 时入口文件暂时没有受管区段，`require_initialized` 按 `state.json` 提示“合并停在半路”，不要重新初始化。
- 自动处理两类不需判断的冲突：编码不同但改动不重叠的文本冲突（合好后存成 UTF-8 并改编码声明）、只有 `svn:externals` 的属性冲突（保留目标的外链）。其余停在 `conflict`，给出三份参考内容，由 agent 按原则处理后 `continue`；`continue` 再查冲突标记、临时文件、Python 语法、乱码和 mergeinfo。
- `--commit` 时如果 `review` 发现和源修订对不上的改动，停在 `merged` 不提交（退出码 2）。
- 授权：`plan`、`status` 只读；`run`（不带 `--commit`）、`continue`、`abort` 要用户确认过合并计划；提交要用户另行批准。调用方可用环境变量 `MHXY_NO_COMMIT=1` 声明会话没有提交批准，此时 `--commit`、`commit` 都只停在 `merged`。

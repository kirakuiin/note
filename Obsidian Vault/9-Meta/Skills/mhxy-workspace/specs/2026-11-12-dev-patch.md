# 开发分支打 patch（建模板、打包、查进度）

日期：2026-11-12　版本：0.3.42

## 目标

在开发分支上让 agent 代为打 patch：按中文模板名找到（或新建）Sunshine 打包模板，确认后发起打包、查询进度，打出的模板名直接给提测流程用。外放分支有单独流程，trunk、周期分支一律不处理。本次只做 skill 层，不接入 popo-agent-service，但输出保持稳定的 JSON，方便以后由它调用并发通知。

## 背景

- 提测单的「Patch 地址」「PC 资源地址」填同一个 Sunshine 打包模板名（`test-request.md`），skill 里此前没有建模板和打包的能力，都靠手工在 Sunshine 上操作。
- 打包服务 mh-patch-mcp（`http://aluba-mh-patch-mcp.eros.nie.netease.com/mcp`，serverInfo `autopatch-mcp` 3.1.1）。Claude 侧没有配置，Codex 侧只配了地址。

## 已核实（2026-11-12，只读）

- `initialize`、`tools/list` 不需要鉴权；服务有状态，`initialize` 的响应头返回 `mcp-session-id`，后续请求要带上；响应是 SSE。
- 调用工具必须带请求头 `X-Access-Token`（服务称为 v2_token，并从中解析当前用户：打包人、popo 通知对象都由它决定）：
  - 不带：`缺少 X-Access-Token header`。
  - 用 CORP 账号密码走 eros 统一登录得到的 `jwt` cookie：`v2_token 无效或已过期`，不能用。
  - Codex 配置里 docset-mcp-office 的令牌是 JWT（字段 `exp`、`ist`、`user`），已于 2026-07-24 过期 → 令牌会过期，需要更新。
  - Claude 的 codeviewer-mcp 走本机 OpenForge 代理（`127.0.0.1:17655`，`token_proxy.py`）：代理每次调用 CodeMaker Hub 的本地 helper `codemaker-hub-gui.exe mcp-token-helper`（输出 `{"X-Access-Token", "X-Auth-User"}`）取当前令牌，失效时用 `hub-auth-helper renew-token` 续签；注释写明静态令牌一天内失效。用户同意后实测：helper 给的令牌调 `get_user_valid` 返回本人、`valid: true`。
- 已有模板的写法（`query_patch_template` 只读）：`respath` 都填到 `…/_test`；资源分支可以与脚本分支不同名、不同年份，甚至不在 `branchs/` 下（如脚本 `2026_dev/sqz_2026_01_06_wintersale26` 配资源 `2025_dev/sqz_2025_11_12_wintersale26/_test`，`share/patch/dct_dev/hc27/_test`）。模板原始字段是 `scriptpath`、`respath`（另有 `reshtpath`、`isPackHD` 等，`pack_issue` 不涉及）。`query_patch_template` 只搜模板名和描述。
- 相关工具（只读）：`query_patch_template`（模板名／单号／关键词）、`query_patch_by_template`（模板 + 最近一次打包）、`query_ca_table_options`（总单号 → 导表选项）、`query_pack_job_status`、`query_recent_pack_jobs`、`get_user_valid`。
- 相关工具（改远端状态）：`pack_issue(subject, script_svn, issue_id=0, res_svn="", tableinfo=None, auto_start=True)` 建或更新模板，`tableinfo=None` 表示按 `issue_id` 自动查导表、`[]` 表示不导表；`start_patching(template_name)` 后台打包，完成后服务给打包人发 popo。
- 开发分支的地址格式与 `pack_issue` 示例一致：脚本 `svn://svn-xyq.gz.netease.com/svn/products/xy1/develop/client/wzimage/branchs/<年>_dev/<分支>`，资源 `svn://svn-xyq.gz.netease.com/svn/products/xy1/share/patch/branchs/<年>_dev/<分支>/_test`（`wzw_2026_11_10_hancu_effect` 实测；`branch.py` 也按这个结构检出）。

## 方案

### 用户确认的约定

- 模板名默认中文（如 `wzw_2026_11_10_hancu_effect` → “寒促特效”）。第一次由 agent 根据分支名、追踪工单标题、最近的 spec 标题拟一个，预览给用户改；确认后记到工作区级配置 `patch_template`，之后打 patch、提测都复用。
- 新建模板时自动填脚本和资源地址；导表默认不导（显式传 `[]`），需要时用户挑选导表选项。
- 只给开发分支用。
- 建模板是对外操作：每次先预览，用户确认后才执行。打包不需要确认（用户 2026-11-12 改定）：模板已存在且绑定本分支时直接发起；没有模板时仍按建模板流程问用户。

### 令牌

- 每次运行时向 CodeMaker Hub helper 现取（与 OpenForge 代理同一来源），不落盘、不进配置、不输出。helper 路径：环境变量 `CODEMAKER_HUB_AUTH_HELPER_BIN` → `%LOCALAPPDATA%`／`Program Files` 下的 `CodeMaker Hub` → PATH。
- 先用 `mcp-token-helper`（秒回当前令牌），失败再用 `renew-token`。服务回“令牌无效”时请求未执行：续签、重开会话后再试一次，仍被拒就报错。
- 取不到令牌时提示用户确认 Hub 已安装、运行并登录。
- 曾考虑把令牌存进用户级配置（`patch_token`，隐藏输入），因令牌一天内过期而放弃。

### 工作区级配置 `patch_template`

单行文本，1–64 字符，不含引号和换行；按分支（工作区）记录。由 `patch.py` 在建模板或打包成功后通过 `workspace.configure_local` 写入，也可以用 `workspace.py config --set-local` 修改。

### scripts/patch.py

```text
patch.py prepare --root <项目> [--name <模板名>]
patch.py tables  --issue-id <总单号>
patch.py create  --root <项目> --name <模板名> [--issue-id <总单号>] [--table <序号>]... [--apply]
patch.py start   --root <项目> [--name <模板名>] [--apply]
patch.py status  (--job-id <ID> | --recent [N])
```

- **分支**：脚本地址取 `--root` 的 `svn info`，必须是开发分支，否则报错“只支持开发分支；外放分支请走单独流程”，不调用任何远端工具。资源地址取 `<root>/../_test` 的 `svn info`，必须在 `share/patch` 仓库下、以 `/_test` 结尾；分支名与脚本不同时只提醒。
- **模板名判断**：只按精确名称判断模板是否存在；服务模糊命中的模板只列入 `candidates` 并提醒，不算存在（否则一个新名字只要是已有模板名的子串就既不能建也不能打）。
- **本地前置检查**：create、start 在调用任何远端写工具前，先确认工作区已初始化、配置可读，避免远端改完才在记录模板名时失败。
- **输出保留**：各子命令就地填写 main 创建的同一个结果对象，出错时已拿到的远端结果（模板名、job_id）仍在输出里。
- **prepare**（只读）：模板名取 `--name`，否则取配置 `patch_template`。
  - 有名字：`query_patch_by_template`，输出模板是否存在、它绑定的脚本／资源地址是否与本分支一致、最近一次打包（时间、打包人、各仓库 revision、包地址）。
  - 没有名字：`query_patch_template(keyword=分支名)`，列出脚本地址等于本分支的模板作为候选；输出 `name_needed: true`，由 agent 拟中文名给用户确认。
  - `next`：`create`（模板不存在）、`start`（模板存在且地址一致）或 `stop`（地址不一致，说明原因）。
- **tables**（只读）：`query_ca_table_options`，原样输出选项，供用户挑选导表。
- **create**：必须带 `--issue-id` 总单号（> 0）。按“#总单号 ”加截断标题算出最终模板名（`job.expected_name`），标题超长时提醒；该名字的模板已存在时拒绝（改用 start）。`--apply` 后最多等 300 秒（每 20 秒查一次）读回。不加 `--apply` 只输出将要传给 `pack_issue` 的参数；加 `--apply` 时调用 `pack_issue(auto_start=false, tableinfo=--table 列表或 [])`，再用 `query_patch_by_template` 读回核对地址，成功后写 `patch_template`。
- **start**：模板必须存在且绑定本分支（`scriptpath` 等于本分支脚本地址），否则拒绝。不加 `--apply` 只预览；加 `--apply` 调 `start_patching`，输出 `job_id`、`batch_id`；配置里还没有这个名字时一并记录。
- **status**：`query_pack_job_status` 或 `query_recent_pack_jobs`，失败时附带服务给出的 `error`（`raw_error` 只在 `--raw` 时输出，避免刷屏）。
- **输出**：每个子命令向 stdout 输出一个 JSON 对象，字段固定：`action`、`applied`、`branch`、`template`、`package`、`job`、`candidates`、`next`、`warnings`、`errors`（不适用的为 null 或空列表）。以后 popo-agent-service 直接运行脚本、读这个 JSON 发通知。
- **退出码**：0 成功（含预览）；1 失败且未改远端；2 远端已改但后续步骤失败（如模板已建、读回不符或记录配置失败），输出说明已完成哪一步。
- 网络超时不重试：请求可能已经执行，输出提示先用 prepare／status 查清再决定。

### 文档

- `references/patch.md`：完整流程（何时用、模板名怎么拟、预览确认、导表、查进度、失败处理）。
- `test-request.md`：模板名优先用工作区的 `patch_template`。
- `workspace-management.md`：新增 `patch_template` 字段。
- 入口模板「按需读取」加一行“打 patch（建模板、打包、查打包进度）”，边界里写明“确认后可建模板、发起打包”；发布版本递增到 0.3.42。

## 不做

- popo 接入、自动打包监控（`join_auto_patch_monitor` 等）、`patch_all`、`create_patching_template`（依赖提测单）。
- 外放分支、周期分支、trunk。
- 改已有模板的地址或导表：模板地址与本分支不一致时只报告，由用户在 Sunshine 上处理。

## 影响

- 新增 `scripts/patch.py`、`references/patch.md`、`tests/test_patch.py`。
- `workspace.py`：`defaults.json` 加 `patch_template`，并加校验。已有配置不受影响。
- 入口模板变化，已有工作区下次 `context` 自动更新受管区段。

## 验证

- 单元测试：分支识别与拒绝、各子命令在假 MCP 上的请求参数和输出、预览不调用写工具、模糊命中、读回不符和远端后失败的退出码 2 与输出保留、未初始化工作区在远端写入前失败、令牌续签一次、Hub helper 解析、配置字段校验。
- 真实服务：只读运行 `prepare`、`status --recent`；真实建模板和打包需用户另行同意。
- Codex review 第 1 轮（gemini-4-argon）：3 条必须修改（出错时输出丢失远端结果；远端写入前未检查工作区配置、记录失败退出码不为 2；模糊命中被当成已存在）和 2 条建议（status 参数互斥、令牌配置校验）全部采纳，最后一条因令牌不再进配置而不适用。

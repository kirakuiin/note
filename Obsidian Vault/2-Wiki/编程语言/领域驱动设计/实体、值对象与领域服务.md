# 实体、值对象与领域服务

> [!summary] 本篇要解决的问题
> 分层、身份、值、行为归属，以及关联与模块的取舍。

**原书对应**：第4—5章。来源、页码约定与资料说明见 [[2-Wiki/编程语言/领域驱动设计/DDD蓝皮书读书笔记|DDD导读]]。

## 三、把模型放进代码

### 1. 分层：先为业务规则留出位置

> [!summary] 意图与动机
> 让重要业务规则有清楚的归属，避免改界面、换数据库时同时改动业务含义。分层本身不会替你发现模型，但能为模型的独立表达创造条件。

原书介绍用户界面层、应用层、领域层、基础设施层。可以先这样区分职责：

| 层 | 订单取消中的职责 |
| --- | --- |
| 用户界面 | 接收取消请求、展示结果 |
| 应用 | 检查调用者权限、加载订单、安排事务、协调取消流程 |
| 领域 | 判断业务条件、执行合法的取消行为 |
| 基础设施 | 保存对象、调用外部服务、提供技术实现 |

应用层知道“先做什么，再做什么”；领域层知道“业务上什么操作成立”。把业务规则从界面中隔离，也可以对照已有笔记 [[2-Wiki/编程语言/重构/将领域和表述显示分离|将领域和表述显示分离]]。

这里列的是职责。具体源代码依赖怎样组织，可以采用不同实现方式；不要把今天的某一种架构模板当成蓝皮书唯一允许的结构。

### 2. 实体：关注是不是同一个东西

> [!summary] 判断信号
> 即使属性变化，业务仍需追踪“原来那一个”。先确定身份如何被识别，以及在哪个范围内唯一，再决定使用什么ID。

Entity 的核心是身份与连续性。

订单编号为 O-100 的订单，从待付款变成已付款，还是同一个订单。另一个订单即使商品和金额完全相同，也不是它。

建模时先问“业务怎么认出它”，再选择标识方式。数据库主键可能实现身份，但**有主键不等于业务上必然需要实体**。

身份也有范围：订单行可能只需在所在订单内部有身份，不必全系统独立寻址。

### 3. 值对象：关注值是什么

> [!summary] 意图与做法
> 用一个有业务意义的值表达特征，并把相关规则放在一起。明确相等规则；优先采用不可变实现；变化时用新值替换旧值。

Value Object 用来描述某个值或特征，通常按完整的值比较，不关心独立的身份历程。

例如 `Money(100, CNY)` 与另一个 `Money(100, CNY)` 可以被视为相等。重点是金额与币种。把它建成对象，就能集中表达“不同币种不能直接相加”等规则。

```text
Money.add(other):
    如果币种不同：拒绝
    返回一个新的 Money(金额之和, 币种)
```

优先采用不可变值对象：变更地址时替换整个地址值，减少共享可变对象的牵连。对象内部可以有多项数据，甚至引用实体；“值对象”不等于“只有一个简单字段”。

同一概念也可能有不同建模方式：订单上的收货地址快照适合值对象；需要维护修改历史的地址簿条目可能是实体。判断取决于业务需求。

### 4. 领域服务：行为找不到自然的对象归属时

> [!summary] 适用性与取舍
> 操作是领域中的重要行为，但硬放到某个实体或值对象会使它承担别人的职责。服务应表达业务语言；如果只是加载、调用、保存，则先考虑应用层。跨多个对象本身并不足以证明需要领域服务。

Domain Service 表达一个有业务含义、却不适合放进某个实体或值对象的操作。

例如按商品组合、会员资格和促销约束计算一个报价，可能适合一个无状态的定价领域服务。“无状态”指不把某次业务会话的状态保存在服务实例里，并不要求它不能依赖其他能力。

先尝试把行为放回合适的领域对象，再考虑服务。否则容易出现几十个只有 getter/setter 的类，全部业务都堆在一个服务里。

| 操作 | 更自然的归属 |
| --- | --- |
| 两个同币种金额相加 | 金额值对象 |
| 订单接受取消请求 | 订单或相应领域对象 |
| 跨多个概念制定报价 | 视模型而定，可能是领域服务 |
| 启动事务、调用仓库和付款接口 | 应用层协调，技术调用由基础设施实现 |

领域服务、应用服务和技术服务都可能叫 Service；区别在职责，不在类名后缀。

### 5. 关联与模块：减少必须同时理解的东西

订单需要知道客户身份，并不必然意味着客户对象要反向维护所有订单。先判断查询与业务行为真正需要哪一方向的关联；不必要的双向关联会增加同步和加载成本。

Modules 用模块边界表达领域概念之间的内聚关系。例如把履约计划及相关规则放在一起，比只按 `entities / services / repositories` 分目录更能揭示这块业务是什么。

模块可以随模型改变。包名漂亮，但规则到处散落，并没有获得真正的内聚性。

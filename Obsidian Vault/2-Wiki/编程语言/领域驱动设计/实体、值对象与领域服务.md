# 实体、值对象与领域服务

> [!summary] 读完你能回答
> - 两份数据一模一样，在业务上能不能互换？什么时候用实体，什么时候用值对象？
> - 一段业务逻辑该放进对象里，还是放进 Service？
> - 分层、关联、模块各自在帮你解决什么问题？

**原书对应**：第 4—5 章。来源、页码约定见 [[2-Wiki/编程语言/领域驱动设计/DDD蓝皮书读书笔记|DDD导读]]。

## 1. 分层：先给业务规则留一个位置

**为什么要分层？** 让重要的业务规则有个明确的"家"。这样你改界面、换数据库的时候，不会顺手把业务含义也改坏了。分层本身不会帮你找到模型，但它给模型腾出了一块干净的地方。

原书讲了四层，放到"取消订单"里看各自干什么：

| 层 | 在取消订单时负责 |
| --- | --- |
| 用户界面 | 接收取消请求，展示结果 |
| 应用 | 检查调用者有没有权限、加载订单、安排事务、协调整个取消流程 |
| 领域 | 判断业务上能不能取消，执行合法的取消动作 |
| 基础设施 | 保存对象、调用外部服务、提供技术实现 |

一句话区分应用层和领域层：**应用层知道"先做什么、再做什么"；领域层知道"业务上什么操作是成立的"。** 把业务规则从界面里剥出来，也可以对照 [[2-Wiki/编程语言/重构/将领域和表述显示分离|将领域和表述显示分离]]。

> [!warning] 别走极端
> 这张表讲的是**职责**怎么分。源代码的依赖具体怎么组织，可以有不同做法。别把今天流行的某一种架构模板当成蓝皮书唯一允许的结构。

## 2. 实体：关心"是不是同一个"

**判断信号**：就算属性全变了，业务上还需要追踪"原来那一个"——那它就是实体。

Entity 的核心是**身份**和**连续性**。

订单 O-100 从"待付款"变成"已付款"，它还是那个订单。另一张订单就算商品和金额一模一样，也不是它。

建模时先问"**业务上是怎么认出它的？**"，再决定用什么 ID。数据库主键可以用来实现身份，但反过来不成立：**有主键，不代表业务上就必须是实体。**

身份还有范围。比如订单行可能只需要在它所属的订单里能被认出来，没必要在整个系统里单独寻址。

## 3. 值对象：关心"值是什么"

**做法**：用一个有业务含义的值来描述某个特征，把相关规则收在一起。讲清楚怎么比较相等，尽量做成不可变的，要变就整个换一个新值。

Value Object 描述的是一个值或特征，通常按完整的值来比较，不关心它有没有自己的"身世"。

比如 `Money(100, CNY)` 和另一个 `Money(100, CNY)` 就可以看作相等，重要的只是金额和币种。把它做成对象有个好处：像"不同币种不能直接相加"这样的规则，就有了固定的落脚点。

```text
Money.add(other):
    如果币种不同：拒绝
    返回一个新的 Money(金额之和, 币种)
```

为什么推荐不可变？比如改地址时整个替换一个新地址值，就不会出现"两个地方共享同一个可变对象，改一处、另一处跟着变"的麻烦。

两个常见误会：

- **值对象不等于"只有一个字段"**。它内部可以有多项数据，甚至可以引用实体。
- **同一个概念，换个场景可能建模方式不同**。订单上的收货地址是一份快照，适合做值对象；地址簿里需要记录修改历史的条目，就可能是实体。到底选哪个，看业务需要。

## 4. 领域服务：这个动作找不到合适的对象来承担

**什么时候用？** 某个操作是领域里的重要行为，但硬塞给某个实体或值对象，会让它背上不属于自己的职责。

Domain Service 表达的就是这种"有业务含义、但不适合放进任何一个实体或值对象"的操作。

举例：根据商品组合、会员资格和促销条件算出一个报价，可能就适合交给一个无状态的定价领域服务。"无状态"的意思是：不把某次业务会话的状态存在服务实例里，并不是说它不能依赖别的能力。

顺序很重要：**先试着把行为放回合适的领域对象，放不下了再考虑服务。** 否则很容易演变成几十个只有 getter/setter 的"贫血"类，所有业务都堆在一个大 Service 里。

| 操作 | 更自然的归属 |
| --- | --- |
| 两个同币种金额相加 | 金额值对象 |
| 订单接受取消请求 | 订单（或相应的领域对象） |
| 综合多个概念计算报价 | 看模型而定，可能是领域服务 |
| 启动事务、调用仓库和支付接口 | 应用层协调，技术调用交给基础设施 |

> [!warning] 别走极端
> - 操作只是"加载、调用、保存"，那是应用层的活，不是领域服务。
> - "涉及多个对象"本身不足以说明需要领域服务。
> - 领域服务、应用服务、技术服务都可能叫 `XxxService`。区别在职责，不在类名后缀。

## 5. 关联与模块：减少需要同时理解的东西

**关联**：订单需要知道客户是谁，不代表客户对象就得反过来维护自己所有的订单。先想清楚查询和业务行为真正需要哪个方向的关联。多余的双向关联只会增加同步和加载的负担。

**模块（Modules）**：用模块边界表达领域概念之间的内聚关系。比如把"履约计划"和相关规则放在一起，比按 `entities / services / repositories` 分目录更能看出"这块业务是干什么的"。

模块可以随着模型一起调整。包名起得再漂亮，规则却散落各处，那也没有真正的内聚。

## 一分钟回顾

- 应用层管"先后顺序"，领域层管"业务上成不成立"。
- **实体看身份**：属性变了还是"那一个"；有主键不等于必须是实体。
- **值对象看值**：值相同就能互换，尽量不可变，要变就整个替换。
- **领域服务是最后的选择**：先把行为放回对象，放不下再考虑服务。
- 关联只保留真正需要的方向；模块按业务概念组织，而不是按技术类型。

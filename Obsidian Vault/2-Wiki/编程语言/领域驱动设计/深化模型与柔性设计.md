# 深化模型与柔性设计

> [!summary] 本篇要解决的问题
> 从业务反例发现概念，以规格和柔性设计改善模型。

**原书对应**：第8—13章。来源、页码约定与资料说明见 [[2-Wiki/编程语言/领域驱动设计/DDD蓝皮书读书笔记|DDD导读]]。

## 四、通过重构发现更好的模型

这是蓝皮书第三部分的重点：模型的改善不仅来自整理代码，也来自对业务更深入的理解。

### 1. 从一个难看的条件，发现遗漏的概念

最初用一个 `Order.status` 表示整个订单进度。后来条件变成：

```text
如果订单已付款，并且未发货，并且不是部分发货，
并且仓库没有拣货，并且不是特殊预售……
```

这些条件可能不是一个算法写坏了，而是一个状态字段承担了几种不同的业务事实：

- 购买承诺是否仍然有效。
- 钱是否支付、退款是否处理完。
- 商品是否进入仓库作业、哪些数量已发出。

通过讨论，团队可能发现需要单独表达“履约计划”：它描述哪些商品数量准备由哪些履约任务交付。购买承诺、资金处理与履约进度因此可以被分别解释，再定义它们如何协作。

新模型让“已取消但退款处理中”成为可以解释的情况，而不是一个不可能塞进旧枚举的异常状态。

**这才是深化模型**：发现过去隐含的概念，让原来散落的例外拥有清楚的归属。新增类只是结果，业务解释力的提高才是收益。

> [!example] 原书第8章的突破，简化复述
> 银团贷款中，几家公司先承诺承担授信份额，但一次实际放款可以另行协商：某公司少出钱，另一家公司补上。最初的模型把“承诺的授信份额”和“实际贷款份额”绑定，后来只好不断添加调整对象。
> 突破在于承认两种份额可以独立变化，并将份额分配提炼成 `Share Pie` 模型。复杂的例外不再都靠修补旧结构解决。值得记住的是：**业务上不成立的绑定，不能靠更多补丁变成好模型**。（书内132—136页／PDF154—158页。）

### 2. 在哪些地方寻找新概念

| 信号 | 可以追问什么 |
| --- | --- |
| 业务人员不断说某个词，代码里却没有它 | 是不是漏掉了重要概念？ |
| 某段逻辑需要大量注释才能解释 | 是否混合了不同职责或不同业务事实？ |
| 两条“常识”互相矛盾 | 是否来自不同情境或上下文？ |
| 同一组条件出现在许多地方 | 是否有一个应该明确表达的规则？ |
| 一个对象承担整个业务流程 | 流程自身是否需要状态、身份和业务含义？ |

例如“退款申请”如果有审批、重试、驳回和追踪需求，可能需要建模为对象，而不是一次随调用栈消失的 `refund()`。

不是每个动词都值得一个类。只有当明确这个概念能减少歧义、表达重要规则时，才值得引入。

### 3. Specification：把判断条件变成能讨论的规则

Specification（规格）可以理解为一个明确表达“某对象是否满足某项业务条件”的规则对象。

假设促销仅适用于“指定商品且报价金额满100元”的报价。每个调用点都写一份条件，容易逐渐不一致。可以把条件表达成命名规则，并按业务含义组合：

```text
促销适用规格 = 包含指定商品 AND 报价金额至少100元
促销适用规格.isSatisfiedBy(报价)
```

它的价值在于让规则可命名、可组合、可复用。原书也讨论将规格用于验证、选择与按约束构建对象；本文只展开最容易理解的验证用途。

一个只使用一次的简单条件，直接写在对象方法里可能更清楚。不要为了使用模式，把每个 `if` 都改成一套规则框架。

### 4. 柔性设计：让模型易于理解和组合

Supple Design 常译作柔性设计。目标是让开发者可以较容易地使用和改进模型，而不必理解一大团隐含依赖。

原书第10章明确提醒：过多抽象层和间接设计可能妨碍开发。先让关键、复杂部分变得可理解、可组合，比让整个系统预先具备无限扩展能力更实际。（书内168—170页／PDF190—192页。）

| 原书手法 | 白话解释 | 教学例子 |
| --- | --- | --- |
| Intention-Revealing Interfaces | 接口直接说清意图 | `requestCancellation()` 比 `setStatus(9)` 更明确 |
| Side-Effect-Free Functions | 查询或计算尽量不偷偷修改状态 | `calculateTotal()` 返回金额，不顺便改变付款状态 |
| Assertions | 明确前置条件、后置条件与不变量 | 改数量后仍保证数量为正、商品总额一致 |
| Conceptual Contours | 沿业务概念的自然边界切分 | 将资金处理与仓库作业的规则分开表达 |
| Standalone Classes | 降低理解一个类所需的其他知识 | 理解 `Money` 时不必同时加载整个订单体系 |
| Closure of Operations | 运算尽可能仍返回相同概念的值 | 金额相加返回 `Money`，便于继续组合 |

“无副作用”不要求所有方法都不能改变对象。取消订单当然会改变状态；关键是把修改行为说清楚，把计算与修改尽量分开。

“断言”也不仅是语言中的 `assert` 语句。条件需要在接口、测试和实现中得到表达；不能依赖生产环境可能关闭的断言来保护关键业务约束。

“独立类”不等于所有类都零依赖；“运算闭合”也不是所有函数都必须返回自己的类型。它们是改善理解与组合的手法，要服从概念本身。

### 5. 声明式设计：直接表达规则的组成

如果促销规则确实需要经常组合，可以用“满额规则 AND 商品规则”表达业务条件，把遍历、调用和组合机制放到另一层。

这样读模型时容易看到业务是什么，而不用穿过全部执行步骤。原书进一步讨论领域专用语言，但并没有要求每个项目都造一门语言。

### 6. 分析模式与设计模式：借用经验，但检查语义

分析模式提供已有业务建模经验，例如账户、交易等概念关系；使用前仍要验证它是否适合当前业务。

设计模式提供实现组织方法。例如促销策略可以用 [[2-Wiki/编程语言/设计模式/策略模式|策略模式]]，复合规格可以借助 [[2-Wiki/编程语言/设计模式/组合模式|组合模式]]。重点是这些结构能否表达领域含义，而不是凑齐模式。

### 7. 重构的收益，要用业务例子来判断

改进后应能更直接地表达真实场景，例如“已付款、尚未履约的订单接受取消”“部分履约只能取消剩余数量”。如果类数增加了，规则依然要绕很久才能讲清楚，就还没有获得主要收益。

改变模型可能改变业务行为，不能假装它只是格式整理。先固定已确认的场景，再明确哪些规则保持、哪些规则因新理解而调整。

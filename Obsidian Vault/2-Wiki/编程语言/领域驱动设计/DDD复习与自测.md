# DDD复习与自测

> [!summary] 怎么用这一页
> 先合上其他笔记，自己回答问题，再展开答案对照。答不上来的，顺着"按问题找概念"表格回去重读。题目和答案都是教学补充，不是原书内容。来源说明见 [[2-Wiki/编程语言/领域驱动设计/DDD蓝皮书读书笔记|DDD导读]]。

## 1. 热身：合上笔记，用五句话复述 DDD

1. DDD 主要对付什么困难？什么情况下值得投入？
2. 一个模型是怎么进入讨论、代码和测试的？
3. 身份、值、行为归属、一致性，分别帮你做什么决定？
4. 什么样的证据会让你改掉一个已有模型？
5. 两套模型统一不了的时候，怎么划边界、怎么协作？

> [!faq]- 参考要点
> DDD 围绕复杂的业务知识持续建模。模型是**有目的的简化**；统一语言让团队的讨论和代码互相检验。**实体看身份，值对象看值**，领域服务承担那些不适合放进任何对象的业务行为，**聚合保护一组必须一起成立的规则**。新场景、互相矛盾的说法、一再出现的补丁，都可能说明漏掉了概念。不同模型用**限界上下文**划清适用范围，再明确翻译、接口和团队合作关系；**核心域**决定把精力投在哪里。

## 3. 容易混的概念，放在一起比

| 容易混的一对 | 区别在哪 | 一句话判断 |
| --- | --- | --- |
| 领域模型 / 数据库模型 | 前者解释业务概念和规则，后者安排怎么存 | 离开表字段，你能讲清一条业务规则吗？ |
| 实体 / 值对象 | 前者关心持续的身份，后者关心描述的值 | 值相同的两个对象，在这个业务里能互换吗？ |
| 实体 / 聚合根 | 实体不一定是一个聚合的对外入口 | 谁在守这条边界的共同规则？ |
| 领域服务 / 应用服务 | 领域服务表达业务操作，应用服务协调用例 | 这是在做业务判断，还是在安排调用和事务？ |
| 工厂 / 仓储 | 工厂负责创建，仓储负责找回和持久化访问 | 是生一个新对象，还是恢复一个已有身份？ |
| 聚合 / 模块 | 聚合保护一致性，模块组织内聚的概念 | 是要"一起提交才正确"，还是"放一起好理解"？ |
| 模块 / 限界上下文 | 模块组织同一个模型；上下文划定模型的适用范围 | 同一个词在这里的模型含义一致吗？ |
| 限界上下文 / 微服务 | 前者是语义边界，后者是独立运行和部署 | 这条边界来自语义，还是只是运维上的拆分？ |
| 子域 / 限界上下文 | 子域是在拆业务问题；上下文是在划具体模型的范围 | 你在分解业务，还是在圈定模型？两者不强制一一对应 |
| 核心域 / 技术难点 | 核心域看的是业务上的差异化价值 | 把它做好，能成为这家公司的关键优势吗？ |
| 代码重构 / 模型深化 | 整理代码不一定带来新的业务认识 | 你是否发现了更能解释业务的概念？ |
| 防腐层 / 字段映射 | 防腐层保护本地语义，字段转换只是其中可能的一个动作 | 对方的"成功"真的等于我方的"完成"吗？ |

> [!note] 关于"子域 / 上下文"这一行
> 这是帮助学习的对照。原书战略设计的主线仍然是保持模型完整性、精炼和大比例结构，别把后来常见的分类方式当成原书的固定模板。

## 4. 基础题：先说出理由，再展开答案

**题 1：两个订单的字段完全相同，它们是同一个订单吗？收货地址一定是实体吗？**

> [!faq]- 参考答案
> 两个独立的订单，就算属性全一样，也可能是不同的业务身份；如果是同一个订单在内存里的两份副本，那就是同一个实体的不同表示。地址快照通常按值判断；地址簿里的条目如果需要身份和历史，就可能是实体。判断依据是**业务含义**，不是内存地址，也不是有没有数据库 ID。

**题 2：一次取消同时用到了订单、库存和退款记录，是不是应该把它们放进一个聚合？**

> [!faq]- 参考答案
> 信息还不够，没法下结论。"同一个用例里都用到了"证明不了它们该在一个聚合里。先写出必须同时成立的规则，问问业务能不能接受"退款处理中"这样的中间状态，再看各个对象的生命周期、修改竞争和系统边界。

**题 3：把 OrderService 里的条件判断全部提炼成短函数，算不算完成了领域建模？**

> [!faq]- 参考答案
> 可读性可能变好了，但还要检查：概念准不准确？规则有没有放到合理的地方？语言是不是一致？如果"已取消但退款中"还是表达不了，只提炼函数并没有解决模型问题。

## 5. 应用题：判断依据比术语更重要

**题 4：仓库说的"完成"是包裹出库，交易说的"完成"是客户确认收货。给出两种处理方式，并说说各自的取舍。**

> [!faq]- 参考答案
> 如果它们在同一个模型里，就该改用"已出库""已确认收货"这样清楚的词，别让一个状态装两种意思。如果它们本来就属于两套独立的模型，可以各自保留本地术语，但要在交互协议里讲清楚"出库"和"确认收货"这两个事实。另外，不能光凭一个同名词就决定拆成微服务，还得看模型、团队和集成的实际需求。

**题 5：额度 1000，当前总额 700，两个人同时各加 200。已经把 changeQuantity 放进 Order 类了，还缺什么？**

> [!faq]- 参考答案
> 缺**覆盖整张订单的并发控制**。两份内存副本都可能算出 900；持久化时必须有冲突检测或串行化保护，让其中一次在最新状态下重新判断。还要确认系统里没有绕过聚合根和版本控制、直接改订单行的入口。

**题 6：给订单加 paid、shipped、cancelled 三个布尔字段，是不是比一个 status 更符合 DDD？**

> [!faq]- 参考答案
> 不能看字段个数下结论。拆开的字段可能更准确，也可能放进去一堆没定义过的非法组合。要先列出业务事实、合法的组合以及行为怎么变。如果已经需要按任务判断能撤回多少，这三个布尔值还是不够用；如果业务很简单，三个字段或者一个状态机都可能够用。

**题 7：优惠规则只有一条"满 100 减 10"，要不要马上引入 Specification 和策略接口？以后要加每周组合促销呢？**

> [!faq]- 参考答案
> 只有一个简单条件时，直接写就行，不用先搭框架。等规则需要反复组合、单独命名、复用和校验时，规格就有价值了；如果变化点是"计算算法不一样"，策略模式可能更合适。关键是说清楚**到底是什么在变**，别因为名字听起来像就混着用。

**题 8：支付接口返回 SUCCESS，领域对象立刻变成 RefundCompleted。这段翻译有什么需要确认的地方？**

> [!faq]- 参考答案
> 必须先查清 SUCCESS 是"已受理"还是"钱真的退完了"。如果只是受理，本地就应该保留"待确认"的状态，并说明之后怎么拿到最终结果。还要定义重复请求、失败和超时分别怎么处理。这不是把枚举名改漂亮就能解决的。

**题 9：登录模块最难写、出故障代价最大，它是不是核心域？**

> [!faq]- 参考答案
> 技术难度、可靠性要求、业务差异化价值，是三把不同的尺子。对普通零售业务来说，登录很可能不是核心域；但如果一家公司的竞争优势就是身份风控，相关模型就可能属于核心。先说清楚组织的目标，不能给某个模块贴一个固定的分类。

**题 10：为"预约取消"设计一个最小模型。别直接照搬订单的答案。**

> [!faq]- 解题检查表
> 先问清楚：预约的是什么？谁能取消？截止时间怎么算？收不收费？取消后名额释不释放？重复申请怎么处理？然后再选身份、时间值、取消行为和共同规则。如果涉及外部退款，问问业务能不能接受中间状态。一个合格的答案应该包含：正常场景、边界场景、还没确认的假设，以及设计取舍。没有唯一正确的类图。

## 6. 怎样判断自己真的学会了

| 水平 | 你能做到 | 下一步 |
| --- | --- | --- |
| 认得名词 | 能背定义，但换个例子就犹豫 | 重走一遍完整案例，每一步都说出"为什么这么选" |
| 分得清概念 | 能说出实体/值对象、聚合/上下文的区别 | 做应用题，先别看答案 |
| 能初步上手 | 能从一个场景提出模型，并列出假设 | 用反例推翻或改进自己的模型 |
| 能讲清取舍 | 能比较几种方案和各自的成本 | 带着实际问题回读原书对应章节 |

复习时先闭卷答，再展开答案；答不出来的就回到对应的那一节。过一段时间，换成你自己工作中的业务再做一遍，看看自己是真懂了，还是只记住了订单这个故事。

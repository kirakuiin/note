## 八、复习速查与情境自测

### 1. 先合上正文，用五句话复述

1. DDD主要处理什么困难，什么情况下投入值得？
2. 一个模型如何进入讨论、代码和测试？
3. 身份、值、行为归属和一致性各帮助你做什么决定？
4. 什么证据会促使你改变已有模型？
5. 当两套模型无法统一时，如何明确边界与协作？

> [!faq]- 参考要点
> DDD围绕复杂业务知识进行持续建模。模型是有目的的简化；统一语言让团队讨论与实现相互检验。实体看身份，值对象看值，服务承载不自然属于某个对象的领域行为，聚合保护一组必须一致维护的规则。新场景、矛盾与重复补丁可能揭示遗漏概念。不同模型用限界上下文划清适用范围，再明确翻译、接口和团队合作关系；核心域决定投入重点。

### 3. 易混概念对照

| 容易混淆的概念 | 区别 | 判断办法 |
| --- | --- | --- |
| 领域模型 / 数据库模型 | 前者解释业务概念与规则，后者安排持久化结构 | 能否脱离表字段说明一条业务规则？ |
| 实体 / 值对象 | 前者关心持续身份，后者关心所描述的值 | 值相同的两个对象在此业务中能否互换？ |
| 实体 / 聚合根 | 实体未必承担一个聚合的对外入口 | 谁保护该边界的共同规则？ |
| 领域服务 / 应用服务 | 领域服务表达业务操作，应用服务协调用例 | 这是业务判断，还是安排调用和事务？ |
| 工厂 / 仓储 | 工厂创建，仓储找回与持久化访问 | 是一个新业务对象，还是恢复既有身份？ |
| 聚合 / 模块 | 聚合保护一致性，模块组织内聚概念 | 要一起提交正确，还是一起理解方便？ |
| 模块 / 限界上下文 | 模块组织同一模型；上下文界定模型适用范围 | 同一个词的模型含义是否一致？ |
| 限界上下文 / 微服务 | 前者是模型语义边界，后者涉及独立运行部署 | 边界来自语义，还是只来自运维拆分？ |
| 子域 / 限界上下文 | 子域划分业务问题；上下文界定所采用模型 | 在分解业务，还是划定具体模型范围？二者不强制一一对应 |
| 核心域 / 技术难点 | 核心域取决于业务差异化价值 | 做好它是否形成这家组织的关键优势？ |
| 代码重构 / 模型深化 | 代码整理未必带来新业务认识 | 是否发现了更能解释业务的概念？ |
| 防腐层 / 字段映射 | 防腐层保护本地语义，字段转换只是可能的动作 | 对方的“成功”是否真的等于我方的“完成”？ |

子域与上下文的对照是学习辅助：原书的战略设计主线仍以保持模型完整性、精炼和大比例结构为准，不把后续常见分类当成原书的固定模板。

### 4. 基础检查：先说理由，再看答案

**题1：两个订单字段相同，是否就是同一个订单？收货地址一定是实体吗？**

> [!faq]- 参考答案
> 两个独立订单即使属性相同，也可能有不同业务身份；如果是同一订单的两个内存副本，则是同一实体的不同表示。地址快照通常按值判断，地址簿条目若有身份和历史需求则可能是实体。关键是业务语义，不是内存地址或有没有数据库ID。

**题2：一次取消同时用到订单、库存、退款记录，是否应该放进一个聚合？**

> [!faq]- 参考答案
> 现有信息不足。“一次用例涉及”不能证明需要一个聚合。先写必须同时成立的规则，询问可否存在退款待处理等中间状态，再考察各对象生命周期、修改竞争和系统边界。

**题3：把OrderService里的条件都提炼为短函数，是否已经完成领域建模？**

> [!faq]- 参考答案
> 可读性可能改善，但还需要验证概念是否准确、规则是否有合理归属、语言是否一致。若“已取消但退款中”仍然表达不了，仅提炼函数没有解决模型问题。

### 5. 应用题：判断依据比术语重要

**题4：仓库里的“完成”指包裹出库，交易里的“完成”指客户确认收货。请给出两种处理方式，并说明取舍。**

> [!faq]- 参考答案
> 若都在同一模型中，应使用“已出库”“已确认收货”等清楚词语，避免一个状态装两种意思。若本来属于两套独立模型，可以各自保留本地术语，但在交互协议中明确出库事实和确认收货事实。不能仅凭一个同名词就决定拆成微服务；还要检查模型、团队和集成需求。

**题5：额度1000，总额700；两人同时各加200。把changeQuantity放进Order类以后，还缺什么？**

> [!faq]- 参考答案
> 缺覆盖整个订单修改的并发控制。两个内存副本都可能算出900；持久化时必须冲突检测或串行保护，使其中一次在最新状态下重判。还要确保不存在绕过根和版本控制的订单行更新入口。

**题6：订单增加paid、shipped、cancelled三个字段，是否比一个status更符合DDD？**

> [!faq]- 参考答案
> 不能只凭字段个数判断。独立字段可能更准确，也可能允许未定义的非法组合。要列出业务事实、合法组合与行为变化。如果已经需要按任务判断可撤回数量，这三个布尔值仍然不够；如果业务简单，三个字段或一个状态机都可能足够。

**题7：优惠规则只有一次“满100减10”，是否马上引入Specification与策略接口？以后新增每周组合促销呢？**

> [!faq]- 参考答案
> 一次简单条件通常可以直接表达，不必先建框架。若规则需要反复组合、独立命名、复用与校验，规格可能有价值；如果变化点是不同计算算法，策略可能合适。要分别说明正在变化的是什么，不因名字相似混用模式。

**题8：支付接口返回SUCCESS，领域对象立刻变成RefundCompleted。这段翻译有什么待确认之处？**

> [!faq]- 参考答案
> 必须查明SUCCESS代表受理还是实际退款完成。如果只是受理，本地应保留待确认事实，并说明如何取得最终结果。还需定义重复请求、失败与超时的处理。这不是把枚举名改漂亮就能解决的问题。

**题9：登录模块最难写、故障代价最大，是否就是核心域？**

> [!faq]- 参考答案
> 技术难度、可靠性重要性与业务差异化价值不是同一尺度。对普通零售业务，登录可能不是核心域；对以身份风控为竞争优势的业务，相关模型可能属于核心。要先说明组织目标，不能固定某个模块的分类。

**题10：请为“预约取消”设计一个最小模型；不要直接套用订单答案。**

> [!faq]- 解题检查表
> 先问预约什么、谁可取消、截止时间如何算、是否收费、取消是否释放名额、重复申请怎样处理。再选身份、时间值、取消行为和共同规则。如果涉及外部退款，问业务是否允许中间状态。一个合理答案应包含正常场景、边界场景、未确认假设与设计取舍；没有唯一的类图标准答案。

### 6. 如何判断自己真的学会了

| 水平 | 可观察的表现 | 下一步 |
| --- | --- | --- |
| 认得名词 | 能复述定义，但换个例子就犹豫 | 重走完整案例，逐步解释为什么这样选 |
| 能区分概念 | 能说明实体/值对象、聚合/上下文的差别 | 做应用题，不先看答案 |
| 能初步应用 | 能从场景提出模型并列出假设 | 用反例推翻或改进自己的模型 |
| 能解释取舍 | 能比较替代方案及成本 | 带着实际问题回读原书相应章节 |

复习时先闭卷回答，再展开答案；答不出的地方回到对应节。隔一段时间换成自己的业务再做一次，检查是否只是记住了订单故事。

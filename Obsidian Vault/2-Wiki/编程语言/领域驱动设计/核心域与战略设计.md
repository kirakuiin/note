# 核心域与战略设计

> [!summary] 读完你能回答
> - 核心域怎么判断？为什么"最难写的模块"不一定是核心域？
> - 有哪些办法能让核心在庞大的系统里被看见？
> - 大比例结构是什么？小系统需要它吗？

**原书对应**：第 15—17 章。来源、页码约定见 [[2-Wiki/编程语言/领域驱动设计/DDD蓝皮书读书笔记|DDD导读]]。

战略设计不只是给大系统划边界，还包括两件事：**把核心提炼出来**，以及**用合适的大尺度结构帮团队看清全局**。说白了，就是把有限的精力花在刀刃上。

## 1. 精炼：哪块业务决定了你的优势

Distillation（提炼／精炼）的目的，是让核心业务知识从庞杂的系统里浮出来。

假设一家公司的优势是"面对复杂的商品组合，能找到成本低、时效又靠谱的履约方案"。那这套规划逻辑很可能就是它的 **Core Domain（核心域）**；而普通的账号登录，就不一定是。

几点要注意：

- 核心域**不等于**代码最复杂的地方，也不是某个固定的行业模块。
- 它取决于**这家组织的目标、竞争优势和独有知识**，业务变了，核心也会变。

原书的建议很实在：你没法把系统的每个部分都打磨到同样精细，所以**让最能干的人投入核心，优先做对核心影响大的重构**。技术基础设施往往更有吸引力，但不能因此冷落了最重要的业务模型。（书内 279—280 页／PDF 301—302 页。）

**Generic Subdomains（通用子域）**：也得解决，但体现不出你的主要差异。可以考虑现成产品、外部服务，或者做个简单实现就够。"通用"也不是说你得把它做成一个全世界都能用的框架。

> [!note] 关于"核心／支撑／通用"三分法
> 今天常见的"核心域／支撑子域／通用子域"三分法对落地很有帮助，但别把后来形成的分类习惯，当成原书一字不差的结论。

## 2. 怎样让核心被看见

| 原书手法 | 实际可以做的一件事 |
| --- | --- |
| Domain Vision Statement，领域愿景陈述 | 写一段短文，说清业务价值、差异化和建模方向 |
| Highlighted Core，突出核心 | 在文档或代码导航里，把最重要的业务知识标出来 |
| Cohesive Mechanisms，内聚机制 | 把纯计算或执行机制分离出去，让业务决策更显眼 |
| Segregated Core，隔离核心 | 不让核心模型被一大堆次要细节淹没 |
| Abstract Core，抽象核心 | 提炼出核心概念之间最重要的抽象关系 |

拿履约的例子来说："为什么选这个履约方案"是业务决策；"怎样遍历搜索空间"可以算内聚机制。但如果某种独门算法本身就是你的竞争优势，它也可能属于核心。**别因为代码看起来很"技术"就把它排除在核心之外。**

> [!warning] 别走极端
> 精炼的目的是让核心更好懂，不是给每个手法都新建一层接口。

## 3. 大比例结构：给全局一个够用的秩序

Large-Scale Structure，中文版译作"大比例结构"，也常被叫作"大尺度结构"。它为大型模型提供一种**跨越局部的组织方式**。

它和限界上下文是互补的：**大比例结构帮你理解整体怎么组织，限界上下文保护每套模型的完整性。**（书内 303—305 页／PDF 325—327 页。）

| 原书概念 | 说人话，再举个例子 |
| --- | --- |
| Evolving Order，演进的秩序 | 结构跟着理解一起调整，别提前冻结一张包办未来的蓝图 |
| System Metaphor，系统隐喻 | 用一个大家都懂的图景帮助理解，比如"履约就像流水线"；遇到解释不了的情况就修正隐喻 |
| Responsibility Layers，职责层 | 按领域职责和依赖来组织大模型，比如"政策决定 → 计划安排 → 实际执行" |
| Knowledge Level，知识层 | 把"描述规则或类型的模型"和"按规则运行的实例"分开，比如"促销方案的定义"和"一次具体的报价计算" |
| Pluggable Component Framework，可插拔组件框架 | 模型和协议都已经清楚时，让组件按共同约定来替换 |

两个容易混淆的地方：

- 这里的"职责层"**不是**前面讲的"界面／应用／领域／基础设施"四层的别名。
- "知识层"也**不只是**配置文件或文档目录。

> [!warning] 别走极端
> 大比例结构是有成本的。小系统先有清楚的语言和几个模块就够了，不必一上来就搞知识层或可插拔框架。

## 4. 把三件事放在一起看

战略设计归根结底在回答三个问题：

- **上下文**：哪套模型在哪个范围内有效？
- **精炼**：哪些知识最值得团队投入？
- **大比例结构**：整体怎么组织，才更容易理解和协作？

好的战略要结合现有系统、团队能力、合作关系和业务目标来评估。模型设计需要团队真正参与进来，不能靠一份脱离实现的总体规划一锤定音。

## 一分钟回顾

- **核心域 = 决定你竞争优势的那块业务**，不是代码最难的那块。
- 把最强的人和最多的重构投入核心；通用子域考虑现成方案或简单实现。
- 让核心可见：愿景陈述、突出核心、分离内聚机制、隔离核心、抽象核心。
- 大比例结构帮你看清全局，和限界上下文互补；小系统不必上。
- 战略设计 = 上下文（在哪成立）+ 精炼（投在哪）+ 结构（怎么组织）。

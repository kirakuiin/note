# 核心域与战略设计

> [!summary] 本篇要解决的问题
> 识别核心域，理解精炼与大比例结构的投入取舍。

**原书对应**：第15—17章。来源、页码约定与资料说明见 [[2-Wiki/编程语言/领域驱动设计/DDD蓝皮书读书笔记|DDD导读]]。

## 六、把精力放在真正重要的地方

战略设计不只是在大系统中划边界，还包括提炼核心，以及用恰当的大尺度结构帮助团队理解整体。

### 1. 提炼：哪些业务决定你的优势

Distillation（提炼／精炼）让核心业务知识从庞杂系统中显现出来。

假设这家公司的优势是“针对复杂商品组合，找到成本低且时效可靠的履约方案”。那么这套规划逻辑可能是 Core Domain（核心域），普通账号登录则不一定是。

核心域不等于最复杂的代码，也不等于某个固定行业模块。它与具体组织的目标、竞争优势和知识有关，会随业务改变。

原书强调，无法对系统所有部分做同等程度的精化，应让最有能力的人投入核心，并优先选择对核心影响大的重构。技术基础设施很吸引人，但不能因此让最重要的业务模型被忽略。（书内279—280页／PDF301—302页。）

Generic Subdomains（通用子域）是需要解决、但不体现主要差异化的领域问题。可评估现成产品、外部能力或较简单实现。通用也不意味着你必须把它做成一个可供全世界使用的框架。

今天常见的“核心／支撑／通用”三分法有助于落地，但不能把所有后续分类习惯都直接当成原书逐字结论。

### 2. 怎样让核心变得可见

| 原书手法 | 实际能做的一件事 |
| --- | --- |
| Domain Vision Statement，领域愿景陈述 | 用短文说明业务价值、差异和建模方向 |
| Highlighted Core，突出核心 | 在文档或代码导航中标出最重要的业务知识 |
| Cohesive Mechanisms，内聚机制 | 分离清楚的计算或执行机制，让业务决策更易看见 |
| Segregated Core，隔离核心 | 让核心模型免于被大量次要细节淹没 |
| Abstract Core，抽象核心 | 提取核心概念之间最重要的抽象关系 |

在教学例子中，“为何选择这个履约方案”属于业务决策；“怎样遍历搜索空间”可以是内聚机制。但如果某种独特算法本身就是优势，它也可能属于核心。不要仅因代码看起来技术化就把它排除。

提炼要改善核心的可理解性，不是为每个手法新建一层接口。

### 3. 大尺度结构：给整体一个够用的秩序

Large-Scale Structure，用户提供的版本译作“大比例结构”，也常被解释为大尺度结构。它为大型模型提供跨局部的组织方式。它和限界上下文互补：前者帮助理解整体组织，后者保护各套模型的完整性。（书内303—305页／PDF325—327页。）

| 原书概念 | 白话解释与例子 |
| --- | --- |
| Evolving Order，演进的秩序 | 结构随实际理解调整，不提前冻结一张包办未来的蓝图 |
| System Metaphor，系统隐喻 | 用一个共同图景帮助理解，例如把履约看作流水线；发现解释不了的情况时修正隐喻 |
| Responsibility Layers，职责层 | 按领域职责和依赖组织大型模型，例如政策决定、计划安排、实际执行 |
| Knowledge Level，知识层 | 将描述业务规则或类型的模型，与依这些规则运行的实例区分开，例如促销方案定义与一次报价计算 |
| Pluggable Component Framework，可插拔组件框架 | 在模型与协议已经清晰时，让组件替换遵守共同约定 |

这里的“职责层”不是前面用户界面／应用／领域／基础设施四层的别名；“知识层”也不只是配置文件或文档目录。

大尺度结构有使用成本。小系统可以先有清楚的语言和少量模块，不必立刻上知识层或可插拔框架。

### 4. 把战略放在一起看

- 上下文：哪套模型在哪个范围内有效？
- 提炼：哪些知识最值得团队投入？
- 大尺度结构：怎样组织整体，才更容易理解和协作？

好的策略要结合现有系统、团队能力、合作关系和业务目标评估。模型设计需要团队实际参与，不能由一份脱离实现的总规划永久决定。

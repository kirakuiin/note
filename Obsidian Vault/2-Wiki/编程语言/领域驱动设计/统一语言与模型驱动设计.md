# 统一语言与模型驱动设计

> [!summary] 本篇要解决的问题
> 通过业务讨论形成统一语言，让模型与实现相互检验。

**原书对应**：第1—3章。来源、页码约定与资料说明见 [[2-Wiki/编程语言/领域驱动设计/DDD蓝皮书读书笔记|DDD导读]]。

## 二、先把业务说清楚

### 1. 知识消化：边做边学，而不是先拿齐需求

原书的 Knowledge Crunching 可以理解为：开发者和业务专家把零散事实、经验、例外反复讨论，整理成能解释业务的模型。

第一次听到“发货前可以取消”，不要直接写一个 `status < SHIPPED` 条件。继续问具体情境：

- 仓库已拣货但还没出库，可以取消吗？
- 一部分商品已发货，剩下部分怎么办？
- 系统显示未发货，但仓库已经接单，谁说了算？

你可能发现：“发货”里混着仓库接单、拣货、出库、运输几个动作。原来的一条规则，建立在一个含混概念上。

有效的学习循环是：**具体案例 → 提出模型 → 写一个可运行片段 → 找反例 → 改进模型**。模型会随知识积累变得更有解释力。

原书第1章列出的五个有效建模要素，可以记成：模型连接实现、共用模型语言、对象表达知识和规则、持续精炼、通过讨论与实验检验想法。它们是一套相互促进的活动。（书内9—10页，PDF31—32页。）

### 2. 统一语言：让一个业务词贯穿讨论和代码

Ubiquitous Language，常译作统一语言或通用语言，是团队以领域模型为基础共同使用的语言。它需要进入对话、需求、代码、测试，而不只是留在术语表里。

| 含混说法 | 更容易验证的说法 |
| --- | --- |
| 发货后不能取消 | 履约已进入“拣货中”时，拒绝普通取消 |
| 把状态改成取消 | 接受取消请求，释放尚未履约的购买承诺 |
| 退款成功订单就没了 | 订单仍保留身份和历史；退款记录资金处理结果 |

对应的方法名可以是 `requestCancellation()`，对应测试可以是“拣货中的订单拒绝取消”。业务人员不必读懂全部实现，也能判断测试讲的规则是否正确。

**统一语言可以演进，也有适用范围。** 同一个词在不同上下文里可以有不同模型；需要避免的是，在同一个模型范围内悄悄使用几种含义。

### 3. 模型驱动设计：让模型和实现互相约束

Model-Driven Design 的关键是选择能在软件中有效表达的模型，并让实现忠实体现它。

一个常见断裂是：分析人员画出“履约计划”，开发人员却把所有规则写进 `OrderManager` 的状态判断里。分析模型解释业务，代码模型负责运行，两套长期不相通。

更好的做法是共同调整：发现“履约计划”在业务上确实重要，就在实现中表达；如果设计太难实现，也要回到模型讨论是否需要简化。

Hands-On Modelers 强调参与建模的人应接触实现，负责实现的人也要参与建模。只传递一张完美类图，难以形成这条反馈回路。

# 统一语言与模型驱动设计

> [!summary] 读完你能回答
> - 业务说"发货前可以取消"，为什么不能直接写成 `status < SHIPPED`？
> - 统一语言和术语表有什么区别？它要出现在哪些地方？
> - 分析模型和代码"各说各话"会出什么问题，怎么避免？

**原书对应**：第 1—3 章。来源、页码约定见 [[2-Wiki/编程语言/领域驱动设计/DDD蓝皮书读书笔记|DDD导读]]。

## 1. 知识消化：边做边学，别指望一次拿齐需求

原书叫它 Knowledge Crunching，直译是"嚼碎知识"。意思是：开发者和业务专家把零散的事实、经验和例外反复讨论，慢慢整理成一个能解释业务的模型。

举个例子。第一次听到"发货前可以取消"，先别急着写 `status < SHIPPED`，而是追问具体情况：

- 仓库已经拣货、但还没出库，算发货了吗？能取消吗？
- 一部分商品发出去了，剩下的怎么办？
- 系统显示没发货，可仓库已经接单了，听谁的？

问着问着你就会发现，"发货"这个词里其实混着好几件事：仓库接单、拣货、出库、运输。原来那一条规则，是建在一个含糊的概念上的。

所以靠谱的学习循环长这样：

**具体案例 → 提出模型 → 写一段能跑的代码 → 找反例 → 改进模型**

转得越多圈，模型越能解释业务。

原书第 1 章总结了有效建模的五个要素，可以记成一句话：**模型连着实现，大家说同一种语言，对象装着知识和规则，持续提炼，靠讨论和实验检验。** 这五件事是互相促进的，不是五个独立步骤。（书内 9—10 页，PDF 31—32 页。）

## 2. 统一语言：一个业务词从讨论一路用到代码

Ubiquitous Language，常译作"统一语言"或"通用语言"，指团队**以领域模型为基础**共同使用的语言。它不能只躺在术语表里，而要真正出现在对话、需求、代码和测试中。

对比一下：

| 含糊的说法 | 更容易验证的说法 |
| --- | --- |
| 发货后不能取消 | 履约已进入"拣货中"时，拒绝普通取消 |
| 把状态改成取消 | 接受取消请求，释放还没履约的购买承诺 |
| 退款成功订单就没了 | 订单仍然保留身份和历史；退款单独记录资金处理结果 |

落到代码里，方法名可以叫 `requestCancellation()`，测试名可以叫"拣货中的订单拒绝取消"。这样，业务人员不用读懂实现，光看测试名就能判断规则对不对。

> [!warning] 别走极端
> 统一语言**可以演进，也有适用范围**。同一个词在不同上下文里可以有不同含义，这没问题（见 [[2-Wiki/编程语言/领域驱动设计/限界上下文与上下文映射|限界上下文]]）。真正要避免的，是在**同一个模型范围内**悄悄混用几种意思。

## 3. 模型驱动设计：让模型和代码互相约束

Model-Driven Design 的关键有两点：**选一个能在代码里顺利表达的模型，再让代码老老实实地体现它。**

常见的断裂是这样的：分析人员画了一个"履约计划"，开发人员却把所有规则塞进 `OrderManager` 的一堆状态判断里。分析模型负责解释业务，代码模型负责跑起来，两套东西长期不相通。

更好的做法是两边一起调整：

- 如果"履约计划"在业务上确实重要，就在代码里把它表达出来。
- 如果某个设计在代码里实在太难实现，就回到模型讨论，看能不能简化。

原书还有一个配套原则叫 Hands-On Modelers：**建模的人要摸代码，写代码的人也要参与建模。** 只把一张"完美类图"扔过墙，这条反馈回路就断了。

## 一分钟回顾

- 知识消化是一个循环：案例 → 模型 → 代码 → 反例 → 改进。
- 听到含糊的业务词，先用具体情境追问，常常能挖出藏在里面的几个概念。
- 统一语言要进入对话、代码和测试，不只是一张术语表。
- 同一个模型范围内，一个词只能有一种意思。
- 模型和代码要能互相修正：建模的人写代码，写代码的人参与建模。

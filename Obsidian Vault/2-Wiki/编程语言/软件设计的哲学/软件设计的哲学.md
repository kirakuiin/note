# 软件设计的哲学

这组文档讨论如何设计容易理解、使用和修改的软件。九个主题从复杂性的成因出发，逐步讲解模块边界、接口、错误处理、设计比较和代码表达，并通过具体案例说明方法与取舍。

> [!summary] 学习主线
> 软件设计要降低理解和修改的难度。先识别依赖与模糊，再通过深模块、信息隐藏、合适的通用接口和错误语义减少使用者要掌握的知识；最后用命名、注释、一致性与持续改进，使剩下的重要信息容易被发现。

## 一、先建立一条因果链

系统变得难改，往往不是因为某次巨大的错误，而是许多小依赖和隐含规则不断累积。它们表现为：一个变化牵动很多位置、完成任务前要掌握很多背景、甚至不知道还有哪些地方需要考虑。

模块化的作用，是让开发者在工作时只面对相关的一部分复杂性。但模块也增加接口和协作成本，所以拆得细不自动等于简单。

深模块用较简单的完整接口提供有价值的能力。信息隐藏解释了这种深度如何形成：让内部设计知识不再成为外部依赖。通用接口和合理默认值让一套机制服务多个当前场景；复杂性下沉让共同的困难只处理一次。

无法消除的知识仍要说清楚。注释、名称和一致性帮助读者看到必要契约，而设计两次、持续重构与测量让这些边界在演进中得到修正。

## 二、几个原则要成对理解

| 原则 | 同时必须记住的边界 |
| --- | --- |
| 隐藏复杂性 | 调用者必须知道的约束不能省略 |
| 模块应该深 | 无关职责塞在一个类里不会自动产生深度 |
| 接口适度通用 | 当前使用若需要大量适配，通用化可能过头 |
| 复杂性下沉 | 底层不应因此掌握不属于它的业务策略 |
| 拆分有助于理解 | 新接口和跨方法依赖也有成本 |
| 减少异常处理 | 失败尚未恢复时不能伪装成功 |
| 先写注释 | 说明必须完整，不能靠删掉约束制造简洁 |
| 保持一致性 | 不同概念不应被强行统一 |
| 持续改善设计 | 在实际约束下选择可验证的步骤 |

这些是判断方向，不是免于推理的规则。出现危险信号后，应带着同一个实际任务比较替代方案。

## 三、危险信号速查

| 观察到的现象 | 进一步检查 | 详细说明 |
| --- | --- | --- |
| 学会接口几乎等于学会实现 | 模块是否没有隐藏足够工作 | [[深模块与抽象]] |
| 一项格式或策略在多处写死 | 是否泄露了共同知识 | [[信息隐藏与模块边界]] |
| 按“读取、处理、写入”拆开后仍同步变化 | 执行顺序是否掩盖知识边界 | [[信息隐藏与模块边界]] |
| 常见调用必须学习大量少用选项 | 默认值和高级接口能否分离 | [[通用接口与复杂性下沉]] |
| 通用模块不断增加特定业务入口 | 机制是否混入专用策略 | [[通用接口与复杂性下沉]] |
| 多层方法传递相同参数且几乎不处理 | 每一层增加了什么能力 | [[分层拆分与合并]] |
| 相似代码反复出现 | 是否缺少合适机制，或控制流不合理 | [[分层拆分与合并]] |
| 两个方法必须来回跳转才能理解 | 是否形成连体方法 | [[分层拆分与合并]] |
| 注释只是把语句翻译一遍 | 是否缺少目的、契约和理由 | [[注释命名与可理解性]] |
| 接口说明充满私有结构与算法 | 抽象是否把实现泄露给使用者 | [[注释命名与可理解性]] |
| 名字模糊，或很难准确命名 | 概念和职责是否清楚 | [[注释命名与可理解性]] |
| 必须写很长的说明才知道如何使用 | 是否有过多前提、状态与特例 | [[注释命名与可理解性]] |
| 快速阅读时容易作出错误猜测 | 哪些关键知识不可见或不一致 | [[注释命名与可理解性]] |

各调用者重复处理错误、优化缺少测量等具体检查，分别见 [[错误与特殊情况]]和 [[演进性能与综合应用]]。

## 四、把设计判断用于重构、模式和代码表达

[[📚大纲（重构）|重构]]通过保持行为的步骤调整现有结构。可以提炼，也可以内联；决定依据是整体理解成本与知识边界，而不是手法本身看起来是否先进。

[[📚大纲（设计模式）|设计模式]]提供成熟的解决方案和共同语言，但需要同时计算新增角色、接口与配置的代价。模式名称本身不能证明设计合适。

代码表达可以从命名、函数结构和注释三方面改善：提取函数要检验独立性，注释要检验信息增量。短函数可能更清楚，但过度拆分会增加跳转；注释能补全契约，但复述代码没有帮助。相关方法也可参阅 [[代码整洁之道]]。

## 五、学完后用三个任务检验理解

1. 为同一需求画出两种接口，写出典型调用，并解释哪一方承担协调复杂性。可跟做 [[设计两次]]中的跨行删除案例。
2. 找一段已有代码，指出一个具体的依赖或模糊问题，提出改法及其代价，而不只贴危险信号标签。
3. 只凭接口说明预测空值、边界、失败和状态变化，再核对实现。如果必须靠实现者口头补充，找出缺失知识应放的位置。

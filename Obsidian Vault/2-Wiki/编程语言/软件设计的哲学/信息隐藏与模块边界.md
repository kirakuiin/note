# 信息隐藏与模块边界

> [!summary] 本篇要解决的问题
> 模块边界应围绕“哪些知识需要一起变化”建立。把字段设为 private 只是访问控制；只有调用者不再依赖内部决策，才能获得信息隐藏的收益。

## 一、隐藏的对象是设计知识

信息隐藏并不是把代码变得看不见，而是使某项设计决策在边界外不再重要。例如：树怎样保持平衡、记录怎样映射到磁盘、字符串怎样编码、缓存如何淘汰。

如果调用者只需要“按键查值”，就不必知道节点结构。将内部表示从一种树改成另一种，只要对外契约保持成立，调用者就无需修改。这同时降低了学习成本和变更传播。

相反，字段虽然是 private，但 `getNodes()` 返回内部节点集合，调用者仍依据节点结构工作，就没有隐藏这项表示决策。访问权限和知识依赖是两个不同问题。

## 二、信息泄露有显式和隐蔽两种形式

显式泄露发生在接口中：返回内部可变集合、要求调用者传入存储块号、让外部决定内部初始化步骤。维护者至少还能通过接口看见这些依赖。

隐蔽泄露发生在多个实现里：两个模块各自写死同一种文件格式、两个函数分别假定相同的状态编号。它们的接口看似独立，修改时却必须同步。这类依赖往往更难被发现。

“这里也知道这个格式”是有用的审查信号。可以逐项列出一项决策的知情者，再判断它们是否真的都需要知道。

## 三、为什么按执行顺序拆分容易出错

考虑一个配置编辑工具：读取文件 → 修改设置 → 写回文件。很自然的拆法是 `Reader`、`Editor`、`Writer` 三个类。

但读取和写入都依赖键的编码、转义、版本字段和默认值。改变格式时两端必须一起修改。流程上有先后，不代表知识上彼此独立。

一种更合理的边界是：

```text
settings = ConfigFormat.decode(bytes)
updated = editSettings(settings)
bytes = ConfigFormat.encode(updated)
```

格式知识由 `ConfigFormat` 掌握，业务编辑面对结构化设置。读和写仍发生在不同时间，甚至仍是不同函数，但它们属于同一个格式抽象。

如果编码器和解码器必须独立部署，也不必强行合成一个进程或一个巨大类。可以共享清楚的格式契约与兼容性验证。该原则要求管理共同知识，并非禁止流水线结构；真正独立的处理阶段仍适合分开。

## 四、HTTP 请求的读取和解析为什么发生重复

假设把“从连接读取完整请求”和“解析请求内容”分到两个类。看起来职责清楚，但要知道读到哪里结束，读取端已经需要理解请求结构，例如请求体长度信息。解析端随后又理解一次同样的格式。

因此，读取层并不只是读字节，它已经承担一部分协议解析。将这些知识集中到一个接收请求的抽象中，调用者就能得到解析后的请求，也不必协调两次调用。

这里的关键是共享的协议知识：**若读取和解析两个阶段都必须理解同一套消息边界规则，当前边界就没有真正隔离这些知识。** 如果读取层只提供不依赖协议的字节流，它与解析层仍可以保持清楚的分工。

## 五、返回数据结构与提供操作的区别

下面两种接口看起来都能获得请求参数：

```text
request.getParams().get("count")
request.getIntParameter("count")
```

第一种可能迫使调用者理解容器类型、缺失值含义、字符串转换规则，以及容器能否被修改。第二种可以把这些工作集中在请求模块中，调用方只处理一个有意义的参数值。

但第二种还必须明确：参数缺失怎样处理、转换失败怎样处理、重复参数怎样处理。它更深的原因是封装了共同规则，不是因为方法名更长。

这也不意味着所有集合返回值都有问题。若“列出全部记录”本来就是接口的业务能力，返回只读快照或迭代视图可能很自然。要区别稳定的数据契约与直接暴露可变内部表示。

同理，不能为了信息隐藏，把请求参数中的 `count` 是否符合具体业务上限也塞进通用协议模块。协议模块可以负责通用解析，业务模块仍掌握业务约束。

## 六、默认值与局部隐藏

有些信息只在少见场景中重要。正常调用使用合理默认值，高级调用才覆盖配置，可以减少多数使用者要掌握的知识。

以 HTTP 响应为例，模块已经掌握、可以推导的信息，不应反复要求调用者填写。这样既减少参数，也避免两处信息矛盾。

隐藏不要求绝对不可访问。把少见配置与常用接口分开，是一种局部隐藏。关键是普通任务不需要先学习整个高级选项集合。

## 七、发现泄露后，怎样选择修复方式

| 发现的问题 | 可考虑的改法 | 需要防止的副作用 |
| --- | --- | --- |
| 两个模块共享大量设计知识 | 合并或重划边界 | 无关职责被一起吸入 |
| 多处实现同一机制 | 提取能隐藏该知识的模块 | 新模块只是公开原来的所有细节 |
| 外部依赖内部表示 | 提供任务级操作或稳定视图 | 接口遗漏调用者实际需要的信息 |
| 每个调用者重复设置同一选项 | 推导或默认处理 | 隐藏本应由业务决定的策略 |

单纯把重复代码搬进 `Utils`，再把全部内部结构作为参数传进去，可能只是换了泄露的位置。提取之后应重新写调用示例，确认使用者真的少知道了一些东西。

## 八、信息隐藏也适用于类内部

类内部同样可以出现“所有方法都知道所有字段”。让私有辅助方法围绕完整子任务组织、限制状态被修改的位置，可以降低类内依赖。

例如格式校验状态只由解析相关方法维护，比让日志、展示、保存方法都直接调整它更容易推理。公开接口做得很简单，还需要内部边界支持长期维护。

## 九、什么时候不能隐藏

如果调用者必须依据一项信息做决定，它就属于契约：结果是否持久化、对象是否共享、返回数据是否会变化、操作是否可能部分完成。把这些内容省略，只会形成错误抽象。

可以尝试改变实现，使某项知识真的不再重要，例如模块自行恢复短暂失败；但在承诺仍依赖调用者配合时，不能只把配合要求从文档中删掉。

> [!question] 自检
> 两个类都没有公开格式字段，为什么仍可能泄露信息？因为它们的实现可能各自依赖同一格式。合并它们后为什么还要检查接口？因为调用者若仍要自行拼接格式规则，知识并未真正被隐藏。

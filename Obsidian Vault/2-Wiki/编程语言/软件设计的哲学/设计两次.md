# 设计两次

> [!summary] 读完你能回答
> - 为什么第一个能用的方案不够？"设计两次"到底要做什么？
> - 两个方案要不同到什么程度，才算真正不同？
> - 设计到什么程度就可以开始写代码了？

第一个能用的方案，只能证明这个问题有解。**比较几个真正不同的方案，你才能看清它们各自把复杂性放在了哪里**，然后找到更好的边界。

> [!note] 设计两次 ≠ 实现两次
> 它要求你比较的是**思路**，不是把产品完整做两遍。

## 1. 为什么不能只给第一个方案挑毛病

只看一个方案时，你很容易把它的代价当成"需求本来就这样"。比如底层按行存储文本，你就会理所当然地认为每个调用者都得处理跨行编辑。只有看到了按范围操作的接口，你才会发现：这些负担其实是**接口选择**带来的，不是需求本身带来的。

备选方案就像一个参照物，帮你分清哪些困难来自需求，哪些是当前结构自己制造的。就算最后还是选了第一个，你也应该能讲清楚它为什么在真实约束下更合适，而不是"因为最先想到"或者"已经写了很多代码"。

比较还能提升你的设计能力：你会一次次看到，哪些边界容易泄露知识、哪些表示会制造特殊情况。这种反馈，比只做一个实现更容易积累判断力。

## 2. 两个方案要多不同，才算"不同"

把 `deleteText` 改名成 `removeText`，或者给同一组方法换个类名，都不算实质差异。真正的差异通常来自这几个方面：

- **用什么概念表达操作**：按行、按字符，还是按范围？
- **谁来负责协调**：每个调用者自己做，还是交给公共模块？
- **什么是权威状态**：直接存储，还是从别的状态推导出来？
- **边界按什么划**：按执行阶段、按共享知识，还是按稳定的能力？

> [!tip] 别故意找个烂方案来陪衬
> 可以选一个同样合理、只是优先照顾不同目标的设计，并认真写出它的优点。这样的比较才有意义。

## 3. 先固定任务，别拿不同的问题来比

假设要设计一个支持插入、删除和替换文本的编辑器，至少要支持跨行操作。为了把注意力集中在接口上，先不考虑并发编辑；位置用 ASCII 字符串里从零开始的偏移量，换行符也占一个位置。

要编辑的内容是：

```text
abc
def
ghi
```

它的字符串形式是 `"abc\ndef\nghi"`。现在要删除 `[2, 9)`，也就是 `"c\ndef\ng"`，保留前缀 `"ab"` 和后缀 `"hi"`，结果是 `"abhi"`。

除了这个任务，还要比较普通插入、粘贴多行、删除空范围，以及恢复被删掉的内容。**别只挑恰好对某个方案有利的数据来演示。**

## 4. 方案 A：按行操作

```text
getLine(index) -> String
setLine(index, content)
insertLine(index, content)
deleteLine(index)
```

**优点**：如果底层本来就是一个行数组，实现起来很直观，读写整行也很自然。

**完成同一个任务时，调用者要做什么**：先找出范围两端分别在哪一行；取第一行删除起点之前的部分，再取最后一行删除终点之后的部分；把两段拼起来替换第一行；最后删掉中间和末尾被吸收的行。

```text
prefix = getLine(0).beforeColumn(2)   // "ab"
suffix = getLine(2).fromColumn(1)     // "hi"
setLine(0, prefix + suffix)
deleteLine(2)
deleteLine(1)
```

这还只是这一个跨行案例，同一行内删除、删到末尾、换行约定这些还得另外处理。调用者已经得懂行的表示方式、怎么拼接、删除后索引怎么变。好几种编辑操作可能都要重复这套逻辑。

**评价**：它让存储模块的实现变轻松了，却把文本操作的机制漏给了界面。如果产品只做整行处理，代价可能不大；要支持任意选区编辑，代价就很明显了。

## 5. 方案 B：按单个字符操作

```text
charAt(offset) -> Character
insertChar(offset, character)
deleteChar(offset)
```

**优点**：接口很少，能表达任意文本变化，也不再直接暴露行结构。

删除同一个范围时，可以从后往前删，避免还没删的字符位置发生移动：

```text
for offset from 8 down to 2:
    deleteChar(offset)
```

这比手工拼行通用多了，但每个批量操作的调用者还是得自己管循环、顺序和中间状态。如果每删一个字符都要发一次通知或记一条历史，删一大段就会产生一大堆额外动作。

性能也不能简单地说"就是多循环七次"：内部可能每次都要搬动数据。具体开销取决于表示和实现，但这个接口已经**堵死了模块"一次处理整段"的机会**。

**评价**：参数和方法都很少，可调用者仍然要承担共同的机制。**简单的原语，不一定能拼出好用的高层接口。**

## 6. 从前两个方案的问题，推出方案 C：按范围操作

前两个方案有个共同问题：用户要删的明明是"一个范围"，调用者却得把它翻译成一大堆存储动作。既然已经有了文本模块，为什么不让它完整地处理范围修改呢？

```text
read(start, end) -> String
insert(position, content)
delete(start, end)
```

同一个删除任务现在只需要：

```text
delete(2, 9)
```

文本模块内部可以用行数组、分块、间隙缓冲区等任何表示来实现。调用者只依赖范围语义，不依赖拼行算法。

> [!warning] 简洁不能靠跳过问题换来
> `delete(2, 9)` 还不是完整的设计。还得规定：范围是不是左闭右开？空范围怎么处理？位置无效怎么办？操作失败时是否保证原子性？修改后旧的位置还有效吗？

至于"替换"，可以先想想"删除 + 插入"够不够用。如果用户需要一次通知、一条历史记录，或者一个不可分割的替换操作，那就有理由提供 `replace(start, end, content)`。这是从当前需要推出来的操作，而不是为了少一个方法，就逼调用者自己去协调。

## 7. 把比较结果写下来

| 维度 | 按行 | 按单字符 | 按范围 |
| --- | --- | --- | --- |
| 任意跨行删除 | 调用者自己拼行 | 调用者自己循环 | 模块一次完成 |
| 调用者需要知道 | 行的表示和边界 | 索引变化和循环顺序 | 范围契约 |
| 批量优化的空间 | 取决于调用者怎么组合 | 容易被原语粒度限制 | 模块可以选整体算法 |
| 适合的任务 | 整行处理 | 确实需要单字符原语 | 编辑器选区和批量修改 |
| 主要代价 | 表示泄露 | 协调逻辑散落各处 | 模块内部实现更复杂 |

在已经固定的编辑器需求下，范围接口更有吸引力：调用者更简单，复杂性进入了本来就掌握文本表示的模块。但如果需求换成"逐行处理日志"，这个选择就要重新评估。

> [!important] 设计两次的真正产出
> 不只是选出一个"赢家"，还要说清楚**它在什么约束下更好**，以及**为此付出了什么代价**。

## 8. 设计到什么程度，就可以开始写了

先勾勒出关键方法，再比较优缺点，不需要让每个候选方案都达到能上线的程度。可以准备这些：职责说明、核心接口、典型调用、关键状态和错误语义。只有那些**靠推理解决不了的关键疑问**，才值得做小原型或者实际测量。

比如，比较接口用伪代码就够了；但如果某种数据结构在大文件上的性能决定了方案是否可行，那就做个有代表性的性能实验。**别拿"设计两次"当理由，复制出两套完整的产品。**

花多少时间探索，要和决策的影响相称：被广泛使用、改起来代价很高的接口，值得多想想；局部的、随时能改的细节，没必要写厚厚的报告。当比较已经揭示了关键差异，剩下的问题能在实现中低成本验证时，就可以开始动手了。

## 9. 接口和实现，要分开比较

范围接口定下来之后，实现还可以另外比较：按行存储是否方便现有操作？分块怎么支持插入？间隙缓冲区是否适合典型的编辑位置？**接口选择关心的是使用成本和信息隐藏，实现选择更关心内部的简单性和性能。**

不要因为"内部是行数组"，就决定外部也必须按行操作。反过来，用了范围接口，也不代表底层一定是一个连续的字符串。

如果所有候选方案都很别扭，也别硬从里面挑一个。把它们的共同缺陷列出来，重新审视抽象或职责分配，常常能找到第三种设计。**比较不是投票，而是一种发现问题的工具。**

## 10. 常见误用

- **先把偏爱的方案做出来，再找理由证明它好**：比较得太晚，已经有沉没成本了。
- **只比实现代码的行数**：忽略了调用者、文档和错误处理。
- **用一堆猜测的未来需求证明通用框架必要**：缺少眼下的收益。
- **只列优缺点，不写同一任务的调用示例**：关键的复杂性没落到看得见的地方。

> [!question] 练习
> 为"加载配置"设计两个方案：一个让调用者自己依次读取、解析、校验；另一个由模块直接返回完整的配置对象。写出加载失败后各自处于什么状态，以及加入"版本迁移"时分别要改哪里。如果你觉得后者更好，理由应该是**知识和责任更集中**，而不只是调用代码行数更少。

## 一分钟回顾

- 第一个能用的方案只证明"有解"；比较才能看清**复杂性被放在了哪里**。
- 真正的不同来自：用什么概念、谁来协调、什么是权威状态、边界怎么划。
- 先固定同一个任务，用同一个例子跑每个方案。
- 文本编辑案例：按行（表示泄露）、按字符（协调散落）、按范围（模块扛复杂性）。
- 只设计到能比较为止，不要实现两遍；接口和实现分开比。

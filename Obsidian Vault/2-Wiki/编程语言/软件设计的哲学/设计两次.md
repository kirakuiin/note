# 设计两次

> [!summary] 本篇要解决的问题
> 第一种能工作的方案，只证明问题有解。比较几个真正不同的方案，才能看见各自把复杂性放在了哪里，并找到更好的边界。设计两次要求比较思路，不要求把产品完整实现两遍。

## 一、为什么不能只检查第一种方案有没有缺陷

单看一个方案，很容易把它的代价视为“需求本来就这样”。例如面向行存储文本，于是认为每个调用者必须处理跨行编辑。只有看到范围接口，才会发现这些负担其实来自接口选择。

备选方案提供参照，帮助区分需求本身的困难与当前结构制造的困难。即使最后保留第一案，也应能解释为什么它在真实约束下更合适，而不是因为最早想到或已经写了很多代码。

比较还会提升设计能力：你会反复看到哪些边界容易泄露知识、哪些表示制造特殊情况。这样的反馈比只完成一个实现更容易形成判断经验。

## 二、“不同方案”需要有多不同

把 `deleteText` 改成 `removeText`，或把同一组方法换一个类名，不算有实质差异。有效差异通常来自：

- 用什么概念表达操作：行、字符还是范围。
- 谁承担协调：每个调用者还是公共模块。
- 什么状态是权威状态：直接存储还是从其他状态推导。
- 边界按什么划分：执行阶段、共享知识还是稳定能力。

不必刻意挑一个荒谬方案衬托偏爱的方案。可以选择同样合理、但优先照顾不同目标的设计，认真写出它的优点。

## 三、先固定任务，避免拿不同问题比较

假设要设计一个支持插入、删除和替换文本的编辑器，至少包括跨行操作。暂不处理并发编辑；为了把讨论集中在接口上，位置采用 ASCII 字符串中的零起始偏移，换行也占一个位置。

待编辑内容为：

```text
abc
def
ghi
```

其字符串表示为 `"abc\ndef\nghi"`。要删除 `[2, 9)`，即 `"c\ndef\ng"`，保留前缀 `"ab"` 和后缀 `"hi"`，结果为 `"abhi"`。

还要比较普通插入、粘贴多行、空范围删除，以及恢复被删除内容。不要只选择恰好符合某方案的数据来演示。

## 四、方案 A：按行操作

```text
getLine(index) -> String
setLine(index, content)
insertLine(index, content)
deleteLine(index)
```

**优点**：如果底层本来就是行数组，实现直观；整行读取和修改也自然。

**同一任务的调用过程**：调用者先找出范围两端所在的行，取第一行删除起点前的部分，再取最后一行删除终点后的部分，把两段拼起来，替换首行，最后删除中间及末尾被吸收的行。

```text
prefix = getLine(0).beforeColumn(2)   // "ab"
suffix = getLine(2).fromColumn(1)     // "hi"
setLine(0, prefix + suffix)
deleteLine(2)
deleteLine(1)
```

这里只展示这个特定跨行案例；同一行、末尾和换行约定还需要单独定义。调用者已经知道行表示、拼接方式和删除时的索引变化。多个编辑操作可能重复这套逻辑。

**评价**：它方便了存储模块实现，却把文本操作机制泄露给界面。若产品只做整行处理，代价可能很小；对于任意选区编辑，代价更明显。

## 五、方案 B：按单个字符操作

```text
charAt(offset) -> Character
insertChar(offset, character)
deleteChar(offset)
```

**优点**：接口少，可以表达任意文本变更，不再直接暴露行结构。

删除同一范围时，可以从末端向前删除，避免尚未删除字符的索引移动：

```text
for offset from 8 down to 2:
    deleteChar(offset)
```

这比手工拼行更通用，但每个批量调用仍要管理循环、顺序和中间状态。如果每删除一个字符都会发通知或记录历史，大段删除还会产生大量额外动作。

性能也不能简单推断为“循环七次慢一点”：内部可能每次都移动数据。具体开销取决于表示与实现，但接口已经限制了模块把整段操作一次处理的机会。

**评价**：参数和方法数量很少，调用者却仍承担共同机制。简单原语不一定构成好用的高层接口。

## 六、从前两案的问题推导方案 C：按范围操作

前两案共同的问题是：用户要删除一个范围，调用者却必须把它翻译成许多存储动作。既然文本模块存在，就可以由它完整处理范围修改。

```text
read(start, end) -> String
insert(position, content)
delete(start, end)
```

删除任务现在直接表达为：

```text
delete(2, 9)
```

文本模块可以用行数组、块、间隙缓冲区等不同表示实现它。调用者只依赖范围语义，不依赖拼行算法。

但 `delete(2, 9)` 仍不是完整设计。还需要规定范围是否左闭右开、空范围行为、无效位置、操作失败的原子性，以及修改后旧位置是否仍然有效。接口简洁不能靠跳过这些问题获得。

对于替换，可以先考虑删除加插入是否足够；如果用户需要一次通知、一次历史动作或不可分割的替换，就有理由提供 `replace(start, end, content)`。这是由当前需要推导出的操作，不是为了少一个方法强迫调用者自行协调。

## 七、把比较结果写下来

| 维度 | 按行 | 按单字符 | 按范围 |
| --- | --- | --- | --- |
| 任意跨行删除 | 调用者拼行 | 调用者循环 | 模块一次完成 |
| 调用者需知 | 行表示与边界 | 索引变化与循环顺序 | 范围契约 |
| 批量优化空间 | 依赖调用组合 | 容易被原语粒度限制 | 模块可选择整体算法 |
| 适合的任务 | 整行处理 | 单字符原语需求 | 编辑器选区与批量变更 |
| 主要代价 | 表示泄露 | 共同协调散落 | 模块内部实现更复杂 |

在已经固定的编辑器需求下，范围接口更有吸引力。它让调用者更简单，且复杂性进入了本来就掌握文本表示的模块。如果需求改为逐行日志处理，这个选择需要重新评估。

这就是设计两次的关键结果：不仅给出胜者，还说清楚它在哪些约束下更好，以及为此承担了什么代价。

## 八、设计到什么程度才开始实现

先勾勒关键方法，再比较优缺点，不必让每个候选都达到可上线程度。可以准备：职责说明、核心接口、典型调用、关键状态与错误语义。只在无法靠推理解决的关键疑问上制作小原型或测量。

例如，接口比较可以用伪代码完成；若候选数据结构在大文件上的成本决定可行性，再做有代表性的性能实验。不要以“设计两次”为由复制两套完整产品。

探索时间应与决策影响相称：广泛使用、修改代价高的接口值得多想，局部可逆细节不必写厚重报告。比较已经揭示关键差异、剩余问题可以在实现中低成本验证时，就可以进入实现。

## 九、接口和实现要分别比较

范围接口确定后，实现仍可以另做比较：按行存储是否便于现有操作，字符块怎样支持插入，间隙缓冲区是否符合典型编辑位置。接口选择关心使用成本与信息隐藏，实现选择更关心内部简单性和性能。

不要因为“内部是行数组”，就直接决定外部必须按行操作。反过来，范围接口也不意味着底层一定是连续字符串。

若所有候选都很别扭，不必从两者中硬选。把共同缺陷列出来，重新检查抽象或职责分配，往往能找到第三种设计。比较不是一次投票，而是一种发现问题的工具。

## 十、常见误用与练习

- 先实现偏爱的方案，再找理由证明它优越：比较太晚，已经有沉没成本。
- 只比较实现行数：忽略调用者、文档和错误处理。
- 用大量猜测的未来需求证明通用框架必要：缺少当前收益。
- 只列优缺点却不给同一任务的调用示例：关键复杂性没有落到可观察的位置。

> [!question] 练习
> 为“加载配置”设计两案：调用者自己依次读取、解析、校验，或模块返回完整配置对象。写出加载失败后的状态，以及加入版本迁移时分别需要改哪里。若后者更好，理由应是知识和责任更集中，而不仅是调用行数少。

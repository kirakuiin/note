# 错误与特殊情况

> [!summary] 本篇要解决的问题
> 错误处理的设计目标是减少必须理解和处理特殊情况的位置，同时保留调用者作出正确决定所必需的失败信息。忽略错误不等于解决错误。

## 一、异常的成本为什么容易被低估

这里的“异常”不限于语言中的 `throw`，错误码、特殊返回值、失败回调同样会改变正常流程。

正常路径描述“下一步做什么”；失败路径还要确定“已经做了多少、留下什么状态、能否恢复、如何向上说明”。恢复动作自己还可能失败。处理器分散在多个调用点时，这些推理会重复发生。

因此，评价一个会抛出许多错误的模块时，不能只看模块实现多么简短。它把多少恢复义务转交给了其他地方，也属于接口复杂性。

## 二、四种方法处理的是不同层面

| 方法 | 改变了什么 | 适合的条件 |
| --- | --- | --- |
| 通过定义规避错误 | 合理的边界情况成为正常语义 | 调用者不需要把该情况视为失败 |
| 屏蔽异常 | 底层自行恢复，维持原承诺 | 底层有能力完整处理 |
| 聚合异常 | 多个失败由共同边界处理 | 这些失败有相同的收尾或响应方式 |
| 明确终止 | 不再维持无法兑现的运行承诺 | 没有合理恢复办法，继续运行更危险 |

不要跳过语义分析直接选择一种语法。例如，把多个 `catch` 合成一个 `catch Exception`，并不自动构成好的异常聚合。

## 三、通过定义规避错误：改变契约，而非捕获后假装成功

### 删除例子

若契约是“删除一个存在的对象”，目标不存在可能算失败；若契约是“返回后目标不存在”，目标原本不存在时，承诺已经满足。

```text
ensureAbsent(key):
    remove key if present
    succeed if key is absent
```

这种定义适合清理临时状态：无论此前执行到哪一步，都可以调用同一个清理操作。

但权限不足、存储不可达等情况并不能等价于“不存在”。如果无法确认结果，就不能按同一种正常返回处理。若业务需要知道究竟删除了几个对象，也可以返回计数，同时仍允许零个。

调用者先检查存在、再删除，也不必然解决问题，因为两次操作之间状态可能改变。更好的契约应由真正执行操作的模块负责兑现。

### 范围截取例子

某些截取接口可以定义为返回“指定范围与有效内容的交集”，从而不必在每次调用前截断越界索引。

这适合宽容的内容截取。但如果越界代表程序违反关键不变量，严格报错也可能更合适。尤其要明确负数是从尾部计数还是无效坐标，不能把不同语言的切片规则当成一种通用语义。

### 延后资源释放

文件删除可以采用另一种生命周期设计：先将名称从目录中移除，已经打开该文件的使用者仍可继续访问，直到不再有引用时才释放数据。这样不必把“仍有人使用”传播为每个使用者都要处理的失败。

这种设计将“禁止新访问”和“释放已有资源”分开处理。能否采用它取决于具体文件系统、共享模式和平台能力，不能假设所有文件删除接口都提供相同保证。

## 四、屏蔽异常：处理完成后才算隐藏

可靠传输可以在内部处理丢包，使应用不必对每个数据包重试。关键是底层确实完成恢复，或在恢复无法完成时按接口报告失败。

```text
错误做法：发送失败 -> 捕获 -> 返回成功
合理方向：可恢复故障 -> 尝试恢复 -> 成功兑现承诺或报告最终失败
```

例如，网络文件客户端可以在服务暂时不可用时等待恢复，避免每个应用分别实现恢复逻辑。代价是调用可能长时间阻塞。是否适合等待，取决于操作能否重试、应用能否接受阻塞，以及是否需要超时和取消。

某次请求没有收到响应，不代表远端没有执行。重复操作可能产生重复副作用，因此重试机制还必须考虑幂等性或去重。把不确定结果吞掉，会破坏调用者判断正确性的能力。

## 五、聚合异常：放在能统一恢复的边界

请求中可能缺少多个参数，也可能有多个参数格式错误。如果每次读取参数都单独捕获，再生成相似错误响应，就会重复响应与清理知识。

可以让参数提取模块描述具体问题，由请求处理边界统一响应：

```text
dispatch(request):
    try:
        return handle(request)
    catch InvalidRequest as error:
        return invalidRequestResponse(error.safeMessage)
```

这段伪代码中，参数读取者知道错误发生的原因；边界知道怎样结束当前请求。中间层若没有恢复价值，就不必每层捕获再抛出。

聚合的对象应是有共同处理语义的一组错误。内部程序缺陷、权限失败、暂时不可用可能需要不同响应；同一边界可以统一处理，但不能把它们都误报为同一种原因。对外消息与内部诊断也可分开，避免让实现细节成为用户契约。

屏蔽常发生在调用树下方，聚合常发生在上方，两者并不矛盾：它们都在寻找能减少重复处理的位置。

## 六、统一恢复机制与恢复代价

在具备副本恢复能力的存储系统中，某些罕见的小范围损坏，可以交给已经存在的服务器恢复流程处理，避免再建立一套复杂的局部恢复机制。

这种设计减少恢复路径种类，也让公共恢复流程得到更多使用。但代价是扩大恢复范围。只有发生频率、恢复成本和系统承诺允许时才合理，不能把常见小故障全部变成大范围重启。

## 七、何时终止比勉强继续更合理

在无法恢复的内部不一致、资源失败等情况下，输出清楚诊断并终止，可能比在每个调用点伪造恢复逻辑更简单。

必须区分终止一次请求、一个工作进程和整个服务。若系统承诺依靠副本恢复数据，恢复本身就是产品能力，不能为了简化代码取消它。是否终止取决于需求及故障隔离方式，不能只按错误名称决定。

## 八、把错误设计纳入接口设计

对每一种失败，依次回答：它能否被正常语义吸收；底层是否能恢复；哪个边界有足够信息作出处理；失败后系统处于什么状态；调用者还需要知道什么。

要减少的是没有必要的特殊处理，而不是有价值的验证。空范围删除可以正常返回，不表示损坏的内部状态也应被自动修正为“看起来成功”。

> [!question] 自检
> 缓存读取失败后回源算哪一种？若回源能兑现原来的读取承诺，是屏蔽；若直接返回空值并让用户以为记录不存在，就可能隐藏了关键失败信息。

# 错误与特殊情况

> [!summary] 读完你能回答
> - 异常处理的成本为什么总被低估？
> - 规避、屏蔽、聚合、终止，这四种方法各适合什么情况？
> - "把错误吞掉"和"通过定义规避错误"有什么本质区别？

错误处理设计的目标是：**减少需要理解和处理特殊情况的地方，同时把调用者做正确决定所需的失败信息保留下来。** 忽略错误不等于解决了错误。

## 1. 异常的成本为什么容易被低估

这里说的"异常"不只是语言里的 `throw`。错误码、特殊返回值、失败回调，都会打断正常流程。

写正常流程时，你只需要想"下一步做什么"。可一旦出错，要想的就多了：做到一半了吗？留下了什么烂摊子？还救得回来吗？要不要告诉上层？更糟的是，补救动作本身也可能失败。如果每个调用点都各自处理一遍，这些问题就要被想很多遍。

所以，评价一个到处抛错误的模块时，别只看它自己的代码多简短。**它把多少收拾残局的活推给了别人，这笔账也要算进接口复杂性。**

## 2. 四种方法，处理的是不同层面的问题

| 方法 | 改变了什么 | 适合什么时候用 |
| --- | --- | --- |
| **通过定义规避错误** | 合理的边界情况变成了正常语义 | 调用者本来就不需要把这种情况当失败 |
| **屏蔽异常** | 底层自己恢复，继续兑现原来的承诺 | 底层有能力把问题完整处理掉 |
| **聚合异常** | 多个失败交给一个共同的边界处理 | 这些失败的收尾和响应方式相同 |
| **明确终止** | 不再硬撑一个兑现不了的运行承诺 | 没有合理的恢复办法，继续跑更危险 |

> [!warning] 先想语义，再选语法
> 比如把好几个 `catch` 合并成一个 `catch Exception`，并不自动等于好的异常聚合。

## 3. 通过定义规避错误：改契约，而不是捕获后假装成功

### 例子：删除

- 如果契约是"**删除一个存在的对象**"，目标不存在时就可能算失败。
- 如果契约是"**返回后，这个目标一定不存在**"，那目标本来就不存在时，承诺已经满足了。

```text
ensureAbsent(key):
    remove key if present
    succeed if key is absent
```

这种定义特别适合清理临时状态：不管之前执行到了哪一步，都可以调用同一个清理操作。

> [!warning] 别走极端
> - 权限不足、存储连不上，这些情况**不等于**"不存在"。没法确认结果时，就不能当成正常返回。
> - 如果业务需要知道到底删了几个，也可以返回一个计数，同时允许它是零。
> - "先检查存不存在、再删除"也不一定能解决问题，因为两步之间状态可能变了。更好的契约应该由**真正执行操作的模块**来兑现。

### 例子：范围截取

某些截取接口可以定义成"返回指定范围和有效内容的**交集**"，这样调用前就不用每次都先截断越界的索引。

这适合比较宽容的内容截取。但如果越界意味着程序违反了关键的不变量，严格报错可能更合适。尤其要说清楚负数是"从尾部倒数"还是"无效坐标"，别把不同语言的切片规则当成同一种通用语义。

### 例子：延后释放资源

文件删除可以换一种生命周期设计：先把名字从目录里移除，已经打开这个文件的人还能继续用，直到没人引用了才真正释放数据。这样就不用把"还有人在用"变成每个使用者都要处理的失败。

这个设计把"禁止新的访问"和"释放已有资源"分开处理。能不能这么做，取决于具体的文件系统、共享方式和平台能力，别假设所有文件删除接口都有同样的保证。

## 4. 屏蔽异常：真处理完了，才算"藏起来"

可靠传输协议在内部处理丢包，应用就不用对每个数据包自己重试。关键是：**底层真的完成了恢复**，或者恢复不了时按接口约定报告失败。

```text
错误做法：发送失败 -> 捕获 -> 返回成功
合理方向：可恢复故障 -> 尝试恢复 -> 成功兑现承诺，或报告最终失败
```

比如，网络文件客户端可以在服务暂时不可用时等它恢复，免得每个应用都自己写恢复逻辑。代价是调用可能会阻塞很久。适不适合等，要看操作能不能重试、应用能不能接受阻塞、需不需要超时和取消。

> [!danger] 一个很容易踩的坑
> 一次请求没收到响应，**不代表**远端没执行。重复操作可能造成重复的副作用，所以重试机制必须考虑幂等或去重。把"结果不确定"直接吞掉，会让调用者失去判断对错的能力。

## 5. 聚合异常：放到能统一收尾的边界上

一个请求里可能缺了好几个参数，也可能有好几个参数格式不对。如果每读一个参数都单独 catch、再生成一个差不多的错误响应，响应和清理的知识就会被重复很多遍。

更好的做法是：参数提取模块负责描述具体问题，请求处理的边界负责统一响应。

```text
dispatch(request):
    try:
        return handle(request)
    catch InvalidRequest as error:
        return invalidRequestResponse(error.safeMessage)
```

在这段伪代码里，读参数的人知道**为什么**出错，边界知道**怎么结束**这次请求。中间层如果没有恢复的价值，就不必每层都 catch 一下再抛出去。

> [!warning] 别走极端
> 聚合的应该是**有相同处理语义**的一组错误。内部程序缺陷、权限失败、暂时不可用，可能需要完全不同的响应。同一个边界可以统一接住它们，但不能把它们误报成同一种原因。另外，对外的消息和内部的诊断信息也可以分开，别让实现细节变成用户能依赖的契约。

屏蔽常常发生在调用树的**下方**，聚合常常发生在**上方**，两者并不矛盾：它们都在找一个能减少重复处理的位置。

## 6. 统一恢复机制，以及它的代价

在有副本恢复能力的存储系统里，某些罕见的小范围损坏，可以直接交给已有的服务器恢复流程处理，不用再专门造一套复杂的局部恢复机制。

这样恢复路径的种类变少了，公共恢复流程也被用得更多、更可靠。但代价是**恢复范围变大了**。只有当发生频率、恢复成本和系统承诺都允许时，这么做才合理。不能把常见的小故障全变成大范围重启。

## 7. 什么时候直接终止，比硬撑着更合理

遇到无法恢复的内部不一致、资源耗尽之类的情况，输出清楚的诊断信息然后终止，可能比在每个调用点伪造恢复逻辑更简单。

但一定要分清楚你终止的是**一次请求、一个工作进程，还是整个服务**。如果系统承诺了要靠副本恢复数据，那恢复本身就是产品能力，不能为了让代码简单就把它砍掉。要不要终止，取决于需求和故障隔离方式，不能只看错误的名字。

## 8. 把错误设计当成接口设计的一部分

对每一种可能的失败，依次问自己：

1. 它能不能被正常语义吸收？
2. 底层能不能自己恢复？
3. 哪个边界有足够的信息来处理它？
4. 失败后系统处于什么状态？
5. 调用者还需要知道什么？

要减少的是**没必要的**特殊处理，不是有价值的检查。空范围删除可以正常返回，不代表损坏的内部状态也该被自动"修正"成看起来成功的样子。

> [!question] 自检
> 缓存读失败后回源查询，算哪一种？如果回源能兑现原来的读取承诺，那是**屏蔽**；如果直接返回空值，让用户以为记录不存在，那就是把关键的失败信息藏起来了。

## 一分钟回顾

- 异常的真实成本 = 每个调用点都要想"做到哪了、留下什么、能不能救、要不要上报"。
- **规避**：改契约，让边界情况变成正常结果（如"确保不存在"）。
- **屏蔽**：底层真恢复了才算；没收到响应≠没执行，重试要考虑幂等。
- **聚合**：在能统一收尾的边界上一起处理，但别把不同原因混成一种。
- **终止**：无法恢复时清楚地停下，并分清停的是请求、进程还是服务。
- 永远不要"捕获后返回成功"。

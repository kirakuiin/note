# 注释命名与可理解性

> [!summary] 读完你能回答
> - "读实现就知道了"为什么不能代替注释？
> - 好注释和复述代码的注释差在哪？接口注释和实现注释各写什么？
> - 好名字的标准是什么？一致性为什么这么重要？

好代码让读者能**又快又准**地做出判断。结构减少需要知道的东西，名字突出关键含义，注释补上契约和理由，三者一起降低理解成本。

## 1. 为什么"读实现就知道了"不够

能从实现里推出行为，不代表应该让每个调用者都这么做。抽象的价值，恰恰就是让使用者**可以跳过实现**。只有类型和方法名，通常说不清这些事：边界包不包含、单位是什么、资源归谁、会不会阻塞、失败后处于什么状态。

比如 `read(start, end)`，它没告诉你包不包含 `end`，也没告诉你返回的是一份副本还是共享的视图。这些知识不该让每个使用者都重新调查一遍。

不写注释的常见理由有四个：

1. "代码自己会说话。"
2. "没时间写。"
3. "注释会过时。"
4. "现有的注释都没什么用。"

可问题是，类型和名字往往表达不了完整的契约；不写说明，后面的使用者就得一次次重新调查。正确的做法是**只写有新信息的内容**，并把更新注释当作日常修改的一部分，而不是追求注释的数量。

## 2. 注释要提供和代码不同层次的信息

### 更精确：补上声明表达不了的含义

```text
timeout: Integer
```

写一句"超时时间"，等于什么都没说。更有用的写法是：**"等待一次响应的最长毫秒数；0 表示不等待；不包括排队时间。"** 这里的每一项都会改变正确的用法。

给变量写注释，重点解释它**代表什么**：单位、范围、默认值、归属、不变量。别把所有给它赋值的地方机械地列一遍。

### 更抽象：帮读者建立整体直觉

"遍历列表，检查状态，再修改标志"，这只是把语句复述了一遍。如果真实的目的是"**把还没发往同一服务器的请求合并起来，减少往返次数**"，这句话才解释了为什么这几个判断会出现在一起。

这两个方向并不冲突：高层说明告诉读者这段代码**为什么存在**，低层契约保证他不会**误解细节**。要避免的是停留在和代码完全相同的层次上逐句翻译。

## 3. 接口注释和实现注释，写给不同的人

| 类型 | 主要读者 | 应该写什么 |
| --- | --- | --- |
| 类的接口说明 | 要选择、使用这个类的人 | 它提供什么抽象，一个实例代表什么，主要限制 |
| 方法的接口说明 | 调用者 | 行为、参数、返回值、前提、错误、副作用 |
| 实现注释 | 要改方法内部的人 | 算法思路、各阶段的意图、不那么显然的原因 |
| 跨模块设计说明 | 要改协作关系的人 | 共享的契约、相关的位置、必须保持的关系 |

接口说明里别塞用户不需要的算法、私有字段和内部 RPC 名称。实现注释也不应该逼读者跑到每个调用点去拼凑这个局部函数的含义。

**怎么判断一项信息属于接口？** 以范围查询为例：比较键时用什么顺序，会影响查询结果，所以属于接口；服务器内部怎么组织索引，通常不属于。恢复机制如果对使用者完全透明，可以藏起来；如果它会表现为超时、失败或结果变化，那这些外部表现就必须写明。

## 4. 一份完整但不啰嗦的接口说明

比如一个读取文本范围的接口，可以这样写：

```text
readRange(start, end) -> String

返回文本中 [start, end) 的副本，不修改原文本。
start 与 end 为当前文本的零起始字符偏移，换行计入长度。
要求 0 <= start <= end <= length；越界时报告 InvalidRange。
start == end 时返回空字符串。
```

它告诉了使用者：结果是什么、单位是什么、边界怎么算、空范围怎么办、出错怎么报。但它**没有**告诉使用者内部是按行还是按块存的，因为这不需要他知道。

这里选了严格的越界语义，是为了演示一份完整的契约。如果产品需要宽容的截取，也可以设计另一种契约，见 [[错误与特殊情况]]。重点是**把选择写清楚**，而不是只写一句"返回指定文本"。（真实的国际化文本还得说清楚"字符"指什么单位。）

而像"先定位两端所在的块，再拼接涉及的片段，避免复制无关内容"这种信息，就该放在实现内部。调用者不需要背负这些算法知识。

## 5. 先写注释，怎么帮你做设计

推荐的顺序是：先写类的抽象说明，再写主要公开方法的说明和签名；检查整体是否连贯之后，再确定关键状态、填写方法体。中途发现需要新方法时，也先写下它的承诺。

这不是说文档写完就冻结了。实现的反馈会修正文档，而文档反过来也会**暴露设计问题**：

- 一个方法要列出一堆互不相关的情况才能解释清楚 → 可能混了好几种职责。
- 每个方法都要解释同一套准备步骤 → 可能该把这个生命周期封装起来。
- 注释必须详细介绍私有结构 → 接口可能还没形成足够的抽象。
- 一个变量的含义要写很长才说得清 → 可能一个状态承担了好几种意思。

> [!warning] 别走极端
> 删掉限制、把文字缩短，修不好设计。只有**完整、清楚**的说明才有诊断价值。复杂的业务契约也可能确实需要比较长的文档，不能按字数自动判定设计不好。

## 6. 好名字：让读者的第一反应接近事实

如果"文件里的逻辑块"和"磁盘上的物理块"都叫 `block`，就很容易混用：同一个整数，在两种坐标系里可能指向完全不同的数据。用 `fileBlock` 和 `diskBlock`，甚至干脆用不同的类型，就能把这个区别摆到明面上。名字不只是风格问题，**读者会根据名字形成假设**。

类似的命名问题：

| 名字 | 可能被误解成 | 更明确的方向 |
| --- | --- | --- |
| `time` | 是时刻还是时长？单位是什么？ | `deadlineMs`、`elapsedMs`，按实际含义选 |
| `status`（布尔类型） | true 到底代表什么？ | `cursorVisible` 这种一看就能判断真假的谓词 |
| `data` | 什么中间结果都可能叫这个 | `decodedSettings` 这种说出实际含义的名字 |
| `delete(selection)` | 只能删当前选区 | 如果实际支持任意范围，就叫 `delete(range)` |

> [!tip] 精确不等于越长越好
> 上下文已经说清楚的词可以省掉。几行循环里用 `i` 可能就够了；作用域很大的变量，名字就需要承载更多含义。名字要传达**关键的区别**，而不是塞进全部实现过程。

**起不出好名字，本身就是一个信号。** 如果很难找到一个准确又简短的名字，先怀疑一下概念本身清不清楚：是不是把两种状态混在了一个变量里？是不是把两个任务塞进了一个方法？命名困难往往是设计在给你反馈，不只是词汇量不够。

## 7. 一致性为什么比局部的小改进更重要

一致性让读者可以**复用已经学会的规则**：同样的含义用同样的名字，同类的操作有相似的接口，同一种范围约定处处成立。否则，读者每到一个地方都得重新研究一遍。

**不变量**是一种更强的一致性，比如"内部每一行总是以换行结尾"，或者"范围总满足 start <= end"。它减少了状态的组合，让其他代码可以放心地依赖这个保证。关键是要明确**由哪个边界负责建立和维持它**，而不是把责任分散给所有调用者。

保持一致可以靠约定文档、自动检查和代码评审。别因为个人偏好，在已有的约定旁边另起一套。

> [!warning] 别走极端
> 不同的概念，也不该为了形式统一而被强行叫同一个名字。一致性的意思是"**看起来一样的东西，确实有相同的语义**"，不是让每段代码都长得一模一样。

## 8. 几种会让代码变模糊的写法

- **事件回调**：调用点是间接的，读者很难看出谁在什么条件下触发了它。应该写明触发条件、执行在哪个线程、生命周期，必要时提供相关入口的指引，而不只是注释回调内部的语句。
- **没有语义的通用容器**：返回 `Pair<Integer, Boolean>` 很方便，但 `first` 和 `second` 说明不了任何含义。用一个有名字的记录类型，读者在使用处就能看懂字段；只有局部含义已经很明显时，简单的元组才不会增加负担。
- **出人意料的副作用**：构造对象时偷偷启动线程，查询时顺手推进后台任务，这些都可能影响调用者。如果要保留这种设计，就得写进契约，或者考虑改成更显式的操作。
- **声明掩盖了关键行为**：接口类型可以隐藏具体实现，但如果调用方依赖某种访问复杂度或线程安全保证，这些约束仍然要写进契约。问题不在于声明的类型和实际容器是否一致，而在于**关键行为是否写明**。
- **排版把结构挤没了**：适当的空行和阶段说明能把控制流显示出来。代码更紧凑不等于更好读；不过合理排版也代替不了好的结构设计。

## 9. 跨模块的知识放在哪？怎么防止它过时？

消除不了的共享契约，应该放在**修改者自然会经过的地方**。比如新增状态码必然要改枚举定义，那就在那里注明"还要同步更新哪些映射"。如果没有这样一个必经之处，可以写一份设计说明，再在相关代码处引用它。

原则是：**权威的解释尽量只有一份，其他地方提供找到它的路径。** 到处复制同一段说明，更新时很容易漏；只写在提交记录里，读者可能根本不知道要去查。

本地的实现理由放在相关代码旁边，修改行为时同时更新契约。离实现越远的总览，越要保持抽象，这样实现细节变化时它才不容易失效。具体的维护方法见 [[演进性能与综合应用]]。

## 10. 该改代码，还是该补注释？

两件事要同时检查：**代码本身还能不能通过改名、调结构变得更清楚？** 以及 **剩下的必要信息有没有写出来？** 前者减少需要解释的东西，后者补上从局部代码看不出来的契约。

- 如果注释只是在解释一个晦涩的表达式 → 先考虑改代码。
- 如果注释在说明资源归属、范围约定或设计理由 → 光靠提取短函数，往往代替不了它。

> [!question] 自检
> 同事读完还是理解错了，应该补在哪里？先找出到底缺了什么信息：名字误导人就改名字，契约缺失就补接口说明，局部策略不清楚就补实现注释，职责混乱就重新设计。别默认"加一大段注释"就能解决所有问题。

## 一分钟回顾

- 注释的价值在于提供**代码里没有的信息**：更精确的契约，或更抽象的意图。
- **接口注释**写给调用者（做什么、前提、错误、副作用）；**实现注释**写给维护者（为什么这么做）。
- 先写注释能暴露设计问题：难以描述的，往往就是设计得不好的。
- 好名字让第一反应接近事实；**起不出名字，往往是概念不清**。
- 一致性 = 看起来一样的东西，语义真的一样。
- 跨模块知识：权威说明只放一份，放在修改者必经的地方。

# 注释命名与可理解性

> [!summary] 本篇要解决的问题
> 好的代码让读者能迅速作出正确判断。结构减少需要了解的知识，名字突出关键含义，注释补全契约和理由；三者共同降低理解成本。

## 一、为什么“读实现就知道了”不够

能从实现推导行为，不等于应该要求每个调用者都这样做。抽象的价值正是让使用者跳过实现。只写类型和方法名，通常不能说明边界是否包含、单位、资源所有权、阻塞行为以及失败后的状态。

例如 `read(start, end)` 没告诉你是否包含 `end`，也没告诉你返回的是副本还是共享视图。这些知识不应由每个使用者重新调查。

不写注释的常见理由包括：代码已经自解释、没有时间、注释会过时、现有注释没有价值。但类型和名称不一定能表达完整契约；缺少说明也会让后续使用者反复调查。有效的做法是只记录有信息增量的内容，并把更新说明纳入日常修改，而非追求注释数量。

## 二、注释要提供与代码不同层次的信息

### 更精确：补上声明表达不了的含义

```text
timeout: Integer
```

“超时时间”并没有增加信息。更有用的说明是：“等待一次响应的最长毫秒数；零表示不等待；不包含排队时间。”每一项都能改变正确用法。

变量注释宜解释它代表什么：单位、范围、缺省值、所有权、不变量。不要把所有写入位置机械列成一段执行说明。

### 更抽象：帮助读者形成整体直觉

“遍历列表，检查状态，再修改标志”只是复述语句。若真实目的为“把尚未发送到同一服务器的请求合并，减少往返”，这才解释了多个判断为什么出现在一起。

两种方向并不冲突：高层说明告诉读者为什么存在这段代码，低层契约保证他不会误解细节。应避免停留在和代码完全相同的层次上逐句翻译。

## 三、接口注释与实现注释服务不同的人

| 类型 | 主要读者 | 应包含的信息 |
| --- | --- | --- |
| 类的接口说明 | 选择和使用这个类的人 | 它提供什么抽象，一个实例代表什么，主要限制 |
| 方法的接口说明 | 调用者 | 行为、参数、结果、前提、错误、副作用 |
| 实现注释 | 修改方法内部的人 | 算法策略、阶段意图、不明显的原因 |
| 跨模块设计说明 | 修改协作关系的人 | 共享契约、相关位置及必须保持的关系 |

接口说明应避免塞入用户不需要的算法、私有字段和内部 RPC 名称。实现注释也不应要求读者到每个调用点去拼凑局部函数的含义。

以范围查询为例：比较键时采用什么顺序，会影响结果，属于接口；服务器如何组织索引，通常不属于接口。恢复机制若对使用者透明，可以隐藏；若会表现为超时、失败或结果变化，外部表现必须说明。

## 四、一份完整但不过度的接口说明

例如，一个读取文本范围的接口可以这样说明：

```text
readRange(start, end) -> String

返回文本中 [start, end) 的副本，不修改原文本。
start 与 end 为当前文本的零起始字符偏移，换行计入长度。
要求 0 <= start <= end <= length；越界时报告 InvalidRange。
start == end 时返回空字符串。
```

它告诉使用者结果、单位、边界、空范围和错误语义，却不告诉使用者内部按行还是按块存储。

这里选择严格越界语义，是为了演示一个完整契约；若产品需要宽容截取，也可以设计另一个契约，见 [[错误与特殊情况]]。重点是把选择说清楚，不能只写“返回指定文本”。真实国际化文本还需明确字符单位。

下面的信息则适合放在内部相关位置：“先定位两端所在的块，再拼接涉及的片段，避免复制无关内容。”调用者无需承担该算法知识。

## 五、先写注释怎样帮助设计

可以先写类的抽象说明，再写主要公开方法的说明和签名；检查整体是否连贯后，再确定关键状态并填写方法体。发现新方法时，也先描述其承诺。

这并非让文档一旦写出就冻结。实现反馈会修正文档，文档也反过来暴露设计问题：

- 一个方法要列出许多不相关情形才能解释，可能混合了多个职责。
- 每个方法都要解释同一组准备步骤，可能应封装生命周期。
- 注释必须详细介绍私有结构，可能接口没有形成足够抽象。
- 变量含义要写很长才能讲清，可能一项状态承担了多种意义。

但是，删掉限制、缩短文字不能修复设计。只有完整清楚的说明才有诊断价值。复杂业务契约也可能合理地需要较长文档，不能按字数自动判定设计坏。

## 六、名字应该让第一次猜测接近事实

如果逻辑文件块与物理磁盘块都叫 `block`，就容易混用二者：同样的整数值，在两种坐标体系下可能指向完全不同的数据。使用 `fileBlock` 和 `diskBlock`，甚至用不同类型表达，可以让这种区别显式可见。名字不是纯风格，读者会依靠它形成假设。

类似的命名问题还有：

| 名字 | 可能误解 | 更明确的方向 |
| --- | --- | --- |
| `time` | 时刻还是时长，什么单位 | `deadlineMs`、`elapsedMs`，按实际含义选择 |
| `status`，类型为布尔 | true 到底代表什么 | `cursorVisible` 等能判断真假的谓词 |
| `data` | 所有中间结果都可能叫它 | `decodedSettings` 等实际含义 |
| `delete(selection)` | 只能删除当前选区 | `delete(range)`，如果实际支持任意范围 |

精确不等于越长越好。已经由上下文清楚表达的词可以省略；几行循环中的 `i` 可能足够，跨越很大作用域的变量则需要更多语义。名称应传达关键区别，不应塞入全部实现过程。

若很难找到一个准确、简短的名字，先怀疑概念是否清楚：是否把两种状态混在一个变量里，是否把两个任务混在一个方法里。命名困难可以是设计反馈，不只是词汇不足。

## 七、一致性为什么比局部小改进更重要

一致性让读者复用已经学会的规则：相同含义采用相同名字、同类操作有类似接口、同一范围约定在各处成立。否则每个局部都要重新研究。

不变量是一种更强的一致性，例如“内部每行始终带换行”或“范围总满足 start <= end”。它减少状态组合，使其他代码可以安全依赖这项保证。关键是明确由哪个边界建立并维持它，而非把责任散落给所有调用者。

保持一致可依靠约定文档、自动检查和评审。不要因个人偏好，在已有约定旁边另起一套；但不同概念也不应为了形式统一被强行叫同一个名字。

因此，一致性的含义是“看起来一样时，确实具有相同语义”，不是让每一段代码长得一样。

## 八、几种让控制流和数据含义变模糊的做法

**事件回调**：调用点间接，读者难以看出谁在什么条件下触发它。应说明触发条件、执行线程及生命周期，必要时提供相关入口，而不是只注释回调内部语句。

**无语义的通用容器**：返回 `Pair<Integer, Boolean>` 很方便，但 `first` 与 `second` 不说明实际含义。命名记录让读者在使用处理解字段；只有局部语义已很明显时，简单元组才不会增加多少负担。

**超出预期的副作用**：构造对象时启动线程、查询时推进后台任务，都可能影响调用者。若保留这种设计，应明确契约，也可以考虑更显式的操作。

**声明掩盖了关键行为**：接口类型可以隐藏具体实现，但若调用方依赖某种访问复杂度或线程安全保证，这些约束仍需成为契约。问题在于关键行为是否明确，而不在于声明类型是否与实际容器类型完全相同。

**排版压缩结构**：适当空行和阶段说明可以显示控制流。代码更紧凑不等于更好读，合理排版也不等于用注释替代结构设计。

## 九、跨模块知识放在哪里，怎样避免过时

无法消除的共享契约，应放在修改者自然会到达的位置。例如新增状态码必经枚举定义，可以在那里指出必须同步更新的映射。没有单一位置时，可建立一份设计说明，并在相关代码处引用。

原则是：权威解释尽量只有一份，其他位置提供发现路径。到处复制同一段说明，会增加更新遗漏；只写在提交记录里，则读者可能不知道该去查。

本地实现理由放在相关代码附近，修改行为时同时更新契约。较远的总览保持抽象，减少因实现细节变化而失效。具体维护过程见 [[演进性能与综合应用]]。

## 十、怎样选择改代码还是补注释

可以同时检查两件事：代码本身是否还能通过命名和结构调整变得更清楚，剩下的必要信息是否已经写出来。前者减少解释负担，后者补全无法从局部代码直接看出的契约。

如果注释只是解释一个晦涩表达式，先考虑改代码；如果说明资源所有权、范围约定或设计理由，单靠提取短函数未必能代替它。

> [!question] 自检
> 同事读完仍误解时，应该补在哪里？先找出缺失信息：名字误导就改名字，契约缺失就补接口，局部策略不明就补实现说明，职责混乱则重新设计。不要默认加一大段注释就能解决所有问题。

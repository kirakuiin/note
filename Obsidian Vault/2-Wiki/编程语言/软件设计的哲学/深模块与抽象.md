# 深模块与抽象

> [!summary] 读完你能回答
> - 什么叫"深模块"？深度为什么不等于方法少或代码多？
> - 接口到底包括哪些东西？为什么没写在签名里的规则也算？
> - 抽象有哪两种失败方式？

一个模块值不值得存在，要看两件事：**它替你干了多少活**，以及**你为了用它得先学多少规则**。"深度"说的就是这两者的比例，跟继承有几层没有关系。

## 1. 模块的价值：让你不用一次理解整个系统

模块可以是函数、类、子系统，也可以是一个服务。只要有对外接口和内部实现，就能讨论它的深度，不一定非得是面向对象的写法。

理想情况是：**用**一个模块，只要懂它的接口；**改**一个模块，只要懂它自己的实现，再加上它依赖的那些模块的接口。如果每次调用前都得钻进实现里看看，那这个模块边界就没帮读者省下什么。

模块也是有代价的。每多一个模块，就多一条需要命名、解释、被人发现和维护的边界。所以**"把代码拆开"本身不算设计收益**。只有新边界藏起来的复杂性，比它带来的学习成本更多时，拆分才划算。

## 2. 接口到底包括什么

接口有两部分：

- **语言能检查的**：参数类型、返回类型、公开方法。
- **行为契约**：能不能传空值？什么时候会阻塞？资源谁来释放？失败后会不会留下改了一半的状态？

```text
save(document) -> Success
```

这个签名很短，可它没回答：返回时数据落盘了吗？会覆盖旧文件吗？失败了会不会把原文件弄坏？能不能同时调用？只要调用者**必须**知道这些答案，它们就是接口的一部分。不能因为没写在声明里，就不算进复杂性。

> [!important] 衡量接口复杂性的标准
> 算的是**正确使用它所必需的全部知识**。删掉注释并不会让接口变简单，只会让必要的知识更难被发现。

## 3. 深和浅：比的是收益和成本

可以把模块想象成一个矩形：**上边的宽度代表接口的复杂性，面积代表它提供的功能**。

- **又宽又扁**：用起来成本高，藏起来的工作却很少。
- **又窄又深**：接口简单，背后却干了很多活。

（这只是个定性的比喻，别真拿"实现行数 ÷ 参数个数"去算。）

| 维度 | 深模块 | 浅模块 |
| --- | --- | --- |
| 调用者看到的 | 稳定的任务和契约 | 内部步骤、数据表示和协调规则 |
| 完成常见任务 | 几个自然的操作就够 | 要拼接一堆底层操作 |
| 内部实现变了 | 大多数变化留在边界里面 | 很容易传导到调用代码 |
| 文档 | 写全契约也不难懂 | 不解释一堆实现细节就没法用 |

> [!warning] 别走极端
> 浅模块不等于必须删掉。简单的数据结构、必要的适配器可能都很浅，但它们有自己的用途。需要的是讲清它的价值，而不是把所有模块都硬"做大"。

## 4. 完整对比：配置加载的复杂性被放到了哪里

假设好几个调用方都要读同一种应用配置，比较下面两套接口。

### 方案 A：把内部步骤全变成公开接口

```text
reader = ConfigReader(path)
raw = reader.readBytes()
parser = ConfigParser()
tree = parser.parse(raw)
validator = ConfigValidator(schema)
validator.check(tree)
config = ConfigValues(tree)
config.applyDefaults()
```

每个类看起来都很短小。但调用者得知道调用顺序、数据怎么传、默认值和校验谁先谁后，还要在每一步失败时自己收拾状态。哪天要加一个"配置迁移"步骤，所有调用方可能都得插一行新调用。

### 方案 B：直接提供完整的加载能力

```text
config = AppConfig.load(path)
timeout = config.requestTimeoutMs()
```

公开的契约很明确：**成功时，返回的配置已经填好默认值、通过了校验；失败时，报告配置问题，不会给你一个初始化到一半的对象。** 读取、解析、迁移这些步骤，都可以继续在内部实现。

收益不在于从八行变成了两行，而在于**调用者不用再掌握"这几步怎么组合"的知识**。加迁移步骤只改 `AppConfig` 内部就行，错误处理也有了统一的边界。

> [!note] 换个需求，结论可能反过来
> 如果你做的产品本身就是一个让用户自由组合解析和校验的开发工具，方案 A 的拆分可能正是价值所在。深度永远是**相对于提供的能力和目标用户**来判断的。

## 5. 两个经典例子：Unix I/O 和 Java 流

**Unix 文件 I/O 是深模块的典范。** 打开、读写、定位、关闭这几个常用操作背后，藏着目录查找、设备交互、缓存等大量工作。你只管处理文件，不用自己调度磁盘、管理块缓存。

**Java 的流组合则是另一种风格。** 想要带缓冲的对象读取，你得自己把文件流、缓冲流、对象流一层层套起来。这种组合保留了灵活性，但也要求每个使用者都知道该装配哪些对象。如果缓冲是绝大多数人都需要的，那就应该默认提供，再给特殊需求留一个关闭或替换的口子。

这并不是在否定 [[装饰模式]]。装饰确实提供了运行时组合的灵活性，问题在于：**这份灵活性值不值得让每个普通调用者每次都付装配成本？**

> [!tip] 一条好用的原则
> **让常见情况简单，把少见的选项单独隔离出来。** 这往往比把所有选择都摊给所有人要好。

垃圾回收是另一个例子：普通对象的回收工作由运行时替你承担了。不过文件、连接这类资源的生命周期，以及必要的运行时配置，还是得你自己明确管理。

## 6. 抽象的两种失败：漏太多，或藏太多

抽象是**针对某个使用任务**建立的简化视图，省略掉的应该是"你不必知道的信息"。它有两种失败方式：

1. **暴露太多**：读配置的人得先懂解析树，用文件的人得手动选缓存策略。不相关的细节成了日常负担。
2. **隐藏太多**：保存接口没说清"返回成功只代表写进了内存缓存"。需要持久化的调用者就会基于错误的认识去用它。

对于第二种，加一个 `flush`，或者把持久化契约写明白，表面上接口变大了，系统却更容易被正确使用。**好的抽象不能靠漏掉关键语义来换取简短的外表。**

[[信息隐藏与模块边界]]讲怎么找出可以藏起来的知识；[[注释命名与可理解性]]讲怎么把必须暴露的知识说清楚。

## 7. 深模块 ≠ 大类，也 ≠ 长函数

"模块可以比较大"不是让你把所有功能都塞进一个类。一个同时管配置、界面、网络和日志的万能类，就算只有一个 `run()` 入口，内部也很可能耦合成一团。

同理，十行的方法可能已经封装了一个完整独立的判断；一千行的函数也可能只是把一堆杂乱状态挤在了一起。要同时检查三件事：**对外简不简单？内部是不是围绕一个连贯的职责组织的？维护者能不能只看局部就推理清楚？**

还有一个反面现象叫**"类泛滥"（classitis）**：把类的数量当成设计质量。每个类都很小，可整个系统需要更多的跳转、转发、对象生命周期和调用顺序，这些累积起来的成本不能视而不见。

## 8. 实际检查方法

1. 先把完整的接口说明写出来，再写两三个典型的调用示例。
2. 如果说明里必须讲内部数据结构，或者调用示例里满是准备和收尾步骤，就检查有没有可以下沉到模块里的工作。
3. 设想一次内部改动，列出会受影响的调用方有哪些。

> [!question] 自检
> - 方法少就一定深吗？不一定，单个方法也可能藏着一堆隐含规则。
> - 实现复杂就一定深吗？不一定，内部乱糟糟不等于提供了强大的能力。
> - 一次调用就完成任务一定好吗？还得检查它是不是把调用者本该做的业务决定也藏起来了。

## 一分钟回顾

- **深模块**：接口简单，背后干的活多。衡量的是"省下的工作 vs 要学的规则"。
- **接口 = 签名 + 行为契约**。正确使用所需的全部知识都算接口复杂性。
- 把内部步骤暴露成公开接口，会让每个调用者都背上"怎么组合"的知识。
- **让常见情况简单，少见选项隔离出去。**
- 抽象有两种失败：**漏太多**（细节变负担）和**藏太多**（漏掉关键语义）。

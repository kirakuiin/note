# 深模块与抽象

> [!summary] 本篇要解决的问题
> 一个模块是否值得存在，要看它替使用者承担了多少工作，以及使用者为此必须掌握多少规则。深度描述的是这两者的关系，和继承层数没有关系。

## 一、模块的价值：让你不必同时理解整个系统

模块可以是函数、类、子系统或服务。它不必采用某种面向对象语法，只要存在对外接口和内部实现，就可以讨论其深度。

理想情况下，使用一个模块，只需要理解它的接口；修改这个模块，需要理解它自己的实现及其依赖模块的接口。若调用前总要追入实现，模块边界就没有替读者省下多少理解成本。

模块化也有代价。每增加一个模块，就多出一个需要命名、解释、发现和维护的边界。因此，“把代码拆开”本身并不构成设计收益；只有新增边界隐藏的复杂性超过它带来的学习成本，拆分才值得。

## 二、接口到底包括什么

接口有可由语言检查的部分，例如参数类型、返回类型、公有方法；还有行为契约，例如是否允许空值、何时阻塞、谁释放资源、失败后是否留下部分修改。

```text
save(document) -> Success
```

这个签名很短，却没有回答：返回时是否已经落盘？是否覆盖旧文件？失败会不会破坏原文件？是否允许同时调用？如果调用者必须知道这些答案，它们就是接口的一部分，不能因为没写在声明里就不计入复杂性。

**判断接口复杂性时，应计算正确使用所必需的全部知识。** 删除注释不会让接口变简单，只会让必要知识更难发现。

## 三、深与浅：比较收益和成本

可以把模块想象成一个矩形：上边缘代表接口复杂性，面积代表提供的功能。宽而扁意味着使用成本大、隐藏的工作少；窄而深意味着简单接口背后承担了很多工作。这是定性比喻，不能用“实现行数除以参数数量”机械测量。

| 维度 | 较深的模块 | 较浅的模块 |
| --- | --- | --- |
| 调用者看到的内容 | 稳定的任务与契约 | 内部步骤、表示形式和协调规则 |
| 常见任务 | 少量自然的操作 | 拼接很多低层操作 |
| 内部实现变化 | 多数可留在边界内 | 容易传导到调用代码 |
| 文档 | 完整契约仍易理解 | 必须解释大量实现细节才会用 |

浅模块不等于必须删除。简单数据结构、必要的适配器也可能很浅，但有其用途。需要解释它的价值，而不是把所有模块强行“做大”。

## 四、完整对比：配置加载的复杂性被放到了哪里

假定多个调用方都需要读取同一种应用配置，比较下面两套伪接口。

### 方案 A：把内部阶段变成公共接口

```text
reader = ConfigReader(path)
raw = reader.readBytes()
parser = ConfigParser()
tree = parser.parse(raw)
validator = ConfigValidator(schema)
validator.check(tree)
config = ConfigValues(tree)
config.applyDefaults()
```

每个类看起来都很短，但调用者要知道顺序、数据传递、默认值与校验的关系，还要在每一阶段失败时处理相应状态。新增配置迁移步骤后，所有调用方可能都要插入新调用。

### 方案 B：提供完整的加载能力

```text
config = AppConfig.load(path)
timeout = config.requestTimeoutMs()
```

公共契约明确：成功时返回已经应用默认值并通过校验的配置；失败时报告配置问题，不返回半初始化对象。读取、解析、迁移等步骤可以继续在内部实现。

收益不是从八行变成两行，而是调用者不再掌握阶段组合知识。新增迁移步骤可以留在 `AppConfig` 内，错误处理也有统一边界。

不过，如果产品本身就是一个允许用户自由组合解析与校验的开发工具，方案 A 的分离可能有价值。相同的模块划分，在不同需求下会有不同结论。深度始终相对于提供的能力和目标使用者判断。

## 五、Unix I/O 与 Java 流组合

Unix 文件 I/O 是深模块的一个例子：常用的打开、读写、定位和关闭操作背后，隐藏了目录查找、设备交互、缓存等大量工作。调用者处理文件，不必亲自调度磁盘或管理块缓存。

另一种设计是显式组合 Java 的文件流、缓冲流和对象流，以获得带缓冲的对象读取能力。这种组合保留了选择空间，但也要求使用者知道应该装配哪些对象。若缓冲是常见需求，可以默认提供，再为特殊需求留出关闭或替换机制。

这里不是否定 [[装饰模式]]。装饰提供运行时组合的灵活性，问题是这项灵活性是否值得让普通调用者每次都付出装配成本。**使常见情况简单，同时把少见选项隔离出来**，往往比对所有使用者暴露全部选择更好。

垃圾回收进一步减少了使用者原来必须执行的动作：普通对象的回收工作由运行时承担。不过，文件、连接等资源的生命周期，以及必要的运行时配置，仍需要明确管理。

## 六、抽象为什么既可能暴露太多，也可能隐藏太多

抽象是针对使用任务建立的简化视图，省略的是“不必知道的信息”。两种失败都要避免：

1. **暴露太多**：配置读取者必须理解解析树，文件使用者必须手动选择缓存策略。无关细节成为日常负担。
2. **隐藏太多**：保存接口没有说明返回成功只代表写入内存缓存。要求持久性的调用者依据错误认知使用它。

第二种情况中，增加 `flush` 或明确持久化契约可能使表面接口变大，却使系统更容易正确使用。好的抽象不能以遗漏关键语义换取简短外观。

[[信息隐藏与模块边界]]讨论怎样寻找可以隐藏的知识；[[注释命名与可理解性]]讨论怎样把必须暴露的知识表达清楚。

## 七、深模块、长函数与大类的关系

“模块可以较大”不表示把所有功能集中进一个类。一个承担配置、界面、网络和日志的万能类，即使只有 `run()` 一个入口，也可能在内部形成难以理解的耦合。

同样，十行方法可能已经封装了一个完整、独立的判断；一千行函数也可能只是把杂乱状态挤在一起。需要同时检查：对外是否简单，内部是否围绕连贯职责组织，维护者能否局部推理。

多类症的问题是把类的数量当成设计质量。每个类都很小，整个系统却需要更多跳转、转发、对象生命周期和调用顺序，这些累积成本不能忽略。

## 八、实际检查方法

先写完整接口说明，再写两三个典型调用。如果说明必须讲内部数据结构，或调用示例充满准备与收尾步骤，检查是否存在可下沉的工作。然后设想一次内部变更，列出受影响的调用方。

> [!question] 自检
> 方法少是否一定深？不一定，单个方法也可能有许多隐含规则。实现复杂是否一定深？不一定，内部杂乱不等于提供强大能力。一次调用完成任务是否一定好？还要检查是否隐藏了调用者必须作出的业务决定。

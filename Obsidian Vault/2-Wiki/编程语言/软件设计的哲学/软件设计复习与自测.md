# 软件设计复习与自测

> [!summary] 怎么用这一页
> 先合上其他笔记，自己回答问题，再展开答案对照。答不上来的，顺着"按问题找概念"表格回去重读。题目和答案都是基于这组笔记的教学补充，不是原书内容。总览见 [[软件设计的哲学]]。

## 1. 热身：合上笔记，用五句话复述这本书

1. 这本书说的"复杂性"指什么？它有哪三种症状、两个病根？
2. 什么叫深模块？信息隐藏和它是什么关系？
3. 通用接口和复杂性下沉，各自要求把什么放在哪里？
4. 减少错误处理有哪几种办法？哪些失败绝不能藏？
5. 注释、命名、一致性分别在解决什么问题？

> [!faq]- 参考要点
> 复杂性是**理解和修改系统的难度**，表现为变更放大、认知负荷和未知的未知，病根是**依赖**和**模糊**。**深模块**用简单的接口提供大量功能，它的深度来自**信息隐藏**：内部的设计决策不再成为外部依赖。**通用接口**用少量连贯的操作表达共同机制，**复杂性下沉**把机制的麻烦留给模块，但业务策略留在上层。错误处理可以**规避**（改契约）、**屏蔽**（底层真恢复）、**聚合**（在统一边界处理）或**终止**；调用者做决定所需的失败信息不能藏。消除不了的知识，靠**注释**补契约和理由、靠**命名**让第一反应接近事实、靠**一致性**让学过的规则可以复用。

## 3. 容易混的概念，放在一起比

| 容易混的一对 | 区别在哪 | 一句话判断 |
| --- | --- | --- |
| 深模块 / 大类 | 深模块是接口简单、功能多；大类可能只是把无关职责堆在一起 | 内部是围绕一个连贯的职责组织的吗？ |
| private / 信息隐藏 | private 是访问控制；信息隐藏是调用者不依赖内部决策 | 内部表示换了，调用者需要改吗？ |
| 适度通用 / 万能接口 | 前者用少量连贯操作覆盖当前需求；后者用一堆参数和开关应付所有情况 | 当前的调用代码还简单吗？ |
| 下沉机制 / 下沉策略 | 机制（如跨行拼接）该往下沉；策略（如退格删多少）该留在上层 | 下沉后，底层要不要认识上层的概念？ |
| 规避错误 / 吞掉错误 | 规避是改契约，让结果本身就是正确的；吞掉是失败了却假装成功 | 调用者拿到的结果是真的吗？ |
| 屏蔽 / 聚合 | 屏蔽在下层把问题解决掉；聚合在上层统一收尾 | 是有人真的恢复了，还是只是集中报告？ |
| 提取子任务 / 拆分入口 | 前者对外不变、内部更清楚；后者可能把步骤甩给调用者 | 调用者要记住新的调用顺序吗？ |
| 接口注释 / 实现注释 | 前者写给调用者（做什么），后者写给维护者（为什么这么做） | 读者是要"用"它，还是要"改"它？ |
| 一致性 / 形式统一 | 一致性是相同语义用相同形式；形式统一可能把不同概念硬凑在一起 | 看起来一样的东西，语义真的一样吗？ |
| 战略式投资 / 过度设计 | 前者让现在的调用者立刻受益；后者主要靠对未来的猜测 | 能说清这次让复杂性降了多少吗？ |

## 4. 基础题：先说出理由，再展开答案

**题 1：一个模块只有一个方法 `process(data)`，它一定是深模块吗？**

> [!faq]- 参考答案
> 不一定。方法少只说明签名简单，还要看**正确使用它需要知道多少东西**：`data` 要满足什么格式？失败时处于什么状态？会不会阻塞？有没有副作用？如果这些都要调用者自己摸索，或者 `process` 内部把配置、网络、日志杂糅在一起，那它既不深也不好用。

**题 2：配置编辑工具拆成 `Reader`、`Editor`、`Writer` 三个类，每次改文件格式，Reader 和 Writer 都要一起改。问题出在哪？怎么改？**

> [!faq]- 参考答案
> 这是**按执行顺序拆分**导致的隐蔽信息泄露：读和写共享同一份格式知识，却被拆到了两个类里。可以把格式知识集中到一个 `ConfigFormat`，由它负责 `decode` 和 `encode`，业务编辑只面对结构化的设置。读和写仍然可以是两个函数，但它们属于同一个格式抽象。

**题 3：一个类的所有字段都是 private，但提供了 `getNodes()` 返回内部的节点列表。它做到信息隐藏了吗？**

> [!faq]- 参考答案
> 没有。调用者拿到节点列表后，就会按节点结构写代码，内部"怎么表示"这个决策泄露了出去，以后换数据结构就得改调用方。private 只是访问控制。更好的做法是提供任务级的操作（比如"按键查值"），或者返回一个稳定的只读视图。

## 5. 应用题：判断依据比术语更重要

**题 4：你的文本类里有 `backspace(cursor)` 和 `deleteSelection(selection)` 两个方法，现在产品要加一个"删除到行尾"的快捷键。你会怎么做？**

> [!faq]- 参考答案
> 别再往文本类里加 `deleteToLineEnd(cursor)`。这些方法把界面概念带进了底层，每加一种交互底层就要改一次。更好的做法是让文本类提供通用的 `delete(start, end)` 和定位操作，由界面层算出"从光标到行尾"的范围，再调用 `delete`。文本类负责跨行拼接这类表示知识，界面层负责"删哪个范围"的策略。

**题 5：要不要把缓存大小 `cacheSizeMb` 做成一个必填配置项，交给每个部署的人来填？**

> [!faq]- 参考答案
> 先问四个问题：谁掌握做这个决定的信息？能不能根据内存和命中率自动推导？有没有合理的默认值？普通使用者能不能完全不管它？如果模块自己能推导或有好的默认值，就不该把它变成每个人都要研究的必填项。可以保留一个高级覆盖选项给特殊场景。

**题 6：`delete(key)` 在 key 不存在时抛 `NotFoundException`，结果几乎每个调用点都包了一层 try-catch 然后忽略它。怎么改？有什么情况不能这么改？**

> [!faq]- 参考答案
> 可以**通过定义规避错误**：把契约改成"返回后 key 一定不存在"（比如叫 `ensureAbsent`），key 本来就不存在时直接成功。如果业务需要知道删了几个，可以返回一个允许为零的计数。但权限不足、存储连不上这类情况**不能**也当成"不存在"处理，因为结果无法确认，调用者需要知道真实的失败。

**题 7：网络客户端在请求超时后自动重试，重试成功就对上层返回成功。这样设计有什么风险？**

> [!faq]- 参考答案
> 超时**不代表**远端没执行。如果第一次请求其实已经执行了，重试就可能造成重复的副作用（比如重复扣款）。所以自动重试必须配合**幂等设计或去重标识**。另外还要考虑：阻塞多久可以接受？需不需要超时上限和取消？最终仍然失败时，要按约定把失败报告给上层，而不是吞掉。

**题 8：同事把 `save()` 拆成了 `prepare()`、`write()`、`finish()` 三个公开方法，说这样"职责更单一"。你怎么看？**

> [!faq]- 参考答案
> 这很可能是把**实现步骤甩给了调用者**：每个调用者都得记住调用顺序、自己传递中间状态，漏掉一步就出错，复杂性没降反升。如果拆分是为了让代码更清楚，应该保留 `save()` 这个对外入口，在内部提取独立的子任务。只有当调用者确实经常只需要其中一部分功能时，拆出多个入口才有意义。

**题 9：代码里有一行注释 `// 遍历列表，检查状态，设置标志`，还有个变量叫 `time`。分别怎么改进？**

> [!faq]- 参考答案
> 这条注释只是把代码复述了一遍，应该改成说明**为什么**，比如"把还没发往同一服务器的请求合并起来，减少往返次数"。变量 `time` 太模糊：是时刻还是时长？单位是什么？应该按实际含义改成 `deadlineMs` 或 `elapsedMs`。如果这个变量需要跨很大的作用域使用，名字就要承载更多含义。

**题 10：同事手动内联了几个热点函数，说"这样肯定更快"，代码可读性下降了不少。你会怎么评审？**

> [!faq]- 参考答案
> 先问：**优化前后有没有在相同条件下测量过？** 没有可测量收益、又让代码变复杂的优化应该撤回。如果确实存在性能问题，应先找根本性的改进（减少网络往返、换算法、避免复制），再围绕常见路径重新组织状态，而不是简单地内联所有函数。像缓冲区追加的例子那样，好的重构有机会同时减少代码和执行开销。

## 6. 怎样判断自己真的学会了

| 水平 | 你能做到 | 下一步 |
| --- | --- | --- |
| 认得名词 | 能说出"深模块""信息泄露"是什么意思 | 用每篇的例子，复述一遍"为什么" |
| 能识别问题 | 看到代码能指出危险信号 | 别只贴标签，说出具体的依赖或模糊在哪 |
| 能提出方案 | 能给出改法，并说出代价 | 对同一个任务至少写两个方案比较 |
| 能讲清取舍 | 能说明"在什么约束下，哪个方案更好" | 拿自己的真实项目做一次设计评审 |

复习时先闭卷答，再展开答案；答不出来的就回到对应的那一篇。过一段时间，找一段自己写过的代码，用这些问题重新审视一遍。
